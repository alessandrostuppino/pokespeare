WWDC22 · Module 6 — Build Challenges

Modules 1–5 taught the APIs. This module makes you re-implement, from scratch, the WWDC22 technology this project already uses — by building features large enough that you cannot avoid it.

The distinction matters. Reading RetryPolicy.swift and thinking "yes, Duration, understood" is not the same as designing a new manager and discovering for yourself where Sendable bites, where the error boundary belongs, and why the existing code made the choices it did.

Each challenge is a real feature against real endpoints, verified live while writing this document.

What is already in the project, and how each challenge forces it

WWDC22 tech Already at Challenge that forces you to rebuild it
Sendable / @Sendable closures Pokespeare.swift:3-5, APIClient.swift:9 A, B, C — every new manager must be Sendable
any existentials APIClient.swift:14 A — new request types behind one client
Primary associated types absent A (stretch)
Clock / Duration RetryPolicy.swift:9,42 A — per-request timeout budget
Regex absent C — filter parsing
NavigationStack routing SearchView.swift:14, unused B, C
Layout / Grid / ViewThatFits absent B, C
Swift Charts absent C
if/switch expressions, if let shorthand throughout all

The endpoints (verified live)

All four returned HTTP 200 while this document was written.

GET /api/v2/pokemon-species/{name} — already used by PokemonSpeciesRequest. Contains a key this project currently ignores:

{ "evolution_chain": { "url": "https://pokeapi.co/api/v2/evolution-chain/10/" } }

Note carefully: a URL, not an id. There is no evolution_chain.id field. This is a real design problem, not a detail — see Challenge A.

GET /api/v2/evolution-chain/{id} — a recursive tree:

{
  "id": 10,
  "chain": {
    "species": { "name": "pichu" },
    "evolution_details": [],
    "evolves_to": [
      { "species": { "name": "pikachu" },
        "evolution_details": [ { "min_level": null, "trigger": {} } ],
        "evolves_to": [ { "species": { "name": "raichu" }, "evolves_to": [] } ] }
    ]
  }
}

Verified for chain 10: pichu → pikachu → raichu. Branching chains exist (Eevee is chain 67) — your model must handle evolves_to having more than one element.

GET /api/v2/type/{name} — damage_relations has exactly six keys. Verified for electric:

double_damage_from → [ground]
double_damage_to   → [flying, water]
half_damage_from   → [flying, steel, electric]
half_damage_to     → [grass, electric, dragon]
no_damage_from     → []
no_damage_to       → [ground]

GET /api/v2/ability/{name} — effect_entries and flavor_text_entries, both language-tagged exactly like the flavor text PokemonManager already handles.

Rules that apply to every challenge

These are the project's existing invariants. Breaking one is a failed challenge even if the feature works.

  1. The public SDK surface stays deliberate. Today it is exactly four types: Pokespeare, Pokespeare.Error, PokemonView, PokemonViewModel. Anything new that becomes public must be a decision you can defend — audit finding C-17 was accidental public surface.
  2. One transport. APIClient is the only thing that performs a request (APIClient.swift:3-8). No new manager gets its own URLSession — finding C-03 was exactly that duplication.
  3. One error boundary. Pokespeare.Error.from(error:) (Error.swift:109-124) is the single mapping point, and its case ordering is load-bearing. New error types slot into that switch; they do not get their own escape route. Findings C-01 and C-25 were both this.
  4. No Optional as an error channel. Finding C-05. If three things can go wrong, three cases — not one nil.
  5. Everything Sendable, nothing @unchecked in production code.
  6. Tests: no assertions inside catch. Finding C-10. Use #expect(throws:).
  7. Integration tests are tagged and gated behind RUN_INTEGRATION_TESTS (TestTags.swift). Live endpoints are rate-limited; CI must stay green without them.
  8. Localize user-facing strings into both catalogs, en + it. Finding C-21.
  9. Accessibility is not optional. VoiceOver labels, Dynamic Type. Finding C-23.

Challenge A — Evolution chain service

Size: large (the main one). Forces: Sendable, existentials, generic requests, Clock/Duration, structured concurrency, the error boundary.

Goal

Add Pokespeare.evolutionChain(for:) async throws -> EvolutionChain returning the full evolution line for a Pokémon name.

Why this is harder than it looks

Three genuine design problems, in increasing order of interest:

A1 — You get a URL, not an id. pokemon-species gives evolution_chain.url. Your options:

  • Parse the id out of the URL path and build a normal EvolutionChainRequest(id:).
  • Make the request able to be constructed from an absolute URL.

HTTPRequest today builds its URL from host + path components (HTTPRequest.swift, makeURLRequest()). Whichever you choose, write down the argument against the other one. Hint: consider what happens if PokéAPI changes its URL layout, and consider which option is testable without a network.

A2 — The response is recursive. chain.evolves_to[].evolves_to[]…, arbitrarily deep, and branching (Eevee has eight). Your response model must be recursive, and your domain model probably should not be — a flat list of stages, or a tree you actually want to render, is likely nicer than mirroring the JSON. The existing response models all hand-write init(from:) with nested containers (PokemonSpeciesResponse.swift:31-44); follow that style or justify departing from it.

A3 — Two sequential requests. Species, then chain. The second depends on the first, so async let does not apply — unlike SearchViewModel.swift:172-173, where the two calls are independent. Understanding why that difference exists is half the point of this challenge.

Steps

  1. EvolutionChainRequest conforming to HTTPCodableRequest.
  2. EvolutionChainResponse — recursive, Decodable.
  3. EvolutionManager, Sendable, taking an APIClient. Domain logic only: no transport. Mirror PokemonManager.swift.
  4. EvolutionManager.Error with real cases, and a Pokespeare.Error.from(error:) overload. Add public cases only if the user could act on them differently.
  5. Wire a new closure into Pokespeare — it is a struct of closures (Pokespeare.swift:3-5), so adding a service means adding a stored closure, a public method, and a line in live(pokemonManager:translationManager:). This changes a public initializer. Think about whether that is a source-breaking change and what you would do about it in a shipped SDK.
  6. Add a per-request timeout budget using Duration, respecting the injectable-clock work from Module 3 if you did it.

Acceptance criteria

  1. evolutionChain(for: "pikachu") returns pichu → pikachu → raichu in order.
  2. A branching chain (eevee) returns all branches, not just the first.
  3. A Pokémon with no evolutions (tauros) returns a single-stage chain — not an error, and not an empty array that a caller must special-case.
  4. Unit tests with MockedSession fixtures for: happy path, branching, single-stage, 404, malformed body. No live network.
  5. Exactly one integration test, tagged .integration and gated.
  6. Every failure arrives as a Pokespeare.Error. Prove it — a test that asserts a transport failure does not surface as .unknown (that is finding C-01, and it is the single most valuable regression test in the SDK).
  7. All 53 existing SDK tests still pass.
  8. swiftlint lint --strict clean.

Stretch

Give HTTPCodableRequest a primary associated type (Module 1) and use any HTTPCodableRequest<EvolutionChainResponse> somewhere it genuinely helps. If it does not help, say so and revert — that is the correct outcome and a real finding.

Challenge B — Type matchup screen

Size: medium. Forces: NavigationStack routing, Grid, ViewThatFits, a second new manager, localization, accessibility.

Goal

From a Pokémon's detail view, navigate to a screen showing what it is strong and weak against, built from /type/{name}.

A Pokémon has one or two types — PokemonDetailRequest already fetches the detail payload, which carries them. For two types, effectiveness multiplies (double from ground × half from ground = neutral). That combination logic is domain logic and belongs in the manager, not the view, and it is exactly the kind of thing that should have unit tests with hand-built fixtures.

Steps

  1. TypeRequest, TypeResponse (the six damage_relations keys), TypeManager.
  2. Combination logic for dual types, as a pure function. Test it in isolation — no network, no view.
  3. A SwiftUI screen using Grid/GridRow for the effectiveness table.
  4. Reach it with navigationDestination — this is where Module 4's routing work pays off. If you kept the sheet, you now have a concrete reason not to.
  5. ViewThatFits so the table degrades to a list at accessibility text sizes.
  6. Localize every label into en + it, both catalogs.

Acceptance criteria

  1. Electric shows weak-to-ground, resists flying/steel/electric, no damage to ground. Verified values are in the endpoint section above.
  2. A dual-type Pokémon computes multiplied effectiveness, covered by unit tests including a ×4 and a ×0 case.
  3. Readable at the largest accessibility text size — check on device/simulator, not in the canvas.
  4. VoiceOver announces each cell meaningfully. "Two" is not meaningful; "Ground, double damage" is.
  5. No hardcoded English. Both .xcstrings updated.
  6. All existing tests pass; new manager has unit tests with fixtures.

Challenge C — Search filters and history insights

Size: medium. Forces: Regex, Swift Charts, Layout, SwiftData querying.

Goal

Let the search field accept simple filter syntax, and add a small insights view over the search history.

Filter syntax, parsed with Regex (Module 2):

type:electric          → filter history by type
before:2026-01-01      → filter by searchDate
pika                   → plain substring match
type:electric pika     → combined

Steps

  1. A Regex-based parser producing a typed SearchFilter value. Remember Regex is not Sendable — Module 2 §3 covers it, and the SDK has no @MainActor.
  2. Apply filters to the history. Today it is first(where:) in memory (SearchViewModel.swift:143) with a hand-built FetchDescriptor (:256). #Predicate is Batch 2 — for now, do it honestly in memory and write down what you would change once you have #Predicate.
  3. An insights view: searches per day from searchDate, as a BarMark chart.
  4. Accessibility: charts need explicit labels. An unlabelled chart in this app is a regression against commit 9f787fc.

Acceptance criteria

  1. Parser unit tests, parameterized, covering: each filter alone, combined, malformed input, empty input. Malformed input must degrade to plain-text search, never throw into the UI.
  2. Invalid filter values do not crash and do not silently return everything.
  3. Chart has an accessibility label and per-mark values.
  4. Localized, both catalogs.
  5. All existing tests pass.

How to choose

  • Doing one? Challenge A. It is the one that rebuilds the SDK's actual architecture.
  • Doing two? A then B. B consumes A's navigation work.
  • All three? A → B → C. C is the lightest on SDK architecture and the heaviest on UI.

Do not start B or C before Module 4, and do not start A before Module 3 if you intend to do the injectable-clock exercise — A is much more interesting with a testable clock.

What I will look at during review

When you tell me the batch is done, this is what gets read. Stated up front so nothing is a surprise:

  • Does APIClient remain the only transport?
  • Does every new error path terminate in Pokespeare.Error, with the mapping ordering intact?
  • Is anything public that did not need to be?
  • Is there an Optional standing in for an error?
  • Do any tests assert inside a catch?
  • Are integration tests gated?
  • Is the new UI usable at maximum Dynamic Type, and does VoiceOver say something useful?
  • Are new user-facing strings in both catalogs?
  • Where did you deviate from the existing patterns, and can you defend it?

The last one carries the most weight. A defended deviation beats an undefended imitation.

WWDC22 · Modulo 6 — Sfide di implementazione

I moduli 1–5 hanno insegnato le API. Questo modulo ti fa re-implementare da zero la tecnologia WWDC22 che questo progetto già usa — costruendo feature abbastanza grandi da non poterlo evitare.

La distinzione conta. Leggere RetryPolicy.swift e pensare "sì, Duration, chiaro" non è la stessa cosa che progettare un nuovo manager e scoprire da solo dove Sendable morde, dove va il confine degli errori, e perché il codice esistente ha fatto le scelte che ha fatto.

Ogni sfida è una feature reale contro endpoint reali, verificati dal vivo mentre scrivevo questo documento.

Tutti e quattro hanno restituito HTTP 200 mentre scrivevo questo documento.

GET /api/v2/pokemon-species/{name} — già usato da PokemonSpeciesRequest. Contiene una chiave che questo progetto attualmente ignora:

{ "evolution_chain": { "url": "https://pokeapi.co/api/v2/evolution-chain/10/" } }

Nota bene: un URL, non un id. Non esiste un campo evolution_chain.id. È un problema di design vero, non un dettaglio — vedi la Sfida A.

    "species": { "name": "pichu" },
    "evolution_details": [],
    "evolves_to": [
      { "species": { "name": "pikachu" },
        "evolution_details": [ { "min_level": null, "trigger": {} } ],

    ]

GET /api/v2/type/{name} — damage_relations ha esattamente sei chiavi. Verificato per electric:

Regole valide per ogni sfida

Sono le invarianti già in vigore nel progetto. Romperne una è una sfida fallita anche se la feature funziona.

  1. La superficie pubblica dell'SDK resta deliberata. Oggi sono esattamente quattro tipi: Pokespeare, Pokespeare.Error, PokemonView, PokemonViewModel. Qualsiasi cosa nuova che diventi public dev'essere una decisione che sai difendere — il finding C-17 era superficie pubblica accidentale.
  2. Un solo transport. APIClient è l'unica cosa che esegue una richiesta (APIClient.swift:3-8). Nessun nuovo manager si prende la propria URLSession — il finding C-03 era esattamente quella duplicazione.
  3. Un solo confine degli errori. Pokespeare.Error.from(error:) (Error.swift:109-124) è l'unico punto di mappatura, e l'ordinamento dei suoi case è portante. I nuovi tipi d'errore si inseriscono in quello switch; non si prendono una via di fuga propria. I finding C-01 e C-25 erano entrambi questo.
  4. Niente Optional come canale d'errore. Finding C-05. Se tre cose possono andare male, tre case — non un nil.
  5. Tutto Sendable, niente @unchecked nel codice di produzione.
  6. Test: nessuna assertion dentro catch. Finding C-10. Usa #expect(throws:).
  7. I test di integrazione sono taggati e protetti da RUN_INTEGRATION_TESTS (TestTags.swift). Gli endpoint reali hanno rate limit; la CI deve restare verde senza di essi.
  8. Localizza le stringhe utente in entrambi i catalog, en + it. Finding C-21.
  9. L'accessibilità non è facoltativa. Label VoiceOver, Dynamic Type. Finding C-23.

Sfida A — Servizio catena evolutiva

Dimensione: grande (la principale). Forza: Sendable, existential, request generiche, Clock/Duration, concorrenza strutturata, il confine degli errori.

Obiettivo

Aggiungere Pokespeare.evolutionChain(for:) async throws -> EvolutionChain che restituisce la linea evolutiva completa per un nome di Pokémon.

Perché è più difficile di quanto sembri

Tre problemi di design veri, in ordine crescente di interesse:

A1 — Ottieni un URL, non un id. pokemon-species dà evolution_chain.url. Le tue opzioni:

  • Estrarre l'id dal path dell'URL e costruire una normale EvolutionChainRequest(id:).
  • Rendere la request costruibile da un URL assoluto.

HTTPRequest oggi costruisce il suo URL da host + componenti di path (HTTPRequest.swift, makeURLRequest()). Qualunque cosa tu scelga, scrivi l'argomentazione contro l'altra. Indizio: considera cosa succede se PokéAPI cambia la struttura dei suoi URL, e considera quale opzione è testabile senza rete.

A2 — La risposta è ricorsiva. chain.evolves_to[].evolves_to[]…, profonda arbitrariamente, e ramificata (Eevee ne ha otto). Il tuo modello di risposta dev'essere ricorsivo, e il tuo modello di dominio probabilmente non dovrebbe esserlo — una lista piatta di stadi, o un albero che vuoi davvero renderizzare, è verosimilmente più comodo che rispecchiare il JSON. I modelli di risposta esistenti scrivono tutti init(from:) a mano con container annidati (PokemonSpeciesResponse.swift:31-44); segui quello stile o giustifica lo scostamento.

A3 — Due richieste sequenziali. Prima species, poi chain. La seconda dipende dalla prima, quindi async let non si applica — a differenza di SearchViewModel.swift:172-173, dove le due chiamate sono indipendenti. Capire perché esiste quella differenza è metà del senso di questa sfida.

Passi

  1. EvolutionChainRequest conforme a HTTPCodableRequest.
  2. EvolutionChainResponse — ricorsiva, Decodable.
  3. EvolutionManager, Sendable, che prende un APIClient. Solo logica di dominio: nessun transport. Rispecchia PokemonManager.swift.
  4. EvolutionManager.Error con case veri, e un overload di Pokespeare.Error.from(error:). Aggiungi case pubblici solo se l'utente potrebbe agire diversamente.
  5. Collega una nuova closure a Pokespeare — è una struct di closure (Pokespeare.swift:3-5), quindi aggiungere un servizio significa aggiungere una closure memorizzata, un metodo pubblico e una riga in live(pokemonManager:translationManager:). Questo cambia un initializer pubblico. Ragiona se sia una modifica source-breaking e cosa faresti al riguardo in un SDK spedito.
  6. Aggiungi un budget di timeout per richiesta usando Duration, rispettando il lavoro sul clock iniettabile del Modulo 3 se l'hai fatto.

Criteri di accettazione

  1. evolutionChain(for: "pikachu") restituisce pichu → pikachu → raichu in ordine.
  2. Una catena ramificata (eevee) restituisce tutti i rami, non solo il primo.
  3. Un Pokémon senza evoluzioni (tauros) restituisce una catena a stadio singolo — non un errore, e non un array vuoto che il chiamante debba trattare come caso speciale.
  4. Test unitari con fixture MockedSession per: percorso felice, ramificazione, stadio singolo, 404, corpo malformato. Nessuna rete reale.
  5. Esattamente un test di integrazione, taggato .integration e protetto.
  6. Ogni fallimento arriva come Pokespeare.Error. Dimostralo — un test che asserisce che un fallimento di transport non emerge come .unknown (è il finding C-01, ed è il singolo test di regressione più prezioso dell'SDK).
  7. Tutti i 53 test SDK esistenti passano ancora.
  8. swiftlint lint --strict pulito.

Stretch

Dai a HTTPCodableRequest un primary associated type (Modulo 1) e usa any HTTPCodableRequest<EvolutionChainResponse> dove aiuta davvero. Se non aiuta, dillo e fai marcia indietro — è l'esito corretto e un risultato reale.

Sfida B — Schermata efficacia dei tipi

Dimensione: media. Forza: routing con NavigationStack, Grid, ViewThatFits, un secondo nuovo manager, localizzazione, accessibilità.

Obiettivo

Dalla view di dettaglio di un Pokémon, navigare a una schermata che mostra contro cosa è forte e debole, costruita da /type/{name}.

Un Pokémon ha uno o due tipi — PokemonDetailRequest già scarica il payload di dettaglio, che li contiene. Per due tipi l'efficacia si moltiplica (doppio da terra × metà da terra = neutro). Quella logica di combinazione è logica di dominio e appartiene al manager, non alla view, ed è esattamente il genere di cosa che dovrebbe avere test unitari con fixture costruite a mano.

Passi

  1. TypeRequest, TypeResponse (le sei chiavi di damage_relations), TypeManager.
  2. Logica di combinazione per i doppi tipi, come funzione pura. Testala in isolamento — nessuna rete, nessuna view.
  3. Una schermata SwiftUI che usa Grid/GridRow per la tabella di efficacia.
  4. Raggiungila con navigationDestination — è qui che il lavoro di routing del Modulo 4 rende. Se hai tenuto lo sheet, ora hai un motivo concreto per non farlo.
  5. ViewThatFits così la tabella degrada a lista alle dimensioni di testo accessibili.
  6. Localizza ogni etichetta in en + it, entrambi i catalog.

Criteri di accettazione

  1. Electric mostra debolezza a terra, resiste a volante/acciaio/elettro, nessun danno a terra. I valori verificati sono nella sezione endpoint qui sopra.
  2. Un Pokémon a doppio tipo calcola l'efficacia moltiplicata, coperto da test unitari inclusi un caso ×4 e uno ×0.
  3. Leggibile alla massima dimensione di testo accessibile — controlla su dispositivo/simulatore, non nel canvas.
  4. VoiceOver annuncia ogni cella in modo sensato. "Due" non è sensato; "Terra, danno doppio" sì.
  5. Nessun inglese hardcoded. Entrambi gli .xcstrings aggiornati.
  6. Tutti i test esistenti passano; il nuovo manager ha test unitari con fixture.

Sfida C — Filtri di ricerca e statistiche sulla cronologia

Dimensione: media. Forza: Regex, Swift Charts, Layout, query SwiftData.

Obiettivo

Far accettare al campo di ricerca una sintassi di filtro semplice, e aggiungere una piccola view di statistiche sulla cronologia di ricerca.

Sintassi dei filtri, parsata con Regex (Modulo 2):

type:electric          → filtra la cronologia per tipo
before:2026-01-01      → filtra per searchDate
pika                   → match su sottostringa semplice
type:electric pika     → combinati

Passi

  1. Un parser basato su Regex che produce un valore tipizzato SearchFilter. Ricorda che Regex non è Sendable — il Modulo 2 §3 lo copre, e l'SDK non ha @MainActor.
  2. Applica i filtri alla cronologia. Oggi è first(where:) in memoria (SearchViewModel.swift:143) con un FetchDescriptor costruito a mano (:256). #Predicate è materia del Batch 2 — per ora fallo onestamente in memoria e scrivi cosa cambieresti una volta che avrai #Predicate.
  3. Una view di statistiche: ricerche per giorno da searchDate, come grafico BarMark.
  4. Accessibilità: i grafici hanno bisogno di etichette esplicite. Un grafico senza etichette in quest'app è una regressione rispetto al commit 9f787fc.

Criteri di accettazione

  1. Test unitari del parser, parametrizzati, che coprono: ogni filtro da solo, combinati, input malformato, input vuoto. L'input malformato deve degradare a ricerca testuale semplice, mai lanciare nella UI.
  2. Valori di filtro non validi non causano crash e non restituiscono silenziosamente tutto.
  3. Il grafico ha un'etichetta di accessibilità e valori per mark.
  4. Localizzato, entrambi i catalog.
  5. Tutti i test esistenti passano.

Come scegliere

  • Ne fai una? La Sfida A. È quella che ricostruisce l'architettura vera dell'SDK.
  • Ne fai due? A poi B. B consuma il lavoro di navigazione di A.
  • Tutte e tre? A → B → C. C è la più leggera sull'architettura dell'SDK e la più pesante sulla UI.

Non iniziare B o C prima del Modulo 4, e non iniziare A prima del Modulo 3 se intendi fare l'esercizio del clock iniettabile — A è molto più interessante con un clock testabile.

Cosa guarderò durante la revisione

Quando mi dirai che il batch è finito, è questo che verrà letto. Enunciato in anticipo così nulla è una sorpresa:

  • APIClient resta l'unico transport?
  • Ogni nuovo percorso d'errore termina in Pokespeare.Error, con l'ordinamento della mappatura intatto?
  • C'è qualcosa di public che non serviva lo fosse?
  • C'è un Optional che fa le veci di un errore?
  • Qualche test asserisce dentro un catch?
  • I test di integrazione sono protetti?
  • La nuova UI è usabile al massimo Dynamic Type, e VoiceOver dice qualcosa di utile?
