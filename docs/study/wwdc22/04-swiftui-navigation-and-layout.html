WWDC22 · Module 4 — SwiftUI Navigation and Layout

iOS 16 · NavigationStack, NavigationSplitView, navigationDestination, NavigationPath, the Layout protocol, Grid, ViewThatFits, presentation detents, ShareLink/Transferable

Every snippet here was typechecked against the iOS 26.4 SDK in Swift 6 language mode.

1. What shipped, and what problem it solves

Navigation. NavigationView was declarative in appearance and imperative in reality. Pushing a screen meant flipping a Binding<Bool> attached to a NavigationLink that had to already exist in the hierarchy. Consequences everyone hit: you could not push two screens at once, you could not restore a deep link into a nested stack, you could not pop to root without threading booleans through every level, and the whole thing behaved differently on iPad.

iOS 16 replaced it with a data-driven model. The stack is a value — an array — and navigating means mutating that array. Deep linking becomes assignment. Pop-to-root becomes removeAll(). State restoration becomes Codable.

Layout. Before iOS 16, custom layout meant GeometryReader and arithmetic, which fought the layout system rather than joining it. The Layout protocol lets your type participate in SwiftUI's actual negotiation.

2. How it actually works

The layout negotiation — read this first

Every SwiftUI layout is a three-step conversation, and understanding it explains more bugs than any other single fact about SwiftUI:

  1. The parent proposes a size to the child (ProposedViewSize — width and height, each of which may be nil meaning "unspecified", 0 meaning "smallest you can", or .infinity meaning "largest you can").
  2. The child replies with the size it actually wants (sizeThatFits).
  3. The parent places the child, and must respect the child's reply.

The child chooses. The parent proposes, it does not impose. This is why .frame(width:) does not "set the width" — it inserts a view that proposes that width to its child and then reports the child's answer upward.

The Layout protocol exposes exactly these two steps:

struct Equal: Layout {
  func sizeThatFits(proposal: ProposedViewSize, subviews: Subviews, cache: inout ()) -> CGSize {
    proposal.replacingUnspecifiedDimensions()
  }

  func placeSubviews(in bounds: CGRect, proposal: ProposedViewSize, subviews: Subviews, cache: inout ()) {
    let w = bounds.width / CGFloat(max(subviews.count, 1))
    for (i, sv) in subviews.enumerated() {
      sv.place(
        at: CGPoint(x: bounds.minX + CGFloat(i) * w, y: bounds.minY),
        proposal: .init(width: w, height: bounds.height)
      )
    }
  }
}

Subviews is a collection of proxies. You can ask each for sizeThatFits(_:) before deciding, and read per-subview LayoutValueKey data. The cache parameter exists so you can memoize expensive measurement across the multiple passes SwiftUI may run.

AnyLayout lets you swap layout algorithms without changing view identity — which means the transition animates instead of snapping:

AnyLayout(wide ? AnyLayout(HStackLayout()) : AnyLayout(VStackLayout())) {
  Text("a"); Text("b")
}

Compare with the naive if wide { HStack { … } } else { VStack { … } }, which produces two structurally different view trees, destroys and rebuilds the children, and loses their state.

ViewThatFits — the accessibility workhorse

ViewThatFits(in: .horizontal) {
  HStack { Text("a"); Text("b") }     // tried first
  VStack { Text("a"); Text("b") }     // fallback
}

It measures each child in order and uses the first that fits the proposal. The last child is used unconditionally if none fit, so put your most-compressed version last.

This is the single most useful iOS 16 API for Dynamic Type. At accessibility text sizes, a horizontal arrangement that works at default size becomes unreadable — ViewThatFits handles it declaratively instead of with a @Environment(\.dynamicTypeSize) branch.

Grid — the two-dimensional one

Grid/GridRow differs from LazyVGrid in a way that matters: Grid aligns cells across both axes (column widths are consistent down the whole grid), and it is eager — it measures everything. LazyVGrid is lazy and does not align across rows. Use Grid for forms and small tabular layouts; use LazyVGrid for scrolling collections of unknown length.

Navigation: the data-driven model

Homogeneous stack — a typed array. Use this when every destination is the same type. It is the simplest and most testable form:

enum Route: Hashable { case detail(String), settings }

struct Typed: View {
  @State private var path: [Route] = []

  var body: some View {
    NavigationStack(path: $path) {
      Button("go") { path.append(.detail("pikachu")) }
        .navigationDestination(for: Route.self) { r in Text(String(describing: r)) }
    }
  }
}

path is an ordinary array. path.append pushes. path.removeLast() pops. path.removeAll() pops to root. path = [.settings, .detail("pikachu")] deep-links two levels in one assignment. Because it is just a value, you can unit-test navigation logic without a view at all.

Heterogeneous stack — NavigationPath. A type-erased path when destinations are of different types:

@State private var path = NavigationPath()
// path.append(Route.settings); path.append(42)
// with a .navigationDestination(for:) for each type

NavigationPath is Codable when its elements are, which is what makes state restoration tractable. It costs you type safety and random access — you cannot inspect element 2 — so prefer the typed array unless you genuinely need mixed types.

navigationDestination(item:) (iOS 17) is the optional-driven form, and it is the direct analogue of .sheet(item:):

@State private var selected: String?

NavigationStack {
  Button("go") { selected = "pikachu" }
    .navigationDestination(item: $selected) { name in Text(name) }
}

This matters for this project specifically — see section 4.

The placement rule that bites everyone

navigationDestination(for:) must be inside the NavigationStack, attached to a view that is currently in the hierarchy. Put it on a view inside a lazy container that has not been created yet, and the destination is not registered, and the push silently does nothing.

Corollary: do not attach it inside a List row's ForEach body. Attach it to the List itself, or to the stack's root content.

4. Where it lands in this codebase

The stack is present and completely unused. SearchView.swift:14:

NavigationStack {
  content
}

There is not a single navigationDestination, NavigationLink, or NavigationPath in the project. The stack wraps content to get a navigation title (:54) and nothing else.

All navigation is modal. The detail screen is .sheet(item: $viewModel.pokemonDetail) at :17-26. Both alerts are boolean-driven at :27 and :36.

Is that wrong? Not necessarily — a sheet is a legitimate choice for a detail view. But it has consequences that are worth being able to name:

  • No back navigation, no hierarchy. The sheet is a leaf. There is nowhere to go from it.
  • Not deep-linkable. There is no path to restore. A URL scheme or an App Intent (Batch 1, Module 5) opening straight to a Pokémon has nothing to assign to.
  • No state restoration. Kill the app with a sheet open and it comes back to root.
  • Awkward on iPad and Mac, where a split view is the platform-native shape for search-plus-detail.

The detail state is already the right shape. SearchViewModel.swift:70:

var pokemonDetail: Pokemon?

An optional driving a sheet. That is exactly the shape navigationDestination(item:) wants. The migration is genuinely small — which is what makes it a good first exercise.

The empty state is a Spacer(). SearchView.swift:126. Held for Batch 2 (ContentUnavailableView), but notice it now.

ViewThatFits has an obvious home. PokemonView.swift:16-28 stacks sprite, name and description vertically always. SearchView.swift:137-155 lays out each history row horizontally always — sprite, then name — which at accessibility text sizes squeezes the name into a narrow column. The accessibility commit (9f787fc) already fixed the sheet for large text by making it scrollable with [.medium, .large] detents; the rows were not addressed.

5. Exercise

Goal: convert the detail presentation to real navigation, and make the history rows survive accessibility text sizes.

5a — Decide, then justify

Before writing anything, choose between three options and write a paragraph defending your choice:

  1. Keep the sheet. Defensible — but then write down what you are giving up and why it does not matter here.
  2. navigationDestination(item:) with the existing pokemonDetail optional. Smallest diff, gets you hierarchy and deep-linking.
  3. A typed [Route] path. Most capable, biggest change, sets up Batch 1 Module 5 (App Intents) properly.

This is the real skill. The API knowledge is the easy part.

5b — Implement it

If you chose 2 or 3: migrate the detail presentation. Constraints:

  • SearchViewModel is @MainActor @Observable and must stay UIKit-free — audit finding C-16 was UIKit leaking into this view model, do not undo it.
  • Navigation state belongs in the view model, not the view, so it stays testable. The 18 app tests exercise the view model directly.
  • Keep the sheet's accessibility work: the scrollable content and the large-text behaviour from commit 9f787fc must not regress.

5c — Test navigation as data

This is the payoff. Add tests to Demo/PokeAppTests/SearchViewModelTests.swift asserting navigation without a view:

  • Tapping a history item sets the destination.
  • Dismissing clears it.
  • A search that fails does not set a destination (guard against the C-25 class of bug, where an error path silently looked like success).
  • If you chose option 3: assigning a two-element path deep-links correctly.

5d — ViewThatFits for the rows

Wrap the history row layout so it falls back to a vertical arrangement when horizontal does not fit.

Acceptance criteria.

  1. All 18 app tests pass, plus at least 3 new navigation tests.
  2. All 53 SDK tests still pass.
  3. Manually verify at accessibility text size: Settings → Accessibility → Display & Text Size → Larger Text, at maximum. History rows must remain readable and the name must not truncate to two characters.
  4. VoiceOver still reads each row as one element with the Pokémon's name (SearchView.swift:149,162).
  5. swiftlint lint --strict clean.

5e — Optional: a custom Layout

Write one Layout conformance, even a throwaway, purely to feel sizeThatFits/placeSubviews. Print the incoming ProposedViewSize and observe how many times and with what values SwiftUI calls you. It will be more times, and with stranger values (nil, 0, .infinity), than you expect. That observation is the point of the exercise.

6. Pitfalls

  • navigationDestination must be inside the stack and in the live hierarchy. Registered from inside a lazy container that has not materialized, it silently does nothing.
  • One navigationDestination(for:) per type per stack. Two for the same type is undefined behaviour, not an error.
  • Path elements must be Hashable, and for restoration Codable. A SwiftData @Model class is a reference type — pushing the object rather than its identifier will bite you. Push the name or the PersistentIdentifier.
  • if/else around a whole view changes its type, hence its identity, hence resets its state. Use AnyLayout for layout switches and conditional modifiers rather than conditional views wherever possible.
  • ViewThatFits measures children eagerly. Do not put expensive views in the branches you expect not to be used.
  • Grid is eager, LazyVGrid is lazy. A Grid with a thousand rows measures a thousand rows.
  • NavigationPath gives up random access. If you need to inspect or mutate the middle of the stack, use a typed array.

  3. Why does AnyLayout animate a layout switch when an if/else between HStack and VStack does not?
  4. When does ViewThatFits use its last child regardless of fit, and what does that imply about ordering?
  5. Grid vs LazyVGrid — name two concrete differences and a case for each.
  6. Give three things a .sheet(item:) cannot do that a navigationDestination can.

WWDC22 · Modulo 4 — Navigazione e layout in SwiftUI

iOS 16 · NavigationStack, NavigationSplitView, navigationDestination, NavigationPath, il protocol Layout, Grid, ViewThatFits, presentation detent, ShareLink/Transferable

Ogni frammento qui è stato verificato col typechecker contro l'SDK iOS 26.4 in Swift 6 language mode.

1. Cosa è uscito, e quale problema risolve

Navigazione. NavigationView era dichiarativo nell'aspetto e imperativo nella sostanza. Fare push di una schermata significava ribaltare un Binding<Bool> attaccato a un NavigationLink che doveva già esistere nella gerarchia. Conseguenze incontrate da tutti: non potevi fare push di due schermate insieme, non potevi ripristinare un deep link dentro uno stack annidato, non potevi tornare alla radice senza infilare booleani a ogni livello, e su iPad il tutto si comportava diversamente.

iOS 16 l'ha sostituito con un modello guidato dai dati. Lo stack è un valore — un array — e navigare significa mutare quell'array. Il deep linking diventa un'assegnazione. Il pop-to-root diventa removeAll(). Il ripristino dello stato diventa Codable.

Layout. Prima di iOS 16 il layout personalizzato significava GeometryReader e aritmetica, il che combatteva il sistema di layout invece di parteciparvi. Il protocol Layout permette al tuo tipo di partecipare alla vera negoziazione di SwiftUI.

2. Come funziona davvero

La negoziazione del layout — leggi prima questo

Ogni layout SwiftUI è una conversazione in tre passi, e capirlo spiega più bug di qualsiasi altro singolo fatto su SwiftUI:

  1. Il parent propone una dimensione al child (ProposedViewSize — larghezza e altezza, ciascuna delle quali può essere nil cioè "non specificata", 0 cioè "la più piccola che puoi", o .infinity cioè "la più grande che puoi").
  2. Il child risponde con la dimensione che vuole davvero (sizeThatFits).
  3. Il parent colloca il child, e deve rispettare la risposta del child.

Sceglie il child. Il parent propone, non impone. È il motivo per cui .frame(width:) non "imposta la larghezza" — inserisce una view che propone quella larghezza al proprio child e poi riporta verso l'alto la risposta del child.

Il protocol Layout espone esattamente questi due passi:

struct Equal: Layout {
  func sizeThatFits(proposal: ProposedViewSize, subviews: Subviews, cache: inout ()) -> CGSize {
    proposal.replacingUnspecifiedDimensions()
  }

  func placeSubviews(in bounds: CGRect, proposal: ProposedViewSize, subviews: Subviews, cache: inout ()) {
    let w = bounds.width / CGFloat(max(subviews.count, 1))
    for (i, sv) in subviews.enumerated() {
      sv.place(
        at: CGPoint(x: bounds.minX + CGFloat(i) * w, y: bounds.minY),
        proposal: .init(width: w, height: bounds.height)
      )
    }
  }
}

Subviews è una collection di proxy. Puoi chiedere a ciascuno sizeThatFits(_:) prima di decidere, e leggere dati LayoutValueKey per subview. Il parametro cache esiste per memoizzare misurazioni costose attraverso i molteplici passaggi che SwiftUI può eseguire.

AnyLayout ti permette di scambiare algoritmi di layout senza cambiare l'identità della view — il che significa che la transizione si anima invece di scattare:

AnyLayout(wide ? AnyLayout(HStackLayout()) : AnyLayout(VStackLayout())) {
  Text("a"); Text("b")
}

Confronta con l'ingenuo if wide { HStack { … } } else { VStack { … } }, che produce due alberi di view strutturalmente diversi, distrugge e ricostruisce i figli, e ne perde lo stato.

ViewThatFits — il cavallo da tiro dell'accessibilità

ViewThatFits(in: .horizontal) {
  HStack { Text("a"); Text("b") }     // provata per prima
  VStack { Text("a"); Text("b") }     // ripiego
}

Misura ogni figlio in ordine e usa il primo che sta nella proposta. L'ultimo figlio viene usato incondizionatamente se nessuno ci sta, quindi metti in fondo la versione più compressa.

È l'API iOS 16 più utile per il Dynamic Type. Alle dimensioni di testo accessibili una disposizione orizzontale che funziona alla dimensione di default diventa illeggibile — ViewThatFits lo gestisce dichiarativamente invece che con un ramo su @Environment(\.dynamicTypeSize).

Grid — quello bidimensionale

Grid/GridRow differisce da LazyVGrid in un modo che conta: Grid allinea le celle su entrambi gli assi (le larghezze delle colonne sono coerenti lungo tutta la griglia), ed è eager — misura tutto. LazyVGrid è lazy e non allinea tra righe. Usa Grid per form e piccoli layout tabellari; usa LazyVGrid per collection scrollabili di lunghezza ignota.

Navigazione: il modello guidato dai dati

Stack omogeneo — un array tipizzato. Usalo quando ogni destinazione è dello stesso tipo. È la forma più semplice e testabile:

enum Route: Hashable { case detail(String), settings }

struct Typed: View {
  @State private var path: [Route] = []

  var body: some View {
    NavigationStack(path: $path) {
      Button("go") { path.append(.detail("pikachu")) }
        .navigationDestination(for: Route.self) { r in Text(String(describing: r)) }
    }
  }
}

path è un array ordinario. path.append fa push. path.removeLast() fa pop. path.removeAll() torna alla radice. path = [.settings, .detail("pikachu")] fa deep link di due livelli in un'assegnazione. Poiché è solo un valore, puoi testare la logica di navigazione senza alcuna view.

Stack eterogeneo — NavigationPath. Un path con tipo cancellato quando le destinazioni sono di tipi diversi:

@State private var path = NavigationPath()
// path.append(Route.settings); path.append(42)
// con un .navigationDestination(for:) per ciascun tipo

NavigationPath è Codable quando lo sono i suoi elementi, ed è ciò che rende trattabile il ripristino dello stato. Ti costa type safety e accesso casuale — non puoi ispezionare l'elemento 2 — quindi preferisci l'array tipizzato a meno che tu non abbia davvero bisogno di tipi misti.

navigationDestination(item:) (iOS 17) è la forma guidata da un opzionale, ed è l'analogo diretto di .sheet(item:):

@State private var selected: String?

NavigationStack {
  Button("go") { selected = "pikachu" }
    .navigationDestination(item: $selected) { name in Text(name) }
}

Questo conta specificamente per questo progetto — vedi la sezione 4.

La regola di collocazione che frega tutti

navigationDestination(for:) deve stare dentro il NavigationStack, attaccato a una view attualmente nella gerarchia. Mettilo su una view dentro un container lazy non ancora creato, e la destinazione non viene registrata, e il push non fa silenziosamente nulla.

Corollario: non attaccarlo dentro il body di un ForEach in una riga di List. Attaccalo alla List stessa, o al contenuto radice dello stack.

4. Dove atterra in questo codebase

Lo stack c'è ed è completamente inutilizzato. SearchView.swift:14:

NavigationStack {
  content
}

Non c'è un solo navigationDestination, NavigationLink o NavigationPath nel progetto. Lo stack avvolge content per ottenere un titolo di navigazione (:54) e nient'altro.

Tutta la navigazione è modale. La schermata di dettaglio è .sheet(item: $viewModel.pokemonDetail) a :17-26. Entrambi gli alert sono guidati da booleani a :27 e :36.

È sbagliato? Non necessariamente — uno sheet è una scelta legittima per una view di dettaglio. Ma ha conseguenze che vale la pena saper nominare:

  • Niente navigazione indietro, niente gerarchia. Lo sheet è una foglia. Da lì non si va da nessuna parte.
  • Non deep-linkabile. Non c'è un path da ripristinare. Uno schema URL o un App Intent (Batch 1, Modulo 5) che apre direttamente su un Pokémon non ha nulla a cui assegnare.
  • Nessun ripristino dello stato. Chiudi l'app con uno sheet aperto e torna alla radice.
  • Scomodo su iPad e Mac, dove una split view è la forma nativa della piattaforma per ricerca-più-dettaglio.

Lo stato del dettaglio ha già la forma giusta. SearchViewModel.swift:70:

var pokemonDetail: Pokemon?

Un opzionale che guida uno sheet. È esattamente la forma che vuole navigationDestination(item:). La migrazione è genuinamente piccola — ed è ciò che ne fa un buon primo esercizio.

Lo stato vuoto è uno Spacer(). SearchView.swift:126. Rimandato al Batch 2 (ContentUnavailableView), ma notalo adesso.

ViewThatFits ha una casa ovvia. PokemonView.swift:16-28 impila sprite, nome e descrizione verticalmente sempre. SearchView.swift:137-155 dispone ogni riga della cronologia orizzontalmente sempre — sprite, poi nome — il che alle dimensioni di testo accessibili schiaccia il nome in una colonna stretta. Il commit sull'accessibilità (9f787fc) ha già sistemato lo sheet per il testo grande rendendolo scrollabile con detent [.medium, .large]; le righe non sono state toccate.

5. Esercizio

Obiettivo: convertire la presentazione del dettaglio in navigazione vera, e far sopravvivere le righe della cronologia alle dimensioni di testo accessibili.

5a — Decidi, poi giustifica

Prima di scrivere qualsiasi cosa, scegli tra tre opzioni e scrivi un paragrafo a difesa della tua scelta:

  1. Tieni lo sheet. Difendibile — ma allora scrivi a cosa rinunci e perché qui non conta.
  2. navigationDestination(item:) con l'opzionale pokemonDetail esistente. Diff minimo, ti dà gerarchia e deep linking.
  3. Un path tipizzato [Route]. Il più capace, la modifica più grande, prepara come si deve il Modulo 5 del Batch 1 (App Intents).

È questa la vera abilità. La conoscenza dell'API è la parte facile.

5b — Implementalo

Se hai scelto 2 o 3: migra la presentazione del dettaglio. Vincoli:

  • SearchViewModel è @MainActor @Observable e deve restare libero da UIKit — il finding C-16 era UIKit che filtrava in questo view model, non annullarlo.
  • Lo stato di navigazione appartiene al view model, non alla view, così resta testabile. I 18 test app esercitano direttamente il view model.
  • Mantieni il lavoro di accessibilità dello sheet: il contenuto scrollabile e il comportamento con testo grande dal commit 9f787fc non devono regredire.

5c — Testa la navigazione come dato

È qui che si raccoglie. Aggiungi test a Demo/PokeAppTests/SearchViewModelTests.swift che asseriscono la navigazione senza una view:

  • Toccare un elemento della cronologia imposta la destinazione.
  • Il dismiss la azzera.
  • Una ricerca che fallisce non imposta una destinazione (guardia contro la classe di bug C-25, dove un percorso d'errore sembrava silenziosamente un successo).
  • Se hai scelto l'opzione 3: assegnare un path di due elementi fa deep link correttamente.

5d — ViewThatFits per le righe

Avvolgi il layout della riga della cronologia così che ripieghi su una disposizione verticale quando quella orizzontale non ci sta.

5e — Facoltativo: un Layout personalizzato

Scrivi una conformance Layout, anche usa e getta, solo per sentire sizeThatFits/placeSubviews. Stampa il ProposedViewSize in ingresso e osserva quante volte e con quali valori SwiftUI ti chiama. Saranno più volte, e con valori più strani (nil, 0, .infinity), di quanto ti aspetti. Quell'osservazione è il senso dell'esercizio.

6. Trappole

  • navigationDestination deve stare dentro lo stack e nella gerarchia viva. Registrato dentro un container lazy non ancora materializzato, non fa silenziosamente nulla.
  • Un navigationDestination(for:) per tipo per stack. Due per lo stesso tipo è comportamento indefinito, non un errore.
  • Gli elementi del path devono essere Hashable, e per il ripristino Codable. Una classe @Model di SwiftData è un reference type — fare push dell'oggetto invece del suo identificativo ti morderà. Fai push del nome o del PersistentIdentifier.
  • Un if/else attorno a un'intera view ne cambia il tipo, quindi l'identità, quindi ne azzera lo stato. Usa AnyLayout per gli scambi di layout e modifier condizionali invece di view condizionali dove possibile.
  • ViewThatFits misura i figli in modo eager. Non mettere view costose nei rami che ti aspetti non vengano usati.
  • Grid è eager, LazyVGrid è lazy. Un Grid con mille righe misura mille righe.
  • NavigationPath rinuncia all'accesso casuale. Se devi ispezionare o mutare il centro dello stack, usa un array tipizzato.
