WWDC22 · Module 1 — Generics and Existentials

Swift 5.7 · SE-0335, SE-0309, SE-0341, SE-0346, SE-0352, SE-0353, SE-0358

1. What shipped, and what problem it solves

Before Swift 5.7, generics and protocols had a usability cliff. Two symptoms everyone hit:

"Protocol can only be used as a generic constraint." The moment a protocol had an associated type, you could not write it as a type. any Collection was illegal. Your options were a type eraser you hand-wrote, or restructuring the whole call site around generics.

some and any looked identical but weren't. Both spelled as a bare protocol name — func f(_ x: Shape) — even though one is a compile-time-resolved concrete type and the other is a runtime box. Beginners could not tell them apart because the syntax gave them nothing to tell apart.

Swift 5.7 fixed both, plus the ergonomics around them. The through-line: make the distinction between "one specific type, chosen by the caller" and "any type, decided at runtime" visible in the source, then remove the artificial restrictions on the second one.

2. How it actually works

This is the section that matters. If you only remember one thing from this module, make it the layout diagram.

some — opaque types, resolved at compile time

func makeShape() -> some Shape { Circle() }

some Shape means: there is exactly one concrete type here, the compiler knows it, the caller does not. The caller learns "this conforms to Shape" and nothing more.

Because the type is known at compile time, the compiler can specialize: it emits a version of the function with Circle baked in. Method calls are direct, the value is stored inline, no boxing, no indirection. The cost of some at runtime is zero — it is an information-hiding tool, not a performance tool.

The rule that trips people: a function returning some Shape must return the same concrete type on every path. This does not compile:

func makeShape(circular: Bool) -> some Shape {
  circular ? Circle() : Square()   // ❌ two different concrete types
}

any — existentials, resolved at runtime

let shapes: [any Shape] = [Circle(), Square()]

any Shape means: some type conforming to Shape, possibly different for each value, decided at runtime. The heterogeneous array above is only possible with any.

This costs something, and the cost is precisely specified in Swift's ABI documentation. From the official type layout document:

If there is no class constraint on a protocol or protocol composition type, the existential container has to accommodate a value of arbitrary size and alignment. It does this using a fixed-size buffer, which is three pointers in size and pointer-aligned.

The layout, quoted from that same document:

struct OpaqueExistentialContainer {
  void *fixedSizeBuffer[3];              // 24 bytes on 64-bit
  Metadata *type;                         // what type is actually in there
  WitnessTable *witnessTables[NUM_WITNESS_TABLES];  // how to call its methods
};

Read that carefully, because three consequences fall straight out of it:

  1. Values ≤ 3 words fit inline. A struct Point { var x, y: Double } is 2 words — it lives directly in the buffer. Free.
  2. Values > 3 words get heap-allocated. A struct with four Doubles does not fit, so the existential stores a pointer to a side allocation. Putting one in an array means one heap allocation per element. This is the hidden cost of [any Shape].
  3. Method calls go through a witness table. Not a direct call, not even a vtable — a table of function pointers looked up by protocol conformance. Not free, and not inlinable across the boundary.

There is a cheaper case, also from the ABI doc: if a protocol is class-constrained (protocol P: AnyObject), the compiler uses a ClassExistentialContainer — a single pointer, since class instances are already one pointer and already carry their own metadata. No fixed-size buffer, no side allocation.

The rule of thumb: reach for some by default. Reach for any when you genuinely need heterogeneity or runtime-varying types — and know that you are paying for it.

Why any became mandatory

SE-0335 made the keyword required (in Swift 6 language mode; a warning before that). The motivation is exactly the confusion above: the expensive thing looked identical to the free thing. Now the expensive thing is spelled longer, which is a deliberate design signal.

This project already follows the rule — APIClient.swift:14 writes private let session: any Session, and :12 writes @Sendable (Int) -> (any Swift.Error)?.

Primary associated types — SE-0346

The problem: any Collection tells you nothing about the element type. Before 5.7 you had no way to say "a collection of Int" without full generics.

A protocol now nominates some of its associated types as primary:

protocol Collection<Element>: Sequence {   // Element is primary
  associatedtype Element
}

and callers constrain them positionally:

func sum(_ xs: some Collection<Int>) -> Int { xs.reduce(0, +) }
func sumAny(_ xs: any Collection<Int>) -> Int { xs.reduce(0, +) }

SE-0358 retrofitted these across the standard library — Sequence<Element>, Collection<Element>, AsyncSequence<Element, Failure>, and so on. This is why you can write some Collection<Int> today without declaring anything.

Opaque parameters — SE-0341

some in parameter position is pure sugar, but it is sugar you will use constantly:

func f(_ xs: some Collection<Int>) -> Int { xs.count }

// is exactly equivalent to:
func f<C: Collection<Int>>(_ xs: C) -> Int { xs.count }

Same code, same performance, no angle brackets. Use the generic form only when you need to name the type parameter — for example to constrain two parameters to the same type, which the some form cannot express.

Implicitly opened existentials — SE-0352

This is the quiet one that makes the whole thing hang together. Given a value of existential type, the compiler can now "open" it to call a generic function:

protocol Shape { func area() -> Double }

func areaOf<S: Shape>(_ s: S) -> Double { s.area() }

func use(_ s: any Shape) -> Double {
  areaOf(s)   // ✅ Swift 5.7+: compiler opens the box and binds S to the dynamic type
}

Before 5.7 this was an error, and the workaround was a protocol extension method that existed purely to bounce the call. The compiler now inserts the open automatically at the call site.

The limit: the opened type only exists for the duration of that call. You cannot return it, because there is no way to name it in the return type.

Unlocking existentials for all protocols — SE-0309

Finally: any now works for protocols with associated types and Self requirements. Where a member's type would depend on the erased type, that member is unavailable through the existential — the compiler tells you which. Everything else is usable.

4. Where it lands in this codebase

The SDK made an interesting architectural choice that is worth examining through this lens.

Pokespeare is a struct of closures, not a protocol. Pokespeare.swift:3-5:

public struct Pokespeare: Sendable {
  private var _description: @Sendable (_ name: String) async throws -> String
  private var _sprite: @Sendable (_ name: String) async throws -> URL
}

The README explains the motivation: substitution in tests with no protocol to declare and no mock class to maintain. Ask yourself what the alternative would have cost. protocol PokespeareProtocol + any PokespeareProtocol stored in the view model means an existential box and witness-table dispatch on every call — plus a protocol declaration, plus a mock class per test target. The closure struct has neither. This is a good decision, and now you can articulate why in ABI terms.

Where existentials are used, they are used correctly. APIClient.swift:14 — private let session: any Session — is a legitimate any: the concrete type genuinely varies (real URLSession in production, MockedSession in tests), and it is stored, not just passed. Session is not class-constrained (Session.swift:3 — protocol Session: Sendable), so this is an opaque existential container. URLSession is a class, so the buffer holds a single pointer and fits inline.

Where the sugar is missing. APIClient.swift:32:

func perform<R: HTTPCodableRequest>(_ request: R) async throws -> R.ResponseType

This one must stay generic — the return type R.ResponseType names the type parameter, which some cannot do. Good instinct to check, wrong candidate. Look instead for functions that take a generic parameter and never name it again.

A gap worth noticing. HTTPCodableRequest has an associated ResponseType but declares no primary associated type. If it did — protocol HTTPCodableRequest<ResponseType> — you could write any HTTPCodableRequest<PokemonDetailResponse>, which would make certain test helpers expressible.

5. Exercise

Goal: feel the difference between some and any in this codebase, and add a primary associated type where it earns its place.

5a — Measure the existential

In a scratch file (not in the project), write two versions of a small function: one taking some Session, one taking any Session. Read the generated SIL for each and find the difference:

xcrun swiftc -emit-sil -O yourfile.swift | swift demangle | less

Look for open_existential_addr / witness_method in the any version, and their absence in the some version. Write down what you saw — this is the kind of thing that only sticks once you have seen it in the IR.

5b — Add a primary associated type

Give HTTPCodableRequest a primary associated type for its response:

protocol HTTPCodableRequest<ResponseType>: HTTPRequest { … }

Acceptance criteria.

  1. Everything still compiles and all 53 SDK tests pass.
  2. In Pokespeare/Tests/, write one new test that uses the constrained existential form — any HTTPCodableRequest<PokemonDetailResponse> — to hold a request whose concrete type is not statically known. If you cannot find a natural use, that is a valid finding: write it down as "primary associated type not justified here" and revert. Knowing when not to use a feature is the harder half.
  3. swiftlint lint --strict clean.
xcodebuild test -scheme Pokespeare -destination 'platform=iOS Simulator,name=iPhone 17 Pro'

5c — Apply opaque parameters

Find at least one function in the SDK whose generic parameter is declared and then never named again, and convert it to the some form. Confirm the tests still pass. If there are none, say so — the codebase is small and may genuinely not have one.

6. Pitfalls

  • any in a hot loop. [any Shape] where Shape values exceed 3 words means one heap allocation per element. Profile before assuming, but know the mechanism.
  • some in return position needs a single concrete type. Branching on a runtime condition to return different types requires any, or an enum, or @ViewBuilder if it is SwiftUI (which is neither — it builds a TupleView/_ConditionalContent with the branch encoded in the type).
  • Opened existentials cannot escape. You can pass an opened value into a generic function; you cannot return it or store it.
  • some in parameter position cannot express relationships. Two some Collection parameters are two independent types. If you need them to match, use explicit generics.
  • SwiftUI's some View is the same feature. body: some View is an opaque type, which is why the enormous nested generic type of a view hierarchy never has to be spelled. Understanding this explains why if/else in a view body changes the type, and therefore the identity, and therefore resets state.

7. Self-check

Answer from memory before re-reading.

  1. How many bytes is the fixed-size buffer in an opaque existential container on a 64-bit platform, and what happens to a value that does not fit?
  2. Why does a class-constrained protocol produce a cheaper existential than an unconstrained one?
  3. func f(_ x: some P) and func f<T: P>(_ x: T) — are these different at runtime? Is there anything the second can express that the first cannot?
  4. Why can a function returning some Shape not return Circle() on one branch and Square() on another, when a function returning any Shape can?
  5. What did SE-0352 change, and what problem did it remove the need to work around?
  6. Pokespeare is a struct of closures rather than a protocol. Give the ABI-level argument for why that is cheaper than storing any PokespeareProtocol.
  7. In body: some View, what concrete type is actually being hidden, and why does SwiftUI need it hidden?

WWDC22 · Modulo 1 — Generics ed existential

Swift 5.7 · SE-0335, SE-0309, SE-0341, SE-0346, SE-0352, SE-0353, SE-0358

1. Cosa è uscito, e quale problema risolve

Prima di Swift 5.7 generics e protocol avevano uno scalino di usabilità. Due sintomi che tutti hanno incontrato:

"Protocol can only be used as a generic constraint." Nel momento in cui un protocol aveva un associated type, non potevi scriverlo come tipo. any Collection era illegale. Le opzioni erano un type eraser scritto a mano, oppure ristrutturare l'intero call site attorno ai generics.

some e any sembravano identici ma non lo erano. Entrambi scritti come nome nudo del protocol — func f(_ x: Shape) — anche se uno è un tipo concreto risolto a compile-time e l'altro è una scatola a runtime. I principianti non potevano distinguerli perché la sintassi non dava nulla da distinguere.

Swift 5.7 ha sistemato entrambi, più l'ergonomia attorno. Il filo conduttore: rendere visibile nel sorgente la distinzione tra "un tipo specifico, scelto dal chiamante" e "un tipo qualsiasi, deciso a runtime", e poi rimuovere le restrizioni artificiali sul secondo.

2. Come funziona davvero

È la sezione che conta. Se di questo modulo ricordi una cosa sola, che sia lo schema del layout.

some — tipi opachi, risolti a compile-time

func makeShape() -> some Shape { Circle() }

some Shape significa: qui c'è esattamente un tipo concreto, il compilatore lo conosce, il chiamante no. Il chiamante impara "questo è conforme a Shape" e nient'altro.

Poiché il tipo è noto a compile-time, il compilatore può specializzare: emette una versione della funzione con Circle incorporato. Le chiamate a metodo sono dirette, il valore è memorizzato inline, niente boxing, niente indirezione. Il costo di some a runtime è zero — è uno strumento di occultamento dell'informazione, non di performance.

La regola che frega: una funzione che restituisce some Shape deve restituire lo stesso tipo concreto su ogni percorso. Questo non compila:

func makeShape(circular: Bool) -> some Shape {
  circular ? Circle() : Square()   // ❌ due tipi concreti diversi
}

any — existential, risolti a runtime

let shapes: [any Shape] = [Circle(), Square()]

any Shape significa: un tipo qualsiasi conforme a Shape, potenzialmente diverso per ogni valore, deciso a runtime. L'array eterogeneo qui sopra è possibile solo con any.

Questo costa qualcosa, e il costo è specificato con precisione nella documentazione ABI di Swift. Dal documento ufficiale sul layout dei tipi:

If there is no class constraint on a protocol or protocol composition type, the existential container has to accommodate a value of arbitrary size and alignment. It does this using a fixed-size buffer, which is three pointers in size and pointer-aligned.

Il layout, citato dallo stesso documento:

struct OpaqueExistentialContainer {
  void *fixedSizeBuffer[3];              // 24 byte su 64 bit
  Metadata *type;                         // che tipo c'è davvero dentro
  WitnessTable *witnessTables[NUM_WITNESS_TABLES];  // come chiamarne i metodi
};

Leggilo con attenzione, perché ne discendono direttamente tre conseguenze:

  1. I valori ≤ 3 word stanno inline. Una struct Point { var x, y: Double } è 2 word — vive direttamente nel buffer. Gratis.
  2. I valori > 3 word finiscono sull'heap. Una struct con quattro Double non ci sta, quindi l'existential memorizza un puntatore a una side allocation. Metterne uno in un array significa un'allocazione heap per elemento. È il costo nascosto di [any Shape].
  3. Le chiamate a metodo passano da una witness table. Non una chiamata diretta, nemmeno una vtable — una tabella di puntatori a funzione cercata per conformance. Non è gratis, e non è inlinabile attraverso il confine.

C'è un caso più economico, sempre dal documento ABI: se un protocol è vincolato a classi (protocol P: AnyObject), il compilatore usa un ClassExistentialContainer — un singolo puntatore, dato che le istanze di classe sono già un puntatore e portano già i propri metadata. Niente buffer a dimensione fissa, niente side allocation.

La regola pratica: usa some di default. Usa any quando ti serve davvero eterogeneità o tipi che variano a runtime — e sappi che lo stai pagando.

Perché any è diventato obbligatorio

SE-0335 ha reso la parola chiave obbligatoria (in Swift 6 language mode; un warning prima). La motivazione è esattamente la confusione qui sopra: la cosa costosa sembrava identica a quella gratuita. Ora la cosa costosa si scrive più lunga, che è un segnale di design deliberato.

Questo progetto segue già la regola — APIClient.swift:14 scrive private let session: any Session, e :12 scrive @Sendable (Int) -> (any Swift.Error)?.

Primary associated type — SE-0346

Il problema: any Collection non ti dice nulla sul tipo degli elementi. Prima di 5.7 non avevi modo di dire "una collection di Int" senza generics completi.

Un protocol ora nomina alcuni dei suoi associated type come primari:

protocol Collection<Element>: Sequence {   // Element è primario
  associatedtype Element
}

e i chiamanti li vincolano posizionalmente:

func sum(_ xs: some Collection<Int>) -> Int { xs.reduce(0, +) }
func sumAny(_ xs: any Collection<Int>) -> Int { xs.reduce(0, +) }

SE-0358 li ha applicati retroattivamente a tutta la standard library — Sequence<Element>, Collection<Element>, AsyncSequence<Element, Failure> e così via. È il motivo per cui oggi puoi scrivere some Collection<Int> senza dichiarare nulla.

Opaque parameter — SE-0341

some in posizione di parametro è puro zucchero sintattico, ma è zucchero che userai di continuo:

func f(_ xs: some Collection<Int>) -> Int { xs.count }

// è esattamente equivalente a:
func f<C: Collection<Int>>(_ xs: C) -> Int { xs.count }

Stesso codice, stessa performance, niente parentesi angolari. Usa la forma generica solo quando devi nominare il parametro di tipo — per esempio per vincolare due parametri allo stesso tipo, cosa che la forma some non può esprimere.

Existential aperti implicitamente — SE-0352

È quello silenzioso che tiene insieme tutto il resto. Dato un valore di tipo existential, il compilatore può ora "aprirlo" per chiamare una funzione generica:

protocol Shape { func area() -> Double }

func areaOf<S: Shape>(_ s: S) -> Double { s.area() }

func use(_ s: any Shape) -> Double {
  areaOf(s)   // ✅ Swift 5.7+: il compilatore apre la scatola e lega S al tipo dinamico
}

Prima di 5.7 era un errore, e il workaround era un metodo in protocol extension che esisteva solo per rimbalzare la chiamata. Ora il compilatore inserisce l'apertura automaticamente al call site.

Il limite: il tipo aperto esiste solo per la durata di quella chiamata. Non puoi restituirlo, perché non c'è modo di nominarlo nel tipo di ritorno.

Existential per tutti i protocol — SE-0309

Infine: any ora funziona per protocol con associated type e requisiti su Self. Dove il tipo di un membro dipenderebbe dal tipo cancellato, quel membro non è disponibile attraverso l'existential — il compilatore ti dice quale. Tutto il resto è utilizzabile.

4. Dove atterra in questo codebase

L'SDK ha fatto una scelta architetturale interessante che vale la pena esaminare con questa lente.

Pokespeare è una struct di closure, non un protocol. Pokespeare.swift:3-5:

public struct Pokespeare: Sendable {
  private var _description: @Sendable (_ name: String) async throws -> String
  private var _sprite: @Sendable (_ name: String) async throws -> URL
}

Il README spiega la motivazione: sostituzione nei test senza protocol da dichiarare e senza mock class da mantenere. Chiediti quanto sarebbe costata l'alternativa. protocol PokespeareProtocol + any PokespeareProtocol tenuto nel view model significa una scatola existential e dispatch via witness table a ogni chiamata — più una dichiarazione di protocol, più una mock class per test target. La struct di closure non ha né l'una né l'altra. È una buona decisione, e ora sai articolarne il perché in termini di ABI.

Dove si usano existential, si usano correttamente. APIClient.swift:14 — private let session: any Session — è un any legittimo: il tipo concreto varia davvero (URLSession reale in produzione, MockedSession nei test), ed è memorizzato, non solo passato. Session non è vincolato a classi (Session.swift:3 — protocol Session: Sendable), quindi è un opaque existential container. URLSession è una classe, quindi il buffer contiene un singolo puntatore e sta inline.

Dove manca lo zucchero. APIClient.swift:32:

func perform<R: HTTPCodableRequest>(_ request: R) async throws -> R.ResponseType

Questa deve restare generica — il tipo di ritorno R.ResponseType nomina il parametro di tipo, cosa che some non può fare. Buon istinto controllarla, candidato sbagliato. Cerca invece funzioni che prendono un parametro generico e non lo nominano mai più.

Un buco da notare. HTTPCodableRequest ha un ResponseType associato ma non dichiara alcun primary associated type. Se lo facesse — protocol HTTPCodableRequest<ResponseType> — potresti scrivere any HTTPCodableRequest<PokemonDetailResponse>, il che renderebbe esprimibili certi helper di test.

5. Esercizio

Obiettivo: sentire la differenza tra some e any in questo codebase, e aggiungere un primary associated type dove se lo guadagna.

5a — Misura l'existential

In un file di scarto (non nel progetto), scrivi due versioni di una piccola funzione: una che prende some Session, una che prende any Session. Leggi il SIL generato per entrambe e trova la differenza:

xcrun swiftc -emit-sil -O tuofile.swift | swift demangle | less

Cerca open_existential_addr / witness_method nella versione any, e la loro assenza nella versione some. Scrivi cosa hai visto — è il tipo di cosa che si fissa solo dopo averla vista nell'IR.

5b — Aggiungi un primary associated type

Dai a HTTPCodableRequest un primary associated type per la sua risposta:

protocol HTTPCodableRequest<ResponseType>: HTTPRequest { … }

Criteri di accettazione.

  1. Tutto compila ancora e i 53 test SDK passano.
  2. In Pokespeare/Tests/, scrivi un nuovo test che usa la forma existential vincolata — any HTTPCodableRequest<PokemonDetailResponse> — per contenere una request il cui tipo concreto non è noto staticamente. Se non trovi un uso naturale, è un risultato valido: scrivilo come "primary associated type non giustificato qui" e fai marcia indietro. Sapere quando non usare una feature è la metà più difficile.
  3. swiftlint lint --strict pulito.
xcodebuild test -scheme Pokespeare -destination 'platform=iOS Simulator,name=iPhone 17 Pro'

5c — Applica gli opaque parameter

Trova almeno una funzione nell'SDK il cui parametro generico è dichiarato e poi mai più nominato, e convertila alla forma some. Verifica che i test passino ancora. Se non ce ne sono, dillo — il codebase è piccolo e potrebbe genuinamente non averne.

6. Trappole

  • any in un loop caldo. [any Shape] dove i valori Shape superano 3 word significa un'allocazione heap per elemento. Profila prima di dare per scontato, ma conosci il meccanismo.
  • some in posizione di ritorno vuole un unico tipo concreto. Ramificare su una condizione a runtime per restituire tipi diversi richiede any, o un enum, o @ViewBuilder se è SwiftUI (che non è né l'uno né l'altro — costruisce un TupleView/_ConditionalContent con il ramo codificato nel tipo).
  • Gli existential aperti non possono uscire. Puoi passare un valore aperto a una funzione generica; non puoi restituirlo o memorizzarlo.
  • some in posizione di parametro non può esprimere relazioni. Due parametri some Collection sono due tipi indipendenti. Se devono coincidere, usa generics espliciti.
  • Il some View di SwiftUI è la stessa feature. body: some View è un tipo opaco, ed è il motivo per cui l'enorme tipo generico annidato di una gerarchia di view non va mai scritto. Capirlo spiega perché un if/else nel body di una view cambia il tipo, quindi l'identità, quindi azzera lo stato.

7. Autovalutazione

Rispondi a memoria prima di rileggere.

  1. Quanti byte è il buffer a dimensione fissa in un opaque existential container su piattaforma a 64 bit, e cosa succede a un valore che non ci sta?
  2. Perché un protocol vincolato a classi produce un existential più economico di uno non vincolato?
  3. func f(_ x: some P) e func f<T: P>(_ x: T) — sono diversi a runtime? C'è qualcosa che il secondo può esprimere e il primo no?
  4. Perché una funzione che restituisce some Shape non può restituire Circle() su un ramo e Square() su un altro, mentre una che restituisce any Shape sì?
  5. Cosa ha cambiato SE-0352, e quale workaround ha reso non più necessario?
  6. Pokespeare è una struct di closure invece che un protocol. Dai l'argomentazione a livello di ABI sul perché sia più economico che memorizzare any PokespeareProtocol.
  7. In body: some View, quale tipo concreto viene effettivamente nascosto, e perché SwiftUI ha bisogno di nasconderlo?
