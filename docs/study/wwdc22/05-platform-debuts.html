WWDC22 · Module 5 — Platform Debuts: App Intents, Swift Charts, Lock Screen Widgets, Transferable

iOS 16 · Four frameworks that all debuted at WWDC22 and are all absent from this project. This module is broader and shallower than the previous four by design — each of these earns a deeper pass in a later batch, where they were substantially extended.

Every snippet here was typechecked against the iOS 26.4 SDK in Swift 6 language mode.

1. App Intents

What it is, and why it replaced what came before

App Intents is how your app exposes actions to the rest of the system: Shortcuts, Siri, Spotlight, the Action button, widgets, and (from iOS 18) Apple Intelligence.

It replaced SiriKit Intents, and the difference is not cosmetic. SiriKit required a .intentdefinition file, a code generator, and a separate app extension target. App Intents is pure Swift in your app target — a protocol conformance, and that is the whole integration.

import AppIntents

struct ShowPokemonIntent: AppIntent {
  static let title: LocalizedStringResource = "Show Pokémon"
  static let openAppWhenRun = true

  @Parameter(title: "Name")
  var name: String

  func perform() async throws -> some IntentResult & ProvidesDialog {
    .result(dialog: "Showing \(name)")
  }
}

Three things to notice:

  • title is a LocalizedStringResource, not a String. This is the type that Batch 2 covers properly — it defers localization to display time rather than resolving at construction. The system needs that, because it may display your intent's name in Shortcuts under a locale your app is not currently running in. This project's habit of pre-resolving String(localized:) at init (SearchViewModel.swift:40-56) would be actively wrong here.
  • perform() is async throws and returns a result type composed from protocols — ProvidesDialog, ReturnsValue, ShowsSnippetView, and so on, mixed as needed.
  • @Parameter makes the property appear as an editable field in the Shortcuts editor, with a type-appropriate control, for free.

AppShortcutsProvider publishes intents that should be available with no user setup at all:

struct Shortcuts: AppShortcutsProvider {
  static var appShortcuts: [AppShortcut] {
    AppShortcut(
      intent: ShowPokemonIntent(),
      phrases: ["Show \(.applicationName)"],
      shortTitle: "Show",
      systemImageName: "sparkles"
    )
  }
}

Phrases must interpolate \(.applicationName) — the system requires your app's name in the phrase so users cannot collide with other apps' commands.

Why this project should care

App Intents is the natural consumer of the navigation work from Module 4. "Hey Siri, show Pikachu in PokéSpeare" needs somewhere to navigate to — which means it needs a path to assign, which the sheet-based presentation does not have. Do Module 4 first.

Later batches: interactive widgets driven by intents (WWDC23), Control Widgets and Apple Intelligence integration (WWDC24), Spotlight integration (WWDC25).

2. Swift Charts

A declarative charting framework built on the same layout and result-builder machinery as SwiftUI.

Chart(data) { p in
  BarMark(x: .value("Day", p.day), y: .value("Count", p.count))
    .foregroundStyle(by: .value("Day", p.day))
}
.chartXAxis { AxisMarks() }

The mental model is grammar of graphics: you do not configure a chart object, you describe marks and the data dimensions they encode. BarMark, LineMark, PointMark, AreaMark, RuleMark, RectangleMark, SectorMark (iOS 17). .value("Label", keyPath) is a plottable value — the string is the axis label and the legend entry, so it is user-visible and must be localized.

.foregroundStyle(by:), .symbol(by:), and .lineStyle(by:) create a series split and a legend automatically.

Accessibility is not free. Charts generate an audio-graph representation, but only if your data is Identifiable and you supply .accessibilityLabel/.accessibilityValue on the marks. Given the accessibility work already done in this project (commit 9f787fc), do not regress the standard by adding an unlabelled chart.

Later batches: SectorMark and scrolling charts (WWDC23), function plotting (WWDC24), 3D charts (WWDC25).

3. Lock Screen Widgets

WidgetKit shipped at WWDC20; WWDC22 added the accessory families for the Lock Screen and, later, the Watch complications and Dynamic Island surfaces:

StaticConfiguration(kind: "w", provider: P()) { _ in Text("x") }
  .supportedFamilies([.accessoryCircular, .accessoryRectangular, .accessoryInline, .systemSmall])

The accessory families render in a constrained, desaturated widget rendering mode — you get shape and hierarchy, not colour. Design for that: .widgetAccentable() marks the parts that should take the accent tint.

The TimelineProvider model is the part worth understanding, because it is unlike normal app code. You do not update a widget; you hand the system a timeline of pre-rendered future entries plus a TimelinePolicy for when to ask you again (.atEnd, .after(date), .never). The system decides when to actually refresh, subject to a budget. You cannot force a refresh on a schedule you choose — WidgetCenter.shared.reloadTimelines(ofKind:) is a request, not a command.

Later batches: interactive widgets via App Intents (WWDC23), Control Widgets and the iOS 18 rendering changes (WWDC24).

4. Transferable and ShareLink

Transferable is a protocol describing how a type converts to and from data for sharing, drag-and-drop, and the pasteboard — replacing the NSItemProvider/UTI dance.

struct Card: Transferable {
  let name: String
  static var transferRepresentation: some TransferRepresentation {
    ProxyRepresentation(exporting: \.name)
  }
}

ShareLink(item: Card(name: "Pikachu"), preview: SharePreview("Pikachu"))

Representations, in rough order of preference: CodableRepresentation (JSON, for your own app's types), DataRepresentation (raw bytes with a UTType), FileRepresentation (a file URL), ProxyRepresentation (delegate to another Transferable type — the simplest case, above).

You can declare several; the receiver picks the best one it understands. ShareLink then gets you the system share sheet with a single view.

6. Where it lands in this codebase

None of these four exist in the project. But the data to drive them already does.

Demo/PokeApp/Models/Pokemon.swift stores name, shakespeareanDescription, spriteUrl, and searchDate. That is enough for:

  • App Intent — "show Pokémon X", which needs the navigation from Module 4.
  • Lock Screen widget — the most recently searched Pokémon. The history is already ordered by searchDate (SearchViewModel.swift:256).
  • ShareLink — share a Pokémon's name plus description from the detail view. Genuinely one line once Pokemon is Transferable.
  • Chart — searches per day from searchDate. Honestly, this is thin: a hobby app's search history is not interesting data. Do the chart to learn the API, not because the app needs it.

The one real obstacle. A widget extension is a separate process with a separate bundle. It cannot read the app's SwiftData store as configured today, because PokeApp.swift:28 puts the store in URL.applicationSupportDirectory — inside the app's own container. Sharing requires an App Group and moving the store into the group container.

That is a genuine architectural change, and it is the interesting part of the exercise. It also touches the store-recovery path at PokeApp.swift:27-47, which currently deletes and rebuilds on failure — with two processes opening the same store, "delete and rebuild" is a considerably more dangerous move than it was with one.

7. Exercise

Pick one of A or B. Both are real features; neither is busywork. Do not do all four frameworks — breadth here is for orientation, and depth comes later.

Option A — ShareLink (small, ~30 minutes)

Make Pokemon conform to Transferable and add a ShareLink to the detail view.

Acceptance criteria. 1. Sharing to Messages produces readable text with the name and description. 2. Pokemon is a SwiftData @Model class — reason explicitly about whether to make the model itself Transferable or to introduce a small Sendable value type for sharing. Write down your reasoning. (Consider: @Model classes are not Sendable, and Transferable values cross process boundaries.) 3. All 71 tests still pass; swiftlint lint --strict clean.

Option B — App Intent + Lock Screen widget (substantial, several hours)

Expose "show Pokémon X" as an App Intent, and add a widget showing the most recent search.

Do Module 4 first. Without a navigation path, the intent has nowhere to send the app.

Steps. 1. Add an App Group capability shared by the app and a new widget extension target. 2. Move the SwiftData store into the group container. Revisit the recovery logic at PokeApp.swift:27-47 — with two processes, reason about what happens if the widget is reading while the app deletes. 3. Write ShowPokemonIntent, using LocalizedStringResource for title (not String(localized:)). 4. Add an AppShortcutsProvider so it works in Siri with no user setup. 5. Add a widget supporting .accessoryRectangular and .systemSmall.

Acceptance criteria. 1. The intent appears in the Shortcuts app and navigates the running app to the right Pokémon. 2. The widget shows the most recent search and updates after a new one. 3. The widget is legible in the desaturated accessory rendering mode — check on the Lock Screen, not just in the widget gallery. 4. VoiceOver reads the widget meaningfully. 5. All 71 existing tests still pass. The intent's logic is covered by at least one new test. 6. swiftlint lint --strict clean, and CI green — note that adding a target changes the build, so watch the first CI run.

xcodebuild test -project Demo/PokeApp.xcodeproj -scheme PokeApp -destination 'platform=iOS Simulator,name=iPhone 17 Pro'
xcodebuild test -scheme Pokespeare -destination 'platform=iOS Simulator,name=iPhone 17 Pro'

8. Pitfalls

  • LocalizedStringResource, not String, for anything the system displays outside your app. Pre-resolved strings freeze the locale at construction; Shortcuts may display your intent under a different one.
  • Widgets are a separate process. No shared memory, no shared container without an App Group, and a strict memory limit — do not decode a large image in a timeline entry.
  • You do not control widget refresh. The timeline policy is a hint against a system budget.
  • Accessory families are desaturated. Colour-carried meaning disappears. Use .widgetAccentable() and rely on shape and hierarchy.
  • App Intents parameters must be resolvable without your UI. perform() may run with the app not in the foreground, or not running at all.
  • .value("Label", …) strings in Swift Charts are user-visible. They are axis labels and legend entries — localize them.
  • A chart without accessibility labels is worse than no chart in an app that already got VoiceOver right.
  • Adding an App Group changes provisioning. Expect a signing detour, and expect CI to need attention.

9. Self-check

  1. What did App Intents replace, and what is the concrete developer-experience difference?
  2. Why is AppIntent.title a LocalizedStringResource rather than a String? Give the failure mode of using a pre-resolved String.
  3. What must an AppShortcut phrase interpolate, and why does the system require it?
  4. Describe the TimelineProvider contract. Can you guarantee a widget updates every 5 minutes?
  5. What is "widget rendering mode" for accessory families, and what does it mean for a design that encodes meaning in colour?
  6. Name three TransferRepresentation kinds and when you would choose each.
  7. In Swift Charts, what does .foregroundStyle(by:) do beyond setting a colour?
  8. This app's SwiftData store lives in URL.applicationSupportDirectory. Precisely why does that block a widget from reading it, and what does the fix change about the store-recovery logic in PokeApp.swift?

WWDC22 · Modulo 5 — Debutti di piattaforma: App Intents, Swift Charts, widget da lock screen, Transferable

iOS 16 · Quattro framework che hanno debuttato tutti a WWDC22 e sono tutti assenti da questo progetto. Questo modulo è deliberatamente più largo e meno profondo dei quattro precedenti — ciascuno di questi si guadagna un passaggio più approfondito in un batch successivo, dove sono stati estesi in modo sostanziale.

Ogni frammento qui è stato verificato col typechecker contro l'SDK iOS 26.4 in Swift 6 language mode.

1. App Intents

Cos'è, e perché ha sostituito ciò che c'era prima

App Intents è il modo in cui la tua app espone azioni al resto del sistema: Comandi rapidi, Siri, Spotlight, il tasto Azione, i widget e (da iOS 18) Apple Intelligence.

Ha sostituito SiriKit Intents, e la differenza non è cosmetica. SiriKit richiedeva un file .intentdefinition, un generatore di codice e un target di app extension separato. App Intents è puro Swift nel target dell'app — una conformance a un protocol, e l'integrazione è tutta lì.

import AppIntents

struct ShowPokemonIntent: AppIntent {
  static let title: LocalizedStringResource = "Show Pokémon"
  static let openAppWhenRun = true

  @Parameter(title: "Name")
  var name: String

  func perform() async throws -> some IntentResult & ProvidesDialog {
    .result(dialog: "Showing \(name)")
  }
}

Tre cose da notare:

  • title è un LocalizedStringResource, non una String. È il tipo che il Batch 2 tratta come si deve — rimanda la localizzazione al momento della visualizzazione invece di risolverla alla costruzione. Il sistema ne ha bisogno, perché potrebbe mostrare il nome del tuo intent in Comandi rapidi sotto un locale in cui la tua app non sta girando. L'abitudine di questo progetto di pre-risolvere String(localized:) all'init (SearchViewModel.swift:40-56) sarebbe qui attivamente sbagliata.
  • perform() è async throws e restituisce un tipo di risultato composto da protocol — ProvidesDialog, ReturnsValue, ShowsSnippetView e così via, mescolati secondo necessità.
  • @Parameter fa comparire la proprietà come campo modificabile nell'editor di Comandi rapidi, con un controllo adatto al tipo, gratis.

AppShortcutsProvider pubblica gli intent che devono essere disponibili senza alcuna configurazione da parte dell'utente:

struct Shortcuts: AppShortcutsProvider {
  static var appShortcuts: [AppShortcut] {
    AppShortcut(
      intent: ShowPokemonIntent(),
      phrases: ["Show \(.applicationName)"],
      shortTitle: "Show",
      systemImageName: "sparkles"
    )
  }
}

Le frasi devono interpolare \(.applicationName) — il sistema richiede il nome della tua app nella frase così gli utenti non possono collidere con i comandi di altre app.

Perché a questo progetto dovrebbe interessare

App Intents è il consumatore naturale del lavoro di navigazione del Modulo 4. "Hey Siri, mostra Pikachu in PokéSpeare" ha bisogno di un posto dove navigare — cioè di un path da assegnare, che la presentazione basata su sheet non ha. Fai prima il Modulo 4.

Batch successivi: widget interattivi guidati da intent (WWDC23), Control Widget e integrazione con Apple Intelligence (WWDC24), integrazione Spotlight (WWDC25).

2. Swift Charts

Un framework di grafici dichiarativo costruito sulla stessa macchina di layout e result builder di SwiftUI.

Chart(data) { p in
  BarMark(x: .value("Day", p.day), y: .value("Count", p.count))
    .foregroundStyle(by: .value("Day", p.day))
}
.chartXAxis { AxisMarks() }

Il modello mentale è la grammatica dei grafici: non configuri un oggetto grafico, descrivi mark e le dimensioni dei dati che codificano. BarMark, LineMark, PointMark, AreaMark, RuleMark, RectangleMark, SectorMark (iOS 17). .value("Label", keyPath) è un valore plottabile — la stringa è l'etichetta dell'asse e la voce di legenda, quindi è visibile all'utente e va localizzata.

.foregroundStyle(by:), .symbol(by:) e .lineStyle(by:) creano una divisione in serie e una legenda automaticamente.

L'accessibilità non è gratis. I grafici generano una rappresentazione audio-graph, ma solo se i tuoi dati sono Identifiable e fornisci .accessibilityLabel/.accessibilityValue sui mark. Dato il lavoro di accessibilità già fatto in questo progetto (commit 9f787fc), non far regredire lo standard aggiungendo un grafico senza etichette.

Batch successivi: SectorMark e grafici scrollabili (WWDC23), plotting di funzioni (WWDC24), grafici 3D (WWDC25).

3. Widget da lock screen

WidgetKit è uscito a WWDC20; WWDC22 ha aggiunto le famiglie accessory per la schermata di blocco e, più tardi, le complicazioni di Watch e le superfici della Dynamic Island:

StaticConfiguration(kind: "w", provider: P()) { _ in Text("x") }
  .supportedFamilies([.accessoryCircular, .accessoryRectangular, .accessoryInline, .systemSmall])

Le famiglie accessory rendono in una modalità di rendering vincolata e desaturata — ottieni forma e gerarchia, non colore. Progetta per quello: .widgetAccentable() marca le parti che devono prendere la tinta d'accento.

Il modello TimelineProvider è la parte che vale la pena capire, perché non assomiglia al normale codice di app. Non aggiorni un widget; consegni al sistema una timeline di entry future pre-renderizzate più una TimelinePolicy per quando richiederti (.atEnd, .after(date), .never). Il sistema decide quando ricaricare davvero, soggetto a un budget. Non puoi forzare un refresh su una cadenza che scegli tu — WidgetCenter.shared.reloadTimelines(ofKind:) è una richiesta, non un comando.

Batch successivi: widget interattivi via App Intents (WWDC23), Control Widget e i cambiamenti di rendering di iOS 18 (WWDC24).

4. Transferable e ShareLink

Transferable è un protocol che descrive come un tipo si converte da e verso dati per condivisione, drag-and-drop e pasteboard — sostituendo il balletto NSItemProvider/UTI.

struct Card: Transferable {
  let name: String
  static var transferRepresentation: some TransferRepresentation {
    ProxyRepresentation(exporting: \.name)
  }
}

ShareLink(item: Card(name: "Pikachu"), preview: SharePreview("Pikachu"))

Rappresentazioni, in ordine indicativo di preferenza: CodableRepresentation (JSON, per i tipi della tua app), DataRepresentation (byte grezzi con un UTType), FileRepresentation (un URL di file), ProxyRepresentation (delega a un altro tipo Transferable — il caso più semplice, sopra).

Puoi dichiararne diverse; il destinatario sceglie la migliore che capisce. ShareLink poi ti dà il share sheet di sistema con una sola view.

6. Dove atterra in questo codebase

Nessuno di questi quattro esiste nel progetto. Ma i dati per alimentarli ci sono già.

Demo/PokeApp/Models/Pokemon.swift memorizza name, shakespeareanDescription, spriteUrl e searchDate. Basta per:

  • App Intent — "mostra il Pokémon X", che ha bisogno della navigazione del Modulo 4.
  • Widget da lock screen — il Pokémon cercato più di recente. La cronologia è già ordinata per searchDate (SearchViewModel.swift:256).
  • ShareLink — condividere nome e descrizione di un Pokémon dalla view di dettaglio. Genuinamente una riga, una volta che Pokemon è Transferable.
  • Grafico — ricerche per giorno da searchDate. Onestamente è debole: la cronologia di ricerca di un'app hobbistica non è un dato interessante. Fai il grafico per imparare l'API, non perché l'app ne abbia bisogno.

L'unico ostacolo reale. Un'estensione widget è un processo separato con un bundle separato. Non può leggere lo store SwiftData dell'app com'è configurato oggi, perché PokeApp.swift:28 mette lo store in URL.applicationSupportDirectory — dentro il container dell'app stessa. Condividerlo richiede un App Group e lo spostamento dello store nel container del gruppo.

È un cambiamento architetturale vero, ed è la parte interessante dell'esercizio. Tocca anche il percorso di recupero dello store a PokeApp.swift:27-47, che oggi cancella e ricostruisce in caso di fallimento — con due processi che aprono lo stesso store, "cancella e ricostruisci" è una mossa considerevolmente più pericolosa di quanto fosse con uno solo.

7. Esercizio

Scegli una tra A e B. Sono entrambe feature reali; nessuna delle due è lavoro fine a sé stesso. Non fare tutti e quattro i framework — qui la larghezza serve all'orientamento, la profondità arriva dopo.

Opzione A — ShareLink (piccola, ~30 minuti)

Fai conformare Pokemon a Transferable e aggiungi uno ShareLink alla view di dettaglio.

Criteri di accettazione. 1. Condividere su Messaggi produce testo leggibile con nome e descrizione. 2. Pokemon è una classe @Model di SwiftData — ragiona esplicitamente se rendere Transferable il modello stesso o introdurre un piccolo value type Sendable per la condivisione. Scrivi il tuo ragionamento. (Considera: le classi @Model non sono Sendable, e i valori Transferable attraversano confini di processo.) 3. Tutti i 71 test passano ancora; swiftlint lint --strict pulito.

Opzione B — App Intent + widget da lock screen (sostanziale, diverse ore)

Esponi "mostra il Pokémon X" come App Intent, e aggiungi un widget che mostra la ricerca più recente.

Fai prima il Modulo 4. Senza un path di navigazione l'intent non ha dove mandare l'app.

Passi. 1. Aggiungi una capability App Group condivisa tra l'app e un nuovo target di estensione widget. 2. Sposta lo store SwiftData nel container del gruppo. Rivedi la logica di recupero a PokeApp.swift:27-47 — con due processi, ragiona su cosa succede se il widget sta leggendo mentre l'app cancella. 3. Scrivi ShowPokemonIntent, usando LocalizedStringResource per title (non String(localized:)). 4. Aggiungi un AppShortcutsProvider così funziona in Siri senza configurazione da parte dell'utente. 5. Aggiungi un widget che supporta .accessoryRectangular e .systemSmall.

Criteri di accettazione. 1. L'intent compare nell'app Comandi rapidi e naviga l'app in esecuzione sul Pokémon giusto. 2. Il widget mostra la ricerca più recente e si aggiorna dopo una nuova. 3. Il widget è leggibile nella modalità di rendering accessory desaturata — controlla sulla schermata di blocco, non solo nella galleria widget. 4. VoiceOver legge il widget in modo sensato. 5. Tutti i 71 test esistenti passano ancora. La logica dell'intent è coperta da almeno un nuovo test. 6. swiftlint lint --strict pulito, e CI verde — nota che aggiungere un target cambia la build, quindi tieni d'occhio la prima CI.

xcodebuild test -project Demo/PokeApp.xcodeproj -scheme PokeApp -destination 'platform=iOS Simulator,name=iPhone 17 Pro'
xcodebuild test -scheme Pokespeare -destination 'platform=iOS Simulator,name=iPhone 17 Pro'

8. Trappole

  • LocalizedStringResource, non String, per tutto ciò che il sistema mostra fuori dalla tua app. Le stringhe pre-risolte congelano il locale alla costruzione; Comandi rapidi potrebbe mostrare il tuo intent sotto un altro.
  • I widget sono un processo separato. Nessuna memoria condivisa, nessun container condiviso senza un App Group, e un limite di memoria stretto — non decodificare un'immagine grande in una entry di timeline.
  • Non controlli il refresh del widget. La timeline policy è un suggerimento contro un budget di sistema.
  • Le famiglie accessory sono desaturate. Il significato veicolato dal colore sparisce. Usa .widgetAccentable() e affidati a forma e gerarchia.
  • I parametri di App Intents devono essere risolvibili senza la tua UI. perform() può girare con l'app non in primo piano, o non in esecuzione affatto.
  • Le stringhe .value("Label", …) in Swift Charts sono visibili all'utente. Sono etichette d'asse e voci di legenda — localizzale.
  • Un grafico senza etichette di accessibilità è peggio di nessun grafico in un'app che ha già fatto bene VoiceOver.
  • Aggiungere un App Group cambia il provisioning. Aspettati una deviazione sulla firma, e aspettati che la CI abbia bisogno di attenzione.

  3. Cosa deve interpolare una frase di AppShortcut, e perché il sistema lo richiede?
  4. Descrivi il contratto di TimelineProvider. Puoi garantire che un widget si aggiorni ogni 5 minuti?
  5. Cos'è la "widget rendering mode" per le famiglie accessory, e cosa comporta per un design che codifica significato nel colore?
  6. Nomina tre tipi di TransferRepresentation e quando sceglieresti ciascuno.
  7. In Swift Charts, cosa fa .foregroundStyle(by:) oltre a impostare un colore?
  8. Lo store SwiftData di quest'app vive in URL.applicationSupportDirectory. Perché esattamente questo impedisce a un widget di leggerlo, e cosa cambia il fix riguardo alla logica di recupero dello store in PokeApp.swift?
