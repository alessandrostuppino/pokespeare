WWDC22 · Module 3 — Concurrency Foundations: Sendable, Checking Levels, and Clock

Swift 5.6 / 5.7 · SE-0302, SE-0337, SE-0338, SE-0329

This module is the foundation Batch 3 (Swift 6 data-race safety) and Batch 4 (approachable concurrency) both build on. Read it properly even though the project already uses most of it — the why underneath is what makes those later batches make sense.

1. What shipped, and what problem it solves

Swift 5.5 (WWDC21) gave us async/await, Task, and actors. But it shipped with a hole: the compiler could not check that the values you passed between concurrency domains were safe to pass. You could hand a mutable class instance to a detached task and race against yourself, with no diagnostic.

WWDC22's contribution is the checking machinery:

  • Sendable (SE-0302) — a marker protocol meaning "safe to move across isolation boundaries."
  • Staged checking (SE-0337) — because turning full checking on at once would have broken every codebase in existence, so it arrived as a dial.
  • Defined execution semantics for nonisolated async functions (SE-0338) — which thread does an async function that belongs to no actor actually run on?

Plus, separately but landing in the same release: Clock, Instant, Duration (SE-0329) — a real time abstraction to replace UInt64 nanoseconds.

2. How it actually works

Sendable is a marker protocol

Sendable has no requirements — no methods, no properties. It is a marker: it exists only so the compiler can check it, and it is erased before code generation. There is no witness table, no runtime representation, no cost.

What the compiler checks:

Type Sendable?
struct/enum with all-Sendable stored properties ✅ inferred automatically (if not public — see below)
actor ✅ always — that is what an actor is for
final class with only immutable Sendable stored properties ✅ if you declare the conformance
non-final class ❌ — a subclass could add mutable state
class with var stored properties ❌ unless protected by isolation
@MainActor-isolated class ✅ — isolation is the protection
function types ✅ only when marked @Sendable

The public-type gotcha. Automatic inference for structs and enums stops at module boundaries: a public struct does not get an inferred Sendable conformance, because adding one later would be a source-compatible promise you had not made. You must declare it. This is why Pokespeare.swift:3 writes it explicitly:

public struct Pokespeare: Sendable { … }

@Sendable closures

A closure crossing an isolation boundary must be @Sendable, which imposes two rules: everything it captures must itself be Sendable, and it cannot capture anything mutably (no inout, no mutation of captured vars).

This project uses @Sendable closures as its primary architectural device — Pokespeare.swift:4-5:

private var _description: @Sendable (_ name: String) async throws -> String
private var _sprite: @Sendable (_ name: String) async throws -> URL

That is what makes struct Pokespeare: Sendable legal despite storing closures.

The escape hatch, and its price

@unchecked Sendable tells the compiler "trust me." It is a promise, not a proof — you have taken responsibility for the synchronization by hand.

This project uses it exactly twice, both in test code: MockedSession.swift:5 and the RequestBox at :104. That is the right density. Two @unchecked in test doubles is a considered decision; twenty across production code is a codebase that turned the compiler off.

When you write one, write a comment saying what provides the safety. "It's fine" is not a reason. "All mutation happens under lock, and lock is never held across a suspension" is.

The checking dial — SE-0337

Three levels, historically reached via -strict-concurrency=:

Level Behaviour
minimal Only checks what is explicitly marked. The Swift 5 default.
targeted Checks code that has already adopted concurrency (async functions, actors), leaves the rest alone.
complete Checks everything. This is what Swift 6 language mode enforces as errors rather than warnings.

The intended migration path is minimal → targeted → complete as warnings → flip to Swift 6 mode, where they become errors.

This project is already at the end of that path. Package.swift:1 declares swift-tools-version: 6.0 and the app sets SWIFT_VERSION = 6.0, so both compile under complete checking with errors. There is nothing to migrate — which is exactly why Batch 3 can spend its time on the interesting parts (region-based isolation, sending) instead of on migration mechanics.

One thing to notice: Package.swift has no swiftSettings at all. Swift 6 mode is inherited purely from the tools version. In Batch 3 you will make that explicit and add upcoming-feature flags.

SE-0338 — where does a nonisolated async function run?

This is the one people get wrong, and it is load-bearing for Batch 4.

@MainActor
func caller() async {
  await work()      // where does work() run?
}

nonisolated func work() async -> Int { 42 }

Under SE-0338 (the WWDC22 rule): work() does not inherit the caller's actor. It hops to the global concurrent executor — a cooperative thread pool. So calling it from @MainActor code means: leave the main actor, run on a pool thread, hop back.

The reasoning was sound — a nonisolated async function should not silently block a caller's actor. But the consequence was a great deal of unnecessary hopping, and a category of bug where developers assumed their code stayed on the main actor and it did not.

Swift 6.2 reverses this default via SE-0461: nonisolated async functions now run on the caller's actor, and the new @concurrent attribute is the explicit opt-in to the old behaviour. Batch 4 covers it in full.

Hold both models in your head. Code written between 2022 and 2025 assumes the first; code written now assumes the second; and which one applies depends on a language-mode flag.

Clock, Instant, Duration — SE-0329

Before this, you slept with Task.sleep(nanoseconds: 300_000_000) and counted zeros.

Duration is an amount of time, stored as 128 bits — seconds plus attoseconds — so it does not lose precision the way a Double of seconds does. All of these are verified to compile:

let base: Duration = .milliseconds(300)
base * 4                  // Duration × Int
base * 1.5                // Duration × Double
base + .seconds(1)
base / 2
base < .seconds(1)        // Comparable
base.components           // (seconds: Int64, attoseconds: Int64)

Clock is a protocol with two standard implementations, and the difference matters:

Clock Behaviour while the device is asleep
ContinuousClock Keeps counting. "Wall time elapsed."
SuspendingClock Pauses. "Time the process was actually running."

For a network retry backoff you want ContinuousClock — if the user's phone slept for 30 seconds, that time really did pass as far as the server is concerned. Task.sleep(for:) uses ContinuousClock by default.

Clock also gives you measure, which is the honest way to time async work:

let elapsed = try await ContinuousClock().measure {
  try await someWork()
}

Why Clock being a protocol matters: it is a seam. A custom Clock conformance lets a test drive time forward instantly instead of actually sleeping. Keep that in mind for the exercise.

4. Where it lands in this codebase

This is the area the project already does well, so read it as a worked example rather than a list of defects.

The Sendable surface. Pokespeare.swift:3 (public struct Pokespeare: Sendable), APIClient.swift:9, RetryPolicy.swift:4, PokemonManager.swift:3, TranslationManager.swift:3, and Session.swift:3 — protocol Session: Sendable, which is what lets any Session be stored in a Sendable struct at APIClient.swift:14.

@MainActor where it belongs. SearchViewModel.swift:5. The audit's finding C-02 is the story of what happens without it: the class was @Observable but not isolated, a detached Task mutated UI state and a non-Sendable ModelContext from a background thread, and it compiled — because the app target was still on SWIFT_VERSION = 5.0. The data race was real; the checking was off. That is the single most valuable thing this repository can teach you about Swift 6 mode, and it happened here.

Duration used properly. RetryPolicy.swift:9,42:

var baseDelay: Duration
func delay(forAttempt attempt: Int) -> Duration {
  baseDelay * (1 << attempt)          // 300ms, 600ms, 1200ms
}

and consumed at APIClient.swift:40:

try await Task.sleep(for: retryPolicy.delay(forAttempt: attempt))

Note the comment above that line — Task.sleep throws on cancellation, which is precisely the desired behaviour: a cancelled search must abandon its backoff rather than finish sleeping first. That is a subtle correctness property expressed for free by using the right API.

The gap: the clock is not injectable. RetryPolicy deals in Duration but APIClient calls Task.sleep directly. So the retry tests in RetryTests.swift either really sleep, or test the policy's arithmetic without testing the loop that uses it. HANDOFF.md lists "instrumenting the retry numbers" as unfinished work. This is the exercise.

5. Exercise

Goal: make time injectable, so the retry loop can be tested without real sleeping.

5a — Read before you write

Read APIClient.swift:32-45 and RetryPolicy.swift in full, then Pokespeare/Tests/PokespeareTests/RetryTests.swift. Answer for yourself, in writing:

  • Which of the 7 retry tests actually exercise the while true loop in perform, and which only test RetryPolicy's arithmetic in isolation?
  • How long does the SDK suite take today? Measure it. Some of that is real backoff sleeping.

5b — Inject the clock

Give APIClient a clock dependency, defaulting to ContinuousClock(), and route the backoff sleep through it instead of calling Task.sleep(for:) directly.

Design constraints to respect:

  • APIClient is Sendable (:9) and must stay that way — so whatever you inject must be Sendable too.
  • The SDK is not @MainActor anywhere. Keep it that way.
  • Do not break the cancellation property. A cancelled task must still abandon the wait. Verify this, do not assume it.
  • The public surface must not change. Pokespeare, Pokespeare.Error, PokemonView, PokemonViewModel are the whole public API (see README.md) and this is an internal refactor.

5c — Test with it

Write a test clock and use it to assert something the current tests cannot: that three attempts against a 500 response produce delays of exactly 300ms, then 600ms — without the test taking 900ms.

Acceptance criteria.

  1. A new test asserts the actual backoff sequence, not just the policy's arithmetic.
  2. The SDK suite gets measurably faster. Record both numbers.
  3. Cancellation still works: a test proves a cancelled request stops during backoff rather than completing it.
  4. All 53 SDK tests pass; the 18 app tests are untouched and pass.
  5. swiftlint lint --strict clean.
  6. The public API is byte-for-byte unchanged.
xcodebuild test -scheme Pokespeare -destination 'platform=iOS Simulator,name=iPhone 17 Pro'

Hint, not a solution. There are at least two designs: conform a test type to Clock, or inject a narrower @Sendable (Duration) async throws -> Void sleep closure. The second is smaller and matches the struct-of-closures idiom this SDK already uses everywhere. The first is more conventional and gives you measure for free. Pick one, then write down the argument against the one you rejected — that is the part that teaches.

6. Pitfalls

  • public structs do not infer Sendable. Cross-module inference is deliberately off. Declare it.
  • @unchecked Sendable is a promise you must be able to state. If you cannot name the mechanism providing safety, you do not have one.
  • A @MainActor class is Sendable; the isolation is the proof. This is why SearchViewModel needs no Sendable annotation.
  • Nonisolated async did not inherit the caller's actor before Swift 6.2. Every blog post, sample, and Stack Overflow answer from 2022–2025 assumes the old rule. Check the date on anything you read.
  • SuspendingClock for a network backoff is wrong. Device sleep does not pause the server's rate limiter.
  • Task.sleep throwing on cancellation is a feature. Swallowing that error with try? silently converts "abandon the retry" into "finish the wait, then continue."
  • Duration is not Double seconds. Do not round-trip through TimeInterval to do arithmetic — you will lose precision the type exists to preserve.

7. Self-check

  1. Sendable has no requirements. What does the compiler actually do with a conformance, and what is its runtime cost?
  2. Why does a public struct with all-Sendable properties not get an automatic conformance, when an internal one does?
  3. Name the three strict-concurrency levels and say which one Swift 6 language mode corresponds to.
  4. Under SE-0338, where does a nonisolated async function run when called from @MainActor code? What did Swift 6.2 change, and what is the new opt-in spelling for the old behaviour?
  5. ContinuousClock vs SuspendingClock — which for a network retry backoff, and what concrete scenario distinguishes them?
  6. In APIClient.perform, why is it important that Task.sleep throws rather than returns on cancellation?
  7. Audit finding C-02 was a real data race that compiled. What exactly made the compiler unable to see it, and what single build setting would have surfaced it?
  8. Pokespeare stores two @Sendable closures and is itself Sendable. What would break if the @Sendable on those closure types were removed?

WWDC22 · Modulo 3 — Fondamenta di concorrenza: Sendable, livelli di checking e Clock

Swift 5.6 / 5.7 · SE-0302, SE-0337, SE-0338, SE-0329

Questo modulo è la base su cui si costruiscono sia il Batch 3 (data-race safety di Swift 6) sia il Batch 4 (approachable concurrency). Leggilo bene anche se il progetto usa già quasi tutto — il perché sottostante è ciò che rende sensati quei batch successivi.

1. Cosa è uscito, e quale problema risolve

Swift 5.5 (WWDC21) ci ha dato async/await, Task e gli actor. Ma è uscito con un buco: il compilatore non poteva verificare che i valori passati tra domini di concorrenza fossero sicuri da passare. Potevi consegnare un'istanza di classe mutabile a un task distaccato e correre contro te stesso, senza alcuna diagnostica.

Il contributo di WWDC22 è la macchina di verifica:

  • Sendable (SE-0302) — un marker protocol che significa "sicuro da spostare attraverso confini di isolamento".
  • Verifica a stadi (SE-0337) — perché accendere la verifica completa tutta insieme avrebbe rotto ogni codebase esistente, quindi è arrivata come una manopola.
  • Semantica di esecuzione definita per le funzioni async nonisolated (SE-0338) — su quale thread gira davvero una funzione async che non appartiene a nessun actor?

In più, separatamente ma nella stessa release: Clock, Instant, Duration (SE-0329) — un'astrazione del tempo vera al posto di UInt64 di nanosecondi.

2. Come funziona davvero

Sendable è un marker protocol

Sendable non ha requisiti — nessun metodo, nessuna proprietà. È un marker: esiste solo perché il compilatore possa verificarlo, e viene cancellato prima della generazione del codice. Nessuna witness table, nessuna rappresentazione a runtime, nessun costo.

Cosa verifica il compilatore:

Tipo Sendable?
struct/enum con tutte le proprietà Sendable ✅ inferito automaticamente (se non è public — vedi sotto)
actor ✅ sempre — è a questo che serve un actor
final class con sole proprietà immutabili Sendable ✅ se dichiari la conformance
classe non final ❌ — una sottoclasse potrebbe aggiungere stato mutabile
classe con proprietà var ❌ salvo protezione tramite isolamento
classe isolata @MainActor ✅ — l'isolamento è la protezione
tipi funzione ✅ solo se marcati @Sendable

Il tranello dei tipi public. L'inferenza automatica per struct ed enum si ferma ai confini di modulo: una struct public non ottiene una conformance Sendable inferita, perché aggiungerla dopo sarebbe una promessa source-compatible che non avevi fatto. Devi dichiararla. Ecco perché Pokespeare.swift:3 la scrive esplicitamente:

public struct Pokespeare: Sendable { … }

Closure @Sendable

Una closure che attraversa un confine di isolamento deve essere @Sendable, il che impone due regole: tutto ciò che cattura deve essere a sua volta Sendable, e non può catturare nulla in modo mutabile (niente inout, nessuna mutazione di var catturate).

Questo progetto usa le closure @Sendable come suo dispositivo architetturale principale — Pokespeare.swift:4-5:

private var _description: @Sendable (_ name: String) async throws -> String
private var _sprite: @Sendable (_ name: String) async throws -> URL

È ciò che rende legale struct Pokespeare: Sendable pur memorizzando closure.

La via di fuga, e il suo prezzo

@unchecked Sendable dice al compilatore "fidati". È una promessa, non una prova — ti sei preso la responsabilità della sincronizzazione a mano.

Questo progetto ne usa esattamente due, entrambe nel codice di test: MockedSession.swift:5 e il RequestBox a :104. È la densità giusta. Due @unchecked nei test double sono una decisione ponderata; venti sparsi nel codice di produzione sono un codebase che ha spento il compilatore.

Quando ne scrivi uno, scrivi un commento che dica cosa fornisce la sicurezza. "Va bene" non è una motivazione. "Tutte le mutazioni avvengono sotto lock, e lock non viene mai tenuto attraverso una sospensione" sì.

La manopola della verifica — SE-0337

Tre livelli, storicamente raggiunti via -strict-concurrency=:

Livello Comportamento
minimal Verifica solo ciò che è marcato esplicitamente. Il default di Swift 5.
targeted Verifica il codice che ha già adottato la concorrenza (funzioni async, actor), lascia stare il resto.
complete Verifica tutto. È ciò che lo Swift 6 language mode impone come errori invece che warning.

Il percorso di migrazione previsto è minimal → targeted → complete come warning → passaggio a Swift 6 mode, dove diventano errori.

Questo progetto è già alla fine di quel percorso. Package.swift:1 dichiara swift-tools-version: 6.0 e l'app imposta SWIFT_VERSION = 6.0, quindi entrambi compilano sotto verifica completa con errori. Non c'è niente da migrare — ed è esattamente il motivo per cui il Batch 3 può spendere il suo tempo sulle parti interessanti (region-based isolation, sending) invece che sulla meccanica della migrazione.

Una cosa da notare: Package.swift non ha alcun swiftSettings. Swift 6 mode è ereditato puramente dalla tools version. Nel Batch 3 lo renderai esplicito e aggiungerai gli upcoming-feature flag.

SE-0338 — dove gira una funzione async nonisolated?

È quella che si sbaglia più spesso, ed è portante per il Batch 4.

@MainActor
func caller() async {
  await work()      // dove gira work()?
}

nonisolated func work() async -> Int { 42 }

Sotto SE-0338 (la regola WWDC22): work() non eredita l'actor del chiamante. Salta sull'executor concorrente globale — un pool cooperativo di thread. Quindi chiamarla da codice @MainActor significa: lasciare il main actor, girare su un thread del pool, tornare indietro.

Il ragionamento era sensato — una funzione async nonisolated non dovrebbe bloccare silenziosamente l'actor del chiamante. Ma la conseguenza è stata una gran quantità di salti inutili, e una categoria di bug in cui gli sviluppatori assumevano che il loro codice restasse sul main actor mentre non era così.

Swift 6.2 inverte questo default via SE-0461: le funzioni async nonisolated ora girano sull'actor del chiamante, e il nuovo attributo @concurrent è l'opt-in esplicito al vecchio comportamento. Il Batch 4 lo copre per intero.

Tieni entrambi i modelli in testa. Il codice scritto tra il 2022 e il 2025 assume il primo; il codice scritto oggi assume il secondo; e quale dei due valga dipende da un flag di language mode.

Clock, Instant, Duration — SE-0329

Prima di questo dormivi con Task.sleep(nanoseconds: 300_000_000) contando gli zeri.

Duration è una quantità di tempo, memorizzata su 128 bit — secondi più attosecondi — quindi non perde precisione come farebbe un Double di secondi. Tutte queste sono verificate come compilanti:

let base: Duration = .milliseconds(300)
base * 4                  // Duration × Int
base * 1.5                // Duration × Double
base + .seconds(1)
base / 2
base < .seconds(1)        // Comparable
base.components           // (seconds: Int64, attoseconds: Int64)

Clock è un protocol con due implementazioni standard, e la differenza conta:

Clock Comportamento mentre il dispositivo dorme
ContinuousClock Continua a contare. "Tempo di parete trascorso."
SuspendingClock Si ferma. "Tempo in cui il processo stava davvero girando."

Per un backoff di rete vuoi ContinuousClock — se il telefono dell'utente ha dormito 30 secondi, quel tempo è davvero passato per quanto riguarda il server. Task.sleep(for:) usa ContinuousClock di default.

Clock ti dà anche measure, che è il modo onesto di cronometrare lavoro asincrono:

let elapsed = try await ContinuousClock().measure {
  try await someWork()
}

Perché conta che Clock sia un protocol: è una giuntura. Una conformance Clock personalizzata permette a un test di far avanzare il tempo istantaneamente invece di dormire davvero. Tienilo a mente per l'esercizio.

4. Dove atterra in questo codebase

È l'area che il progetto già fa bene, quindi leggila come esempio svolto invece che come lista di difetti.

La superficie Sendable. Pokespeare.swift:3 (public struct Pokespeare: Sendable), APIClient.swift:9, RetryPolicy.swift:4, PokemonManager.swift:3, TranslationManager.swift:3 e Session.swift:3 — protocol Session: Sendable, che è ciò che permette a any Session di essere memorizzato in una struct Sendable a APIClient.swift:14.

@MainActor dove serve. SearchViewModel.swift:5. Il finding C-02 dell'audit è la storia di cosa succede senza: la classe era @Observable ma non isolata, un Task distaccato mutava stato di UI e un ModelContext non Sendable da un thread di background, e compilava — perché il target app era ancora su SWIFT_VERSION = 5.0. La data race era reale; la verifica era spenta. È la cosa più preziosa che questo repository può insegnarti su Swift 6 mode, ed è successa qui.

Duration usata bene. RetryPolicy.swift:9,42:

var baseDelay: Duration
func delay(forAttempt attempt: Int) -> Duration {
  baseDelay * (1 << attempt)          // 300ms, 600ms, 1200ms
}

e consumata a APIClient.swift:40:

try await Task.sleep(for: retryPolicy.delay(forAttempt: attempt))

Nota il commento sopra quella riga — Task.sleep lancia in caso di cancellazione, che è esattamente il comportamento desiderato: una ricerca cancellata deve abbandonare il suo backoff invece di finire di dormire prima. È una proprietà di correttezza sottile espressa gratis usando l'API giusta.

Il buco: il clock non è iniettabile. RetryPolicy ragiona in Duration ma APIClient chiama Task.sleep direttamente. Quindi i test di retry in RetryTests.swift o dormono davvero, o testano l'aritmetica della policy senza testare il ciclo che la usa. HANDOFF.md elenca "strumentare i numeri dei retry" come lavoro non fatto. È questo l'esercizio.

5. Esercizio

Obiettivo: rendere il tempo iniettabile, così il ciclo di retry può essere testato senza dormire davvero.

5a — Leggi prima di scrivere

Leggi APIClient.swift:32-45 e RetryPolicy.swift per intero, poi Pokespeare/Tests/PokespeareTests/RetryTests.swift. Rispondi a te stesso, per iscritto:

  • Quali dei 7 test di retry esercitano davvero il ciclo while true in perform, e quali testano solo l'aritmetica di RetryPolicy in isolamento?
  • Quanto ci mette oggi la suite SDK? Misuralo. Una parte è backoff reale che dorme.

5b — Inietta il clock

Dai ad APIClient una dipendenza da un clock, con default ContinuousClock(), e fai passare da lì la sleep del backoff invece di chiamare Task.sleep(for:) direttamente.

Vincoli di design da rispettare:

  • APIClient è Sendable (:9) e deve restarlo — quindi anche ciò che inietti deve essere Sendable.
  • L'SDK non è @MainActor da nessuna parte. Che resti così.
  • Non rompere la proprietà di cancellazione. Un task cancellato deve comunque abbandonare l'attesa. Verificalo, non darlo per scontato.
  • La superficie pubblica non deve cambiare. Pokespeare, Pokespeare.Error, PokemonView, PokemonViewModel sono tutta l'API pubblica (vedi README.md) e questo è un refactor interno.

5c — Testa con esso

Scrivi un clock di test e usalo per asserire qualcosa che i test attuali non possono: che tre tentativi contro una risposta 500 producono ritardi di esattamente 300ms, poi 600ms — senza che il test impieghi 900ms.

Criteri di accettazione.

  1. Un nuovo test asserisce la sequenza effettiva di backoff, non solo l'aritmetica della policy.
  2. La suite SDK diventa misurabilmente più veloce. Registra entrambi i numeri.
  3. La cancellazione funziona ancora: un test dimostra che una richiesta cancellata si ferma durante il backoff invece di completarlo.
  4. Tutti i 53 test SDK passano; i 18 test app sono intatti e passano.
  5. swiftlint lint --strict pulito.
  6. L'API pubblica è invariata byte per byte.
xcodebuild test -scheme Pokespeare -destination 'platform=iOS Simulator,name=iPhone 17 Pro'

Indizio, non soluzione. Ci sono almeno due design: far conformare un tipo di test a Clock, oppure iniettare una closure di sleep più stretta @Sendable (Duration) async throws -> Void. Il secondo è più piccolo e coerente con l'idioma struct-di-closure che questo SDK usa ovunque. Il primo è più convenzionale e ti dà measure gratis. Scegline uno, poi scrivi l'argomentazione contro quello che hai scartato — è quella la parte che insegna.

6. Trappole

  • Le struct public non inferiscono Sendable. L'inferenza cross-modulo è disattivata deliberatamente. Dichiarala.
  • @unchecked Sendable è una promessa che devi saper enunciare. Se non sai nominare il meccanismo che fornisce la sicurezza, non ce l'hai.
  • Una classe @MainActor è Sendable; l'isolamento è la prova. Ecco perché SearchViewModel non ha bisogno di annotazione Sendable.
  • async nonisolated non ereditava l'actor del chiamante prima di Swift 6.2. Ogni articolo, esempio e risposta Stack Overflow dal 2022 al 2025 assume la vecchia regola. Controlla la data di quello che leggi.
  • SuspendingClock per un backoff di rete è sbagliato. Il sonno del dispositivo non mette in pausa il rate limiter del server.
  • Che Task.sleep lanci in caso di cancellazione è una feature. Ingoiare quell'errore con try? converte silenziosamente "abbandona il retry" in "finisci l'attesa, poi continua".
  • Duration non è un Double di secondi. Non passare per TimeInterval per fare aritmetica — perderesti la precisione che il tipo esiste per preservare.
