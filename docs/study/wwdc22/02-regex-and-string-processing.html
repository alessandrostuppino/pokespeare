WWDC22 · Module 2 — Regex and String Processing

Swift 5.7 · SE-0350, SE-0351, SE-0354, SE-0355, SE-0357, SE-0363

Every snippet in this document was typechecked against the iOS 26.4 SDK in Swift 6 language mode before being written down.

1. What shipped, and what problem it solves

Swift shipped without native regular expressions for eight years. What you had was NSRegularExpression: a class from Foundation, initialized from a String pattern, throwing at runtime if the pattern was malformed, returning NSRange values you had to convert back into String.Index — a conversion that is genuinely easy to get wrong because NSRange counts UTF-16 code units and String.Index does not count anything simple at all.

Swift 5.7 shipped a six-proposal package that replaces all of it:

  • A Regex type, generic over what it captures, so captures are typed rather than stringly-indexed.
  • Literals — /pattern/ — parsed and validated at compile time. A malformed pattern is now a build error.
  • A result-builder DSL (RegexBuilder) for patterns that have outgrown being readable as a one-liner.
  • String algorithms built on top: split, replacing, trimmingPrefix, ranges(of:), contains.
  • Unicode-correct matching semantics, with an explicit switch between grapheme-cluster and Unicode-scalar level.

The headline change is the compile-time validation. A typo in an NSRegularExpression pattern ships to users. A typo in a /…/ literal fails the build.

2. How it actually works

The type carries the captures

let r = /(\d+)-(\d+)/
// r: Regex<(Substring, Substring, Substring)>

Regex is generic over its Output. With no captures, Output is Substring — the whole match. With n capture groups, Output is an (n+1)-tuple: the whole match first, then each group. The compiler derives that tuple by parsing the literal at compile time.

That is why this is safe:

guard let m = s.firstMatch(of: /(\d+)/) else { return nil }
return Int(m.1)          // m.1 is Substring — statically known to exist

There is no "group 3 does not exist" runtime failure, because group 3 does not typecheck.

Named captures become tuple labels:

guard let m = s.wholeMatch(of: /(?<key>\w+)=(?<value>\w+)/) else { return nil }
return (String(m.key), String(m.value))     // ✅ named, not positional

Three ways to build one, and when each applies

Literal — compile-time validated, zero runtime cost to construct, captures typed. Default choice.

s.wholeMatch(of: /[a-z][a-z\-']{1,29}/)

Builder DSL — for patterns that a reader would otherwise have to decode:

import RegexBuilder

let pattern = Regex {
  Anchor.startOfSubject
  CharacterClass("a"..."z")
  Repeat(1...29) {
    CharacterClass.anyOf("-'").union(CharacterClass("a"..."z"))
  }
  Anchor.endOfSubject
}

More verbose, but diffable, commentable, and composable — you can factor a sub-pattern into a let and reuse it. The DSL is a result builder, exactly like SwiftUI's body.

Runtime string — when the pattern genuinely is not known until runtime (user-supplied search, config file):

func runtime(_ pattern: String) throws -> Regex<AnyRegexOutput> {
  try Regex(pattern)     // throws — this is the only form that can fail at runtime
}

Note the Output type: AnyRegexOutput. The compiler cannot know the capture shape, so you are back to dynamic access. This is the escape hatch, and it should feel like one.

Matching semantics: the Unicode part everybody skips

By default, Swift matches at the grapheme cluster level — the same level String iterates at. . matches one user-perceived character, so it matches 🇮🇹 as one thing, and e + combining-acute as one thing.

NSRegularExpression matches UTF-16 code units. This is a real behavioural difference, not a detail. If you are porting a pattern and the results differ on non-ASCII input, this is why.

You can opt into scalar-level matching with .matchingSemantics(.unicodeScalar) (SE-0363).

Options are applied as methods on the regex, not as flags in the pattern:

let ci = /pikachu/.ignoresCase()

The string algorithms

SE-0357 generalized the String API so that anything taking a separator or a pattern takes a RegexComponent:

s.replacing(/\s+/, with: " ")     // collapse whitespace runs
s.split(separator: /,\s*/)        // split on comma with optional spaces
s.trimmingPrefix(/\s+/)           // drop leading whitespace
s.contains(/pikachu/.ignoresCase())
s.ranges(of: /a/)

These are the ones you will reach for most often. Most "I need a regex" moments are really one of these five.

3. The trap: Regex is not Sendable

This is verified, not remembered. Compiling this in Swift 6 language mode:

let g = /[a-z]+/
nonisolated func fromNonisolated(_ s: String) -> Bool {
  s.wholeMatch(of: g) != nil
}

produces:

error: main actor-isolated let 'g' can not be referenced from a nonisolated context

And explicitly:

error: type 'Regex<Substring>' does not conform to the 'Sendable' protocol

What is happening. Regex is not Sendable. Under Swift 6, a global let of a non-Sendable type cannot be globally accessible without isolation, so the compiler infers @MainActor for it. The declaration compiles fine — the error only fires at the point where nonisolated code touches it.

That last part matters, and it is why this bug hides: your global regex constant compiles, and your @MainActor view model uses it happily. It only explodes the day you reference it from a nonisolated helper or a detached task.

Two fixes, both verified to compile:

// A — build it at the use site. Constructing from a literal is cheap.
nonisolated func a(_ s: String) -> Bool {
  s.wholeMatch(of: /[a-z]+/) != nil
}

// B — a static *computed* property: a fresh Regex per access, no shared state.
enum Patterns {
  static var name: Regex<Substring> { /[a-z]+/ }
}
nonisolated func b(_ s: String) -> Bool {
  s.wholeMatch(of: Patterns.name) != nil
}

Note that B is static var with a getter, not static let. A static let would reintroduce exactly the shared non-Sendable global the compiler objected to.

This matters directly for the exercise below, because the SDK is not @MainActor anywhere.

5. Where it lands in this codebase

Input validation is currently done twice, in two different ad-hoc ways, and neither says what it means.

SearchViewModel.swift:87-89 — a magic number doing two jobs:

var isSearchButtonVisible: Bool {
  searchText.count > 2
}

This single expression is both "should the Search button appear" and "is this input valid" — it is consulted again as a guard at :140. The audit recorded this as finding C-20. Two different questions sharing one answer is exactly how a UI rule and a validation rule drift apart later.

SearchViewModel.swift:233-236 — character filtering by closure:

func searchTextDidChange() {
  let filtered = searchText.filter { $0.isLetter || $0.isWhitespace }
  searchText = filtered != searchText ? filtered : searchText
}

This permits " " (whitespace only) and "a" (too short) and rejects "farfetch'd" and "ho-oh" and "mr. mime" — all of which are real Pokémon names. The filter is simultaneously too permissive and too strict.

A regex states the actual rule in one place, and states it in a form a reader can check against reality.

6. Exercise

Goal: replace both ad-hoc rules with one named, tested, regex-backed validator — and hit the Sendable trap deliberately so you remember it.

6a — Write the validator

Add a validator that answers "is this a plausible Pokémon name?" Real names to satisfy: pikachu, mr. mime, farfetch'd, ho-oh, nidoran♀, porygon-z. Names to reject: "", " ", "a", "123", "<script>".

Decide deliberately where it lives:

  • In the app (Demo/PokeApp/), it is a UI concern — and the app is @MainActor, so the Sendable trap will not bite.
  • In the SDK (Pokespeare/), it is an API-contract concern — and the SDK has no @MainActor anywhere, so a static let regex will fail to compile.

Try the SDK placement first, with a static let, specifically to see the error. Then fix it. Then decide where it actually belongs and write down why.

6b — Separate the two questions

Split isSearchButtonVisible into two properties with two names: one for "the button should be visible", one for "this input is valid enough to send". They may currently return the same value — the point is that they are now allowed to diverge without a bug.

6c — Test it

Add a parameterized Swift Testing case, matching the conventions already used in this repo (see SearchViewModelTests.swift:120-125 for the tuple-argument style):

@Test(arguments: [
  ("pikachu", true), ("mr. mime", true), ("farfetch'd", true),
  ("ho-oh", true), ("", false), ("  ", false), ("a", false), ("123", false),
])
func validatesNames(_ name: String, _ expected: Bool) { … }

Acceptance criteria.

  1. The new test passes, covering every case above.
  2. All 71 existing tests still pass (53 SDK + 18 app).
  3. searchTextDidChange's filter closure is gone, replaced by the regex rule — or you have written down a concrete reason it must stay.
  4. swiftlint lint --strict clean.
  5. You can state, in one sentence, why the regex could not be a static let in the SDK.
xcodebuild test -scheme Pokespeare -destination 'platform=iOS Simulator,name=iPhone 17 Pro'
xcodebuild test -project Demo/PokeApp.xcodeproj -scheme PokeApp -destination 'platform=iOS Simulator,name=iPhone 17 Pro'

6d — Optional: the builder form

Rewrite your pattern using RegexBuilder and keep whichever version a reader would understand faster. There is no correct answer; there is a defensible one. Write down which you kept and why.

7. Pitfalls

  • Regex is not Sendable. Covered above. The failure appears at the use site, not the declaration, so it hides until nonisolated code touches it.
  • static let vs static var for patterns. In non-MainActor code, only the computed var form is safe.
  • Grapheme vs scalar semantics. Swift defaults to grapheme clusters; NSRegularExpression uses UTF-16 code units. Ported patterns can silently change behaviour on emoji, combining marks, and flags.
  • The /…/ literal vs the division operator. Swift's parser handles the ambiguity, but bare / inside a literal must be escaped. For patterns containing many slashes, use the extended form #/ … /#.
  • AnyRegexOutput throws away the type safety that is the whole point. If you find yourself using try Regex(String) for a pattern that is actually a constant, use a literal instead.
  • Do not validate with a regex what the server will validate anyway. Client-side name validation here is a UX affordance (fail fast, no wasted request), not a security boundary. Pokespeare.Error.pokemonNotFound remains the authority.

WWDC22 · Modulo 2 — Regex ed elaborazione di stringhe

Swift 5.7 · SE-0350, SE-0351, SE-0354, SE-0355, SE-0357, SE-0363

Ogni frammento di questo documento è stato verificato col typechecker contro l'SDK iOS 26.4 in Swift 6 language mode prima di essere scritto.

1. Cosa è uscito, e quale problema risolve

Swift è uscito senza espressioni regolari native per otto anni. Quello che avevi era NSRegularExpression: una classe di Foundation, inizializzata da un pattern String, che lanciava a runtime se il pattern era malformato, e restituiva valori NSRange da riconvertire in String.Index — una conversione genuinamente facile da sbagliare, perché NSRange conta code unit UTF-16 e String.Index non conta nulla di semplice.

Swift 5.7 ha rilasciato un pacchetto di sei proposte che sostituisce tutto questo:

  • Un tipo Regex, generico su ciò che cattura, così le catture sono tipizzate invece che indicizzate per stringa.
  • Literal — /pattern/ — parsati e validati a compile-time. Un pattern malformato è ora un errore di build.
  • Un DSL result-builder (RegexBuilder) per pattern che hanno superato la leggibilità di una riga sola.
  • Algoritmi su stringhe costruiti sopra: split, replacing, trimmingPrefix, ranges(of:), contains.
  • Semantica di matching corretta per Unicode, con un interruttore esplicito tra livello grapheme cluster e Unicode scalar.

Il cambiamento principale è la validazione a compile-time. Un refuso in un pattern NSRegularExpression arriva agli utenti. Un refuso in un literal /…/ fa fallire la build.

2. Come funziona davvero

Il tipo porta le catture

let r = /(\d+)-(\d+)/
// r: Regex<(Substring, Substring, Substring)>

Regex è generico sul suo Output. Senza catture, Output è Substring — l'intero match. Con n gruppi di cattura, Output è una tupla di (n+1) elementi: prima il match intero, poi ogni gruppo. Il compilatore ricava quella tupla parsando il literal a compile-time.

Ecco perché questo è sicuro:

guard let m = s.firstMatch(of: /(\d+)/) else { return nil }
return Int(m.1)          // m.1 è Substring — noto staticamente come esistente

Non esiste un fallimento a runtime del tipo "il gruppo 3 non esiste", perché il gruppo 3 non passa il typecheck.

Le catture nominate diventano etichette di tupla:

guard let m = s.wholeMatch(of: /(?<key>\w+)=(?<value>\w+)/) else { return nil }
return (String(m.key), String(m.value))     // ✅ nominate, non posizionali

Tre modi per costruirne una, e quando usarli

Literal — validato a compile-time, costo zero a runtime per costruirlo, catture tipizzate. Scelta di default.

s.wholeMatch(of: /[a-z][a-z\-']{1,29}/)

DSL builder — per pattern che altrimenti un lettore dovrebbe decifrare:

import RegexBuilder

let pattern = Regex {
  Anchor.startOfSubject
  CharacterClass("a"..."z")
  Repeat(1...29) {
    CharacterClass.anyOf("-'").union(CharacterClass("a"..."z"))
  }
  Anchor.endOfSubject
}

Più verboso, ma diffabile, commentabile e componibile — puoi estrarre un sotto-pattern in un let e riusarlo. Il DSL è un result builder, esattamente come il body di SwiftUI.

Stringa a runtime — quando il pattern davvero non è noto fino a runtime (ricerca fornita dall'utente, file di configurazione):

func runtime(_ pattern: String) throws -> Regex<AnyRegexOutput> {
  try Regex(pattern)     // throws — è l'unica forma che può fallire a runtime
}

Nota il tipo Output: AnyRegexOutput. Il compilatore non può conoscere la forma delle catture, quindi torni all'accesso dinamico. Questa è la via di fuga, e deve sembrarlo.

Semantica di matching: la parte Unicode che tutti saltano

Di default Swift fa matching a livello di grapheme cluster — lo stesso livello su cui itera String. . corrisponde a un carattere percepito dall'utente, quindi corrisponde a 🇮🇹 come una cosa sola, e a e + accento combinante come una cosa sola.

NSRegularExpression fa matching su code unit UTF-16. È una differenza di comportamento reale, non un dettaglio. Se stai portando un pattern e i risultati differiscono su input non ASCII, il motivo è questo.

Puoi passare al matching a livello di scalar con .matchingSemantics(.unicodeScalar) (SE-0363).

Le opzioni si applicano come metodi sulla regex, non come flag nel pattern:

let ci = /pikachu/.ignoresCase()

Gli algoritmi su stringhe

SE-0357 ha generalizzato l'API di String così che tutto ciò che prende un separatore o un pattern prende un RegexComponent:

s.replacing(/\s+/, with: " ")     // comprime sequenze di spazi
s.split(separator: /,\s*/)        // divide su virgola con spazi opzionali
s.trimmingPrefix(/\s+/)           // toglie gli spazi iniziali
s.contains(/pikachu/.ignoresCase())
s.ranges(of: /a/)

Sono quelli a cui ricorrerai più spesso. La maggior parte dei momenti "mi serve una regex" è in realtà uno di questi cinque.

3. La trappola: Regex non è Sendable

Questo è verificato, non ricordato. Compilando questo in Swift 6 language mode:

let g = /[a-z]+/
nonisolated func fromNonisolated(_ s: String) -> Bool {
  s.wholeMatch(of: g) != nil
}

si ottiene:

error: main actor-isolated let 'g' can not be referenced from a nonisolated context

E esplicitamente:

error: type 'Regex<Substring>' does not conform to the 'Sendable' protocol

Cosa sta succedendo. Regex non è Sendable. In Swift 6, un let globale di tipo non Sendable non può essere accessibile globalmente senza isolamento, quindi il compilatore gli inferisce @MainActor. La dichiarazione compila benissimo — l'errore scatta solo nel punto in cui codice nonisolated lo tocca.

Quest'ultima parte conta, ed è il motivo per cui il bug si nasconde: la tua costante regex globale compila, e il tuo view model @MainActor la usa contento. Esplode solo il giorno in cui la referenzi da un helper nonisolated o da un task distaccato.

Due fix, entrambi verificati che compilano:

// A — costruiscila nel punto d'uso. Costruire da un literal è economico.
nonisolated func a(_ s: String) -> Bool {
  s.wholeMatch(of: /[a-z]+/) != nil
}

// B — una proprietà statica *calcolata*: una Regex nuova a ogni accesso, nessuno stato condiviso.
enum Patterns {
  static var name: Regex<Substring> { /[a-z]+/ }
}
nonisolated func b(_ s: String) -> Bool {
  s.wholeMatch(of: Patterns.name) != nil
}

Nota che B è static var con un getter, non static let. Un static let reintrodurrebbe esattamente il globale condiviso non Sendable a cui il compilatore si opponeva.

Questo conta direttamente per l'esercizio qui sotto, perché l'SDK non è @MainActor da nessuna parte.

5. Dove atterra in questo codebase

La validazione dell'input è fatta attualmente due volte, in due modi improvvisati diversi, e nessuno dei due dice cosa intende.

SearchViewModel.swift:87-89 — un numero magico che fa due lavori:

var isSearchButtonVisible: Bool {
  searchText.count > 2
}

Questa singola espressione è sia "il bottone Search deve comparire" sia "questo input è valido" — viene riconsultata come guardia a :140. L'audit l'ha registrata come finding C-20. Due domande diverse che condividono una risposta sola è esattamente il modo in cui una regola di UI e una di validazione divergono più avanti.

SearchViewModel.swift:233-236 — filtro dei caratteri via closure:

func searchTextDidChange() {
  let filtered = searchText.filter { $0.isLetter || $0.isWhitespace }
  searchText = filtered != searchText ? filtered : searchText
}

Questo permette " " (solo spazi) e "a" (troppo corto) e rifiuta "farfetch'd", "ho-oh" e "mr. mime" — tutti nomi di Pokémon reali. Il filtro è simultaneamente troppo permissivo e troppo restrittivo.

Una regex enuncia la regola vera in un posto solo, e la enuncia in una forma che un lettore può confrontare con la realtà.

6. Esercizio

Obiettivo: sostituire entrambe le regole improvvisate con un unico validatore basato su regex, nominato e testato — e sbattere deliberatamente contro la trappola Sendable per ricordartela.

6a — Scrivi il validatore

Aggiungi un validatore che risponda a "questo è un nome di Pokémon plausibile?". Nomi reali da soddisfare: pikachu, mr. mime, farfetch'd, ho-oh, nidoran♀, porygon-z. Nomi da rifiutare: "", " ", "a", "123", "<script>".

Decidi deliberatamente dove vive:

  • Nell'app (Demo/PokeApp/) è una questione di UI — e l'app è @MainActor, quindi la trappola Sendable non morde.
  • Nell'SDK (Pokespeare/) è una questione di contratto dell'API — e l'SDK non ha @MainActor da nessuna parte, quindi un static let regex non compilerà.

Prova prima la collocazione nell'SDK, con un static let, apposta per vedere l'errore. Poi sistemalo. Poi decidi dove sta davvero e scrivi perché.

6b — Separa le due domande

Dividi isSearchButtonVisible in due proprietà con due nomi: una per "il bottone deve essere visibile", una per "questo input è abbastanza valido da essere inviato". Al momento possono restituire lo stesso valore — il punto è che ora possono divergere senza generare un bug.

6c — Testalo

Aggiungi un caso Swift Testing parametrizzato, coerente con le convenzioni già in uso nel repo (vedi SearchViewModelTests.swift:120-125 per lo stile con argomenti a tupla):

@Test(arguments: [
  ("pikachu", true), ("mr. mime", true), ("farfetch'd", true),
  ("ho-oh", true), ("", false), ("  ", false), ("a", false), ("123", false),
])
func validatesNames(_ name: String, _ expected: Bool) { … }

Criteri di accettazione.

  1. Il nuovo test passa, coprendo ogni caso qui sopra.
  2. Tutti i 71 test esistenti passano ancora (53 SDK + 18 app).
  3. La closure filter di searchTextDidChange è sparita, sostituita dalla regola regex — oppure hai scritto un motivo concreto per cui deve restare.
  4. swiftlint lint --strict pulito.
  5. Sai dire, in una frase, perché la regex non poteva essere un static let nell'SDK.
xcodebuild test -scheme Pokespeare -destination 'platform=iOS Simulator,name=iPhone 17 Pro'
xcodebuild test -project Demo/PokeApp.xcodeproj -scheme PokeApp -destination 'platform=iOS Simulator,name=iPhone 17 Pro'

6d — Facoltativo: la forma builder

Riscrivi il tuo pattern usando RegexBuilder e tieni la versione che un lettore capirebbe più in fretta. Non c'è una risposta corretta; ce n'è una difendibile. Scrivi quale hai tenuto e perché.

7. Trappole

  • Regex non è Sendable. Trattato sopra. Il fallimento compare nel punto d'uso, non nella dichiarazione, quindi si nasconde finché codice nonisolated non la tocca.
  • static let vs static var per i pattern. In codice non @MainActor, solo la forma var calcolata è sicura.
  • Semantica grapheme vs scalar. Swift usa i grapheme cluster di default; NSRegularExpression usa code unit UTF-16. I pattern portati possono cambiare comportamento silenziosamente su emoji, segni combinanti e bandiere.
  • Il literal /…/ e l'operatore di divisione. Il parser di Swift gestisce l'ambiguità, ma una / nuda dentro un literal va escapata. Per pattern con molte barre, usa la forma estesa #/ … /#.
  • AnyRegexOutput butta via la type safety che è tutto il punto. Se ti ritrovi a usare try Regex(String) per un pattern che in realtà è una costante, usa un literal.
  • Non validare con una regex ciò che il server validerà comunque. La validazione del nome lato client qui è un affordance di UX (fallisci subito, nessuna richiesta sprecata), non un confine di sicurezza. Pokespeare.Error.pokemonNotFound resta l'autorità.
