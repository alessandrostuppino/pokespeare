# WWDC22 · Modulo 6 — Sfide di implementazione

I moduli 1–5 hanno insegnato le API. Questo modulo ti fa **re-implementare da zero la tecnologia WWDC22 che questo progetto già usa** — costruendo feature abbastanza grandi da non poterlo evitare.

La distinzione conta. Leggere `RetryPolicy.swift` e pensare "sì, `Duration`, chiaro" non è la stessa cosa che progettare un nuovo manager e scoprire da solo dove `Sendable` morde, dove va il confine degli errori, e perché il codice esistente ha fatto le scelte che ha fatto.

Ogni sfida è una **feature reale** contro **endpoint reali**, verificati dal vivo mentre scrivevo questo documento.

## Gli endpoint (verificati dal vivo)

Tutti e quattro hanno restituito HTTP 200 mentre scrivevo questo documento.

**`GET /api/v2/pokemon-species/{name}`** — già usato da `PokemonSpeciesRequest`. Contiene una chiave che questo progetto attualmente ignora:

```json
{ "evolution_chain": { "url": "https://pokeapi.co/api/v2/evolution-chain/10/" } }
```

Nota bene: **un URL, non un id.** Non esiste un campo `evolution_chain.id`. È un problema di design vero, non un dettaglio — vedi la Sfida A.

**`GET /api/v2/evolution-chain/{id}`** — un albero ricorsivo:

```json
{
  "id": 10,
  "chain": {
    "species": { "name": "pichu" },
    "evolution_details": [],
    "evolves_to": [
      { "species": { "name": "pikachu" },
        "evolution_details": [ { "min_level": null, "trigger": {} } ],
        "evolves_to": [ { "species": { "name": "raichu" }, "evolves_to": [] } ] }
    ]
  }
}
```

Verificato per la catena 10: `pichu → pikachu → raichu`. Esistono catene ramificate (Eevee è la catena 67) — il tuo modello deve gestire `evolves_to` con più di un elemento.

**`GET /api/v2/type/{name}`** — `damage_relations` ha esattamente sei chiavi. Verificato per `electric`:

```
double_damage_from → [ground]
double_damage_to   → [flying, water]
half_damage_from   → [flying, steel, electric]
half_damage_to     → [grass, electric, dragon]
no_damage_from     → []
no_damage_to       → [ground]
```

**`GET /api/v2/ability/{name}`** — `effect_entries` e `flavor_text_entries`, entrambi taggati per lingua esattamente come il flavor text che `PokemonManager` già gestisce.

## Regole valide per ogni sfida

Sono le invarianti già in vigore nel progetto. Romperne una è una sfida fallita anche se la feature funziona.

1. **La superficie pubblica dell'SDK resta deliberata.** Oggi sono esattamente quattro tipi: `Pokespeare`, `Pokespeare.Error`, `PokemonView`, `PokemonViewModel`. Qualsiasi cosa nuova che diventi `public` dev'essere una decisione che sai difendere — il finding **C-17** era superficie pubblica accidentale.
2. **Un solo transport.** `APIClient` è l'unica cosa che esegue una richiesta (`APIClient.swift:3-8`). Nessun nuovo manager si prende la propria `URLSession` — il finding **C-03** era esattamente quella duplicazione.
3. **Un solo confine degli errori.** `Pokespeare.Error.from(error:)` (`Error.swift:109-124`) è l'unico punto di mappatura, e l'ordinamento dei suoi case è portante. I nuovi tipi d'errore si inseriscono in quello switch; non si prendono una via di fuga propria. I finding **C-01** e **C-25** erano entrambi questo.
4. **Niente `Optional` come canale d'errore.** Finding **C-05**. Se tre cose possono andare male, tre case — non un `nil`.
5. **Tutto `Sendable`, niente `@unchecked`** nel codice di produzione.
6. **Test: nessuna assertion dentro `catch`.** Finding **C-10**. Usa `#expect(throws:)`.
7. **I test di integrazione sono taggati e protetti** da `RUN_INTEGRATION_TESTS` (`TestTags.swift`). Gli endpoint reali hanno rate limit; la CI deve restare verde senza di essi.
8. **Localizza le stringhe utente** in entrambi i catalog, en + it. Finding **C-21**.
9. **L'accessibilità non è facoltativa.** Label VoiceOver, Dynamic Type. Finding **C-23**.

## Sfida A — Servizio catena evolutiva

**Dimensione:** grande (la principale). **Forza:** `Sendable`, existential, request generiche, `Clock`/`Duration`, concorrenza strutturata, il confine degli errori.

### Obiettivo

Aggiungere `Pokespeare.evolutionChain(for:) async throws -> EvolutionChain` che restituisce la linea evolutiva completa per un nome di Pokémon.

### Perché è più difficile di quanto sembri

Tre problemi di design veri, in ordine crescente di interesse:

**A1 — Ottieni un URL, non un id.** `pokemon-species` dà `evolution_chain.url`. Le tue opzioni:

- Estrarre l'id dal path dell'URL e costruire una normale `EvolutionChainRequest(id:)`.
- Rendere la request costruibile da un URL assoluto.

`HTTPRequest` oggi costruisce il suo URL da host + componenti di path (`HTTPRequest.swift`, `makeURLRequest()`). Qualunque cosa tu scelga, **scrivi l'argomentazione contro l'altra.** Indizio: considera cosa succede se PokéAPI cambia la struttura dei suoi URL, e considera quale opzione è testabile senza rete.

**A2 — La risposta è ricorsiva.** `chain.evolves_to[].evolves_to[]…`, profonda arbitrariamente, e ramificata (Eevee ne ha otto). Il tuo modello di risposta dev'essere ricorsivo, e il tuo modello di dominio probabilmente **non** dovrebbe esserlo — una lista piatta di stadi, o un albero che vuoi davvero renderizzare, è verosimilmente più comodo che rispecchiare il JSON. I modelli di risposta esistenti scrivono tutti `init(from:)` a mano con container annidati (`PokemonSpeciesResponse.swift:31-44`); segui quello stile o giustifica lo scostamento.

**A3 — Due richieste sequenziali.** Prima species, poi chain. La seconda dipende dalla prima, quindi `async let` **non** si applica — a differenza di `SearchViewModel.swift:172-173`, dove le due chiamate sono indipendenti. Capire *perché* esiste quella differenza è metà del senso di questa sfida.

### Passi

1. `EvolutionChainRequest` conforme a `HTTPCodableRequest`.
2. `EvolutionChainResponse` — ricorsiva, `Decodable`.
3. `EvolutionManager`, `Sendable`, che prende un `APIClient`. Solo logica di dominio: nessun transport. Rispecchia `PokemonManager.swift`.
4. `EvolutionManager.Error` con case veri, e un overload di `Pokespeare.Error.from(error:)`. Aggiungi case pubblici solo se l'utente potrebbe agire diversamente.
5. Collega una nuova closure a `Pokespeare` — è una struct di closure (`Pokespeare.swift:3-5`), quindi aggiungere un servizio significa aggiungere una closure memorizzata, un metodo pubblico e una riga in `live(pokemonManager:translationManager:)`. **Questo cambia un initializer pubblico.** Ragiona se sia una modifica source-breaking e cosa faresti al riguardo in un SDK spedito.
6. Aggiungi un budget di timeout per richiesta usando `Duration`, rispettando il lavoro sul clock iniettabile del Modulo 3 se l'hai fatto.

### Criteri di accettazione

1. `evolutionChain(for: "pikachu")` restituisce `pichu → pikachu → raichu` in ordine.
2. Una catena ramificata (`eevee`) restituisce tutti i rami, non solo il primo.
3. Un Pokémon senza evoluzioni (`tauros`) restituisce una catena a stadio singolo — **non** un errore, e non un array vuoto che il chiamante debba trattare come caso speciale.
4. Test unitari con fixture `MockedSession` per: percorso felice, ramificazione, stadio singolo, 404, corpo malformato. Nessuna rete reale.
5. Esattamente un test di integrazione, taggato `.integration` e protetto.
6. Ogni fallimento arriva come `Pokespeare.Error`. Dimostralo — un test che asserisce che un fallimento di transport non emerge come `.unknown` (è il finding **C-01**, ed è il singolo test di regressione più prezioso dell'SDK).
7. Tutti i 53 test SDK esistenti passano ancora.
8. `swiftlint lint --strict` pulito.

### Stretch

Dai a `HTTPCodableRequest` un primary associated type (Modulo 1) e usa `any HTTPCodableRequest<EvolutionChainResponse>` dove aiuta davvero. Se non aiuta, dillo e fai marcia indietro — è l'esito corretto e un risultato reale.

## Sfida B — Schermata efficacia dei tipi

**Dimensione:** media. **Forza:** routing con `NavigationStack`, `Grid`, `ViewThatFits`, un secondo nuovo manager, localizzazione, accessibilità.

### Obiettivo

Dalla view di dettaglio di un Pokémon, navigare a una schermata che mostra contro cosa è forte e debole, costruita da `/type/{name}`.

Un Pokémon ha uno o due tipi — `PokemonDetailRequest` già scarica il payload di dettaglio, che li contiene. Per due tipi l'efficacia si **moltiplica** (doppio da terra × metà da terra = neutro). Quella logica di combinazione è logica di dominio e appartiene al manager, non alla view, ed è esattamente il genere di cosa che dovrebbe avere test unitari con fixture costruite a mano.

### Passi

1. `TypeRequest`, `TypeResponse` (le sei chiavi di `damage_relations`), `TypeManager`.
2. Logica di combinazione per i doppi tipi, come funzione pura. Testala in isolamento — nessuna rete, nessuna view.
3. Una schermata SwiftUI che usa `Grid`/`GridRow` per la tabella di efficacia.
4. Raggiungila con `navigationDestination` — è qui che il lavoro di routing del Modulo 4 rende. Se hai tenuto lo sheet, ora hai un motivo concreto per non farlo.
5. `ViewThatFits` così la tabella degrada a lista alle dimensioni di testo accessibili.
6. Localizza ogni etichetta in en + it, entrambi i catalog.

### Criteri di accettazione

1. Electric mostra debolezza a terra, resiste a volante/acciaio/elettro, nessun danno a terra. I valori verificati sono nella sezione endpoint qui sopra.
2. Un Pokémon a doppio tipo calcola l'efficacia moltiplicata, coperto da test unitari inclusi un caso ×4 e uno ×0.
3. Leggibile alla massima dimensione di testo accessibile — controlla su dispositivo/simulatore, non nel canvas.
4. VoiceOver annuncia ogni cella in modo sensato. "Due" non è sensato; "Terra, danno doppio" sì.
5. Nessun inglese hardcoded. Entrambi gli `.xcstrings` aggiornati.
6. Tutti i test esistenti passano; il nuovo manager ha test unitari con fixture.

## Sfida C — Filtri di ricerca e statistiche sulla cronologia

**Dimensione:** media. **Forza:** `Regex`, Swift Charts, `Layout`, query SwiftData.

### Obiettivo

Far accettare al campo di ricerca una sintassi di filtro semplice, e aggiungere una piccola view di statistiche sulla cronologia di ricerca.

**Sintassi dei filtri**, parsata con `Regex` (Modulo 2):

```
type:electric          → filtra la cronologia per tipo
before:2026-01-01      → filtra per searchDate
pika                   → match su sottostringa semplice
type:electric pika     → combinati
```

### Passi

1. Un parser basato su `Regex` che produce un valore tipizzato `SearchFilter`. Ricorda che `Regex` non è `Sendable` — il Modulo 2 §3 lo copre, e l'SDK non ha `@MainActor`.
2. Applica i filtri alla cronologia. Oggi è `first(where:)` in memoria (`SearchViewModel.swift:143`) con un `FetchDescriptor` costruito a mano (`:256`). `#Predicate` è materia del Batch 2 — per ora fallo onestamente in memoria e **scrivi cosa cambieresti una volta che avrai `#Predicate`.**
3. Una view di statistiche: ricerche per giorno da `searchDate`, come grafico `BarMark`.
4. Accessibilità: i grafici hanno bisogno di etichette esplicite. Un grafico senza etichette in quest'app è una regressione rispetto al commit `9f787fc`.

### Criteri di accettazione

1. Test unitari del parser, parametrizzati, che coprono: ogni filtro da solo, combinati, input malformato, input vuoto. L'input malformato deve degradare a ricerca testuale semplice, mai lanciare nella UI.
2. Valori di filtro non validi non causano crash e non restituiscono silenziosamente tutto.
3. Il grafico ha un'etichetta di accessibilità e valori per mark.
4. Localizzato, entrambi i catalog.
5. Tutti i test esistenti passano.

## Come scegliere

- **Ne fai una?** La Sfida A. È quella che ricostruisce l'architettura vera dell'SDK.
- **Ne fai due?** A poi B. B consuma il lavoro di navigazione di A.
- **Tutte e tre?** A → B → C. C è la più leggera sull'architettura dell'SDK e la più pesante sulla UI.

Non iniziare B o C prima del Modulo 4, e non iniziare A prima del Modulo 3 se intendi fare l'esercizio del clock iniettabile — A è molto più interessante con un clock testabile.

## Cosa guarderò durante la revisione

Quando mi dirai che il batch è finito, è questo che verrà letto. Enunciato in anticipo così nulla è una sorpresa:

- `APIClient` resta l'unico transport?
- Ogni nuovo percorso d'errore termina in `Pokespeare.Error`, con l'ordinamento della mappatura intatto?
- C'è qualcosa di `public` che non serviva lo fosse?
- C'è un `Optional` che fa le veci di un errore?
- Qualche test asserisce dentro un `catch`?
- I test di integrazione sono protetti?
- La nuova UI è usabile al massimo Dynamic Type, e VoiceOver dice qualcosa di utile?
- Le nuove stringhe utente sono in **entrambi** i catalog?
- Dove ti sei scostato dai pattern esistenti, e sai difenderlo?

L'ultima ha il peso maggiore. Uno scostamento difeso batte un'imitazione non difesa.
