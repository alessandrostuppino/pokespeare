## 1. What shipped, and what problem it solves

Swift shipped without native regular expressions for eight years. What you had was `NSRegularExpression`: a class from Foundation, initialized from a `String` pattern, throwing at runtime if the pattern was malformed, returning `NSRange` values you had to convert back into `String.Index` — a conversion that is genuinely easy to get wrong because `NSRange` counts UTF-16 code units and `String.Index` does not count anything simple at all.

Swift 5.7 shipped a six-proposal package that replaces all of it:

- A **`Regex` type**, generic over what it captures, so captures are *typed* rather than stringly-indexed.
- **Literals** — `/pattern/` — parsed and validated **at compile time**. A malformed pattern is now a build error.
- A **result-builder DSL** (`RegexBuilder`) for patterns that have outgrown being readable as a one-liner.
- **String algorithms** built on top: `split`, `replacing`, `trimmingPrefix`, `ranges(of:)`, `contains`.
- **Unicode-correct matching semantics**, with an explicit switch between grapheme-cluster and Unicode-scalar level.

The headline change is the compile-time validation. A typo in an `NSRegularExpression` pattern ships to users. A typo in a `/…/` literal fails the build.

## 2. How it actually works

### The type carries the captures

```swift
let r = /(\d+)-(\d+)/
// r: Regex<(Substring, Substring, Substring)>
```

`Regex` is generic over its `Output`. With no captures, `Output` is `Substring` — the whole match. With *n* capture groups, `Output` is an *(n+1)*-tuple: the whole match first, then each group. The compiler derives that tuple **by parsing the literal at compile time**.

That is why this is safe:

```swift
guard let m = s.firstMatch(of: /(\d+)/) else { return nil }
return Int(m.1)          // m.1 is Substring — statically known to exist
```

There is no "group 3 does not exist" runtime failure, because group 3 does not typecheck.

Named captures become tuple labels:

```swift
guard let m = s.wholeMatch(of: /(?<key>\w+)=(?<value>\w+)/) else { return nil }
return (String(m.key), String(m.value))     // ✅ named, not positional
```

### Three ways to build one, and when each applies

**Literal** — compile-time validated, zero runtime cost to construct, captures typed. Default choice.

```swift
s.wholeMatch(of: /[a-z][a-z\-']{1,29}/)
```

**Builder DSL** — for patterns that a reader would otherwise have to decode:

```swift
import RegexBuilder

let pattern = Regex {
  Anchor.startOfSubject
  CharacterClass("a"..."z")
  Repeat(1...29) {
    CharacterClass.anyOf("-'").union(CharacterClass("a"..."z"))
  }
  Anchor.endOfSubject
}
```

More verbose, but diffable, commentable, and composable — you can factor a sub-pattern into a `let` and reuse it. The DSL is a result builder, exactly like SwiftUI's `body`.

**Runtime string** — when the pattern genuinely is not known until runtime (user-supplied search, config file):

```swift
func runtime(_ pattern: String) throws -> Regex<AnyRegexOutput> {
  try Regex(pattern)     // throws — this is the only form that can fail at runtime
}
```

Note the `Output` type: `AnyRegexOutput`. The compiler cannot know the capture shape, so you are back to dynamic access. This is the escape hatch, and it should feel like one.

### Matching semantics: the Unicode part everybody skips

By default, Swift matches at the **grapheme cluster** level — the same level `String` iterates at. `.` matches one user-perceived character, so it matches `🇮🇹` as one thing, and `e` + combining-acute as one thing.

`NSRegularExpression` matches UTF-16 code units. This is a real behavioural difference, not a detail. If you are porting a pattern and the results differ on non-ASCII input, this is why.

You can opt into scalar-level matching with `.matchingSemantics(.unicodeScalar)` ([SE-0363](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0363-unicode-for-string-processing.md)).

Options are applied as methods on the regex, not as flags in the pattern:

```swift
let ci = /pikachu/.ignoresCase()
```

### The string algorithms

[SE-0357](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0357-algorithms-string-processing.md) generalized the `String` API so that anything taking a separator or a pattern takes a `RegexComponent`:

```swift
s.replacing(/\s+/, with: " ")     // collapse whitespace runs
s.split(separator: /,\s*/)        // split on comma with optional spaces
s.trimmingPrefix(/\s+/)           // drop leading whitespace
s.contains(/pikachu/.ignoresCase())
s.ranges(of: /a/)
```

These are the ones you will reach for most often. Most "I need a regex" moments are really one of these five.

## 3. The trap: `Regex` is not `Sendable`

This is verified, not remembered. Compiling this in Swift 6 language mode:

```swift
let g = /[a-z]+/
nonisolated func fromNonisolated(_ s: String) -> Bool {
  s.wholeMatch(of: g) != nil
}
```

produces:

```
error: main actor-isolated let 'g' can not be referenced from a nonisolated context
```

And explicitly:

```
error: type 'Regex<Substring>' does not conform to the 'Sendable' protocol
```

**What is happening.** `Regex` is not `Sendable`. Under Swift 6, a global `let` of a non-`Sendable` type cannot be globally accessible without isolation, so the compiler infers `@MainActor` for it. The declaration compiles fine — the error only fires at the point where **nonisolated** code touches it.

That last part matters, and it is why this bug hides: your global regex constant compiles, and your `@MainActor` view model uses it happily. It only explodes the day you reference it from a `nonisolated` helper or a detached task.

**Two fixes, both verified to compile:**

```swift
// A — build it at the use site. Constructing from a literal is cheap.
nonisolated func a(_ s: String) -> Bool {
  s.wholeMatch(of: /[a-z]+/) != nil
}

// B — a static *computed* property: a fresh Regex per access, no shared state.
enum Patterns {
  static var name: Regex<Substring> { /[a-z]+/ }
}
nonisolated func b(_ s: String) -> Bool {
  s.wholeMatch(of: Patterns.name) != nil
}
```

Note that B is `static var` with a getter, **not** `static let`. A `static let` would reintroduce exactly the shared non-`Sendable` global the compiler objected to.

This matters directly for the exercise below, because the SDK is not `@MainActor` anywhere.

## 5. Where it lands in this codebase

Input validation is currently done twice, in two different ad-hoc ways, and neither says what it means.

**`SearchViewModel.swift:87-89`** — a magic number doing two jobs:

```swift
var isSearchButtonVisible: Bool {
  searchText.count > 2
}
```

This single expression is *both* "should the Search button appear" *and* "is this input valid" — it is consulted again as a guard at `:140`. The audit recorded this as finding **C-20**. Two different questions sharing one answer is exactly how a UI rule and a validation rule drift apart later.

**`SearchViewModel.swift:233-236`** — character filtering by closure:

```swift
func searchTextDidChange() {
  let filtered = searchText.filter { $0.isLetter || $0.isWhitespace }
  searchText = filtered != searchText ? filtered : searchText
}
```

This permits `"   "` (whitespace only) and `"a"` (too short) and rejects `"farfetch'd"` and `"ho-oh"` and `"mr. mime"` — all of which are real Pokémon names. The filter is simultaneously too permissive and too strict.

A regex states the actual rule in one place, and states it in a form a reader can check against reality.

## 7. Pitfalls

- **`Regex` is not `Sendable`.** Covered above. The failure appears at the *use* site, not the declaration, so it hides until nonisolated code touches it.
- **`static let` vs `static var` for patterns.** In non-`MainActor` code, only the computed `var` form is safe.
- **Grapheme vs scalar semantics.** Swift defaults to grapheme clusters; `NSRegularExpression` uses UTF-16 code units. Ported patterns can silently change behaviour on emoji, combining marks, and flags.
- **The `/…/` literal vs the division operator.** Swift's parser handles the ambiguity, but bare `/` inside a literal must be escaped. For patterns containing many slashes, use the extended form `#/ … /#`.
- **`AnyRegexOutput` throws away the type safety** that is the whole point. If you find yourself using `try Regex(String)` for a pattern that is actually a constant, use a literal instead.
- **Do not validate with a regex what the server will validate anyway.** Client-side name validation here is a UX affordance (fail fast, no wasted request), not a security boundary. `Pokespeare.Error.pokemonNotFound` remains the authority.
