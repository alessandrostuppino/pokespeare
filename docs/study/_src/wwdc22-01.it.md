# WWDC22 · Modulo 1 — Generics ed existential

**Swift 5.7** · [SE-0335](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0335-existential-any.md), [SE-0309](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0309-unlock-existential-types-for-all-protocols.md), [SE-0341](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0341-opaque-parameters.md), [SE-0346](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0346-light-weight-same-type-syntax.md), [SE-0352](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0352-implicit-open-existentials.md), [SE-0353](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0353-constrained-existential-types.md), [SE-0358](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0358-primary-associated-types-in-stdlib.md)

## 1. Cosa è uscito, e quale problema risolve

Prima di Swift 5.7 generics e protocol avevano uno scalino di usabilità. Due sintomi che tutti hanno incontrato:

**"Protocol can only be used as a generic constraint."** Nel momento in cui un protocol aveva un associated type, non potevi scriverlo come tipo. `any Collection` era illegale. Le opzioni erano un type eraser scritto a mano, oppure ristrutturare l'intero call site attorno ai generics.

**`some` e `any` sembravano identici ma non lo erano.** Entrambi scritti come nome nudo del protocol — `func f(_ x: Shape)` — anche se uno è un tipo concreto risolto a compile-time e l'altro è una scatola a runtime. I principianti non potevano distinguerli perché la sintassi non dava nulla da distinguere.

Swift 5.7 ha sistemato entrambi, più l'ergonomia attorno. Il filo conduttore: **rendere visibile nel sorgente la distinzione tra "un tipo specifico, scelto dal chiamante" e "un tipo qualsiasi, deciso a runtime", e poi rimuovere le restrizioni artificiali sul secondo.**

## 2. Come funziona davvero

È la sezione che conta. Se di questo modulo ricordi una cosa sola, che sia lo schema del layout.

### `some` — tipi opachi, risolti a compile-time

```swift
func makeShape() -> some Shape { Circle() }
```

`some Shape` significa: *qui c'è esattamente un tipo concreto, il compilatore lo conosce, il chiamante no.* Il chiamante impara "questo è conforme a `Shape`" e nient'altro.

Poiché il tipo è noto a compile-time, il compilatore può **specializzare**: emette una versione della funzione con `Circle` incorporato. Le chiamate a metodo sono dirette, il valore è memorizzato inline, niente boxing, niente indirezione. Il costo di `some` a runtime è *zero* — è uno strumento di occultamento dell'informazione, non di performance.

La regola che frega: una funzione che restituisce `some Shape` deve restituire **lo stesso** tipo concreto su ogni percorso. Questo non compila:

```swift
func makeShape(circular: Bool) -> some Shape {
  circular ? Circle() : Square()   // ❌ due tipi concreti diversi
}
```

### `any` — existential, risolti a runtime

```swift
let shapes: [any Shape] = [Circle(), Square()]
```

`any Shape` significa: *un tipo qualsiasi conforme a `Shape`, potenzialmente diverso per ogni valore, deciso a runtime.* L'array eterogeneo qui sopra è possibile solo con `any`.

Questo costa qualcosa, e il costo è specificato con precisione nella documentazione ABI di Swift. Dal [documento ufficiale sul layout dei tipi](https://github.com/swiftlang/swift/blob/main/docs/ABI/TypeLayout.rst):

> If there is no class constraint on a protocol or protocol composition type, the existential container has to accommodate a value of arbitrary size and alignment. It does this using a **fixed-size buffer**, which is three pointers in size and pointer-aligned.

Il layout, citato dallo stesso documento:

```c
struct OpaqueExistentialContainer {
  void *fixedSizeBuffer[3];              // 24 byte su 64 bit
  Metadata *type;                         // che tipo c'è davvero dentro
  WitnessTable *witnessTables[NUM_WITNESS_TABLES];  // come chiamarne i metodi
};
```

Leggilo con attenzione, perché ne discendono direttamente tre conseguenze:

1. **I valori ≤ 3 word stanno inline.** Una `struct Point { var x, y: Double }` è 2 word — vive direttamente nel buffer. Gratis.
2. **I valori > 3 word finiscono sull'heap.** Una struct con quattro `Double` non ci sta, quindi l'existential memorizza un puntatore a una **side allocation**. Metterne uno in un array significa un'allocazione heap *per elemento*. È il costo nascosto di `[any Shape]`.
3. **Le chiamate a metodo passano da una witness table.** Non una chiamata diretta, nemmeno una vtable — una tabella di puntatori a funzione cercata per conformance. Non è gratis, e non è inlinabile attraverso il confine.

C'è un caso più economico, sempre dal documento ABI: se un protocol è vincolato a classi (`protocol P: AnyObject`), il compilatore usa un `ClassExistentialContainer` — un singolo puntatore, dato che le istanze di classe sono già un puntatore e portano già i propri metadata. Niente buffer a dimensione fissa, niente side allocation.

**La regola pratica:** usa `some` di default. Usa `any` quando ti serve davvero eterogeneità o tipi che variano a runtime — e sappi che lo stai pagando.

### Perché `any` è diventato obbligatorio

[SE-0335](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0335-existential-any.md) ha reso la parola chiave obbligatoria (in Swift 6 language mode; un warning prima). La motivazione è esattamente la confusione qui sopra: la cosa costosa sembrava identica a quella gratuita. Ora la cosa costosa si scrive più lunga, che è un segnale di design deliberato.

Questo progetto segue già la regola — `APIClient.swift:14` scrive `private let session: any Session`, e `:12` scrive `@Sendable (Int) -> (any Swift.Error)?`.

### Primary associated type — SE-0346

Il problema: `any Collection` non ti dice nulla sul tipo degli elementi. Prima di 5.7 non avevi modo di dire "una collection di `Int`" senza generics completi.

Un protocol ora nomina alcuni dei suoi associated type come *primari*:

```swift
protocol Collection<Element>: Sequence {   // Element è primario
  associatedtype Element
}
```

e i chiamanti li vincolano posizionalmente:

```swift
func sum(_ xs: some Collection<Int>) -> Int { xs.reduce(0, +) }
func sumAny(_ xs: any Collection<Int>) -> Int { xs.reduce(0, +) }
```

[SE-0358](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0358-primary-associated-types-in-stdlib.md) li ha applicati retroattivamente a tutta la standard library — `Sequence<Element>`, `Collection<Element>`, `AsyncSequence<Element, Failure>` e così via. È il motivo per cui oggi puoi scrivere `some Collection<Int>` senza dichiarare nulla.

### Opaque parameter — SE-0341

`some` in posizione di parametro è puro zucchero sintattico, ma è zucchero che userai di continuo:

```swift
func f(_ xs: some Collection<Int>) -> Int { xs.count }

// è esattamente equivalente a:
func f<C: Collection<Int>>(_ xs: C) -> Int { xs.count }
```

Stesso codice, stessa performance, niente parentesi angolari. Usa la forma generica solo quando devi *nominare* il parametro di tipo — per esempio per vincolare due parametri allo stesso tipo, cosa che la forma `some` non può esprimere.

### Existential aperti implicitamente — SE-0352

È quello silenzioso che tiene insieme tutto il resto. Dato un valore di tipo existential, il compilatore può ora "aprirlo" per chiamare una funzione generica:

```swift
protocol Shape { func area() -> Double }

func areaOf<S: Shape>(_ s: S) -> Double { s.area() }

func use(_ s: any Shape) -> Double {
  areaOf(s)   // ✅ Swift 5.7+: il compilatore apre la scatola e lega S al tipo dinamico
}
```

Prima di 5.7 era un errore, e il workaround era un metodo in protocol extension che esisteva solo per rimbalzare la chiamata. Ora il compilatore inserisce l'apertura automaticamente al call site.

Il limite: il tipo aperto esiste solo per la durata di quella chiamata. Non puoi restituirlo, perché non c'è modo di nominarlo nel tipo di ritorno.

### Existential per tutti i protocol — SE-0309

Infine: `any` ora funziona per protocol con associated type e requisiti su `Self`. Dove il tipo di un membro dipenderebbe dal tipo cancellato, quel membro non è disponibile attraverso l'existential — il compilatore ti dice quale. Tutto il resto è utilizzabile.

## 4. Dove atterra in questo codebase

L'SDK ha fatto una scelta architetturale interessante che vale la pena esaminare con questa lente.

**`Pokespeare` è una struct di closure, non un protocol.** `Pokespeare.swift:3-5`:

```swift
public struct Pokespeare: Sendable {
  private var _description: @Sendable (_ name: String) async throws -> String
  private var _sprite: @Sendable (_ name: String) async throws -> URL
}
```

Il README spiega la motivazione: sostituzione nei test senza protocol da dichiarare e senza mock class da mantenere. Chiediti quanto sarebbe costata l'alternativa. `protocol PokespeareProtocol` + `any PokespeareProtocol` tenuto nel view model significa una scatola existential e dispatch via witness table a ogni chiamata — più una dichiarazione di protocol, più una mock class per test target. La struct di closure non ha né l'una né l'altra. È una buona decisione, e ora sai articolarne il *perché* in termini di ABI.

**Dove si usano existential, si usano correttamente.** `APIClient.swift:14` — `private let session: any Session` — è un `any` legittimo: il tipo concreto varia davvero (`URLSession` reale in produzione, `MockedSession` nei test), ed è memorizzato, non solo passato. `Session` non è vincolato a classi (`Session.swift:3` — `protocol Session: Sendable`), quindi è un opaque existential container. `URLSession` è una classe, quindi il buffer contiene un singolo puntatore e sta inline.

**Dove manca lo zucchero.** `APIClient.swift:32`:

```swift
func perform<R: HTTPCodableRequest>(_ request: R) async throws -> R.ResponseType
```

Questa *deve* restare generica — il tipo di ritorno `R.ResponseType` nomina il parametro di tipo, cosa che `some` non può fare. Buon istinto controllarla, candidato sbagliato. Cerca invece funzioni che prendono un parametro generico e non lo nominano mai più.

**Un buco da notare.** `HTTPCodableRequest` ha un `ResponseType` associato ma non dichiara alcun primary associated type. Se lo facesse — `protocol HTTPCodableRequest<ResponseType>` — potresti scrivere `any HTTPCodableRequest<PokemonDetailResponse>`, il che renderebbe esprimibili certi helper di test.

## 5. Esercizio

**Obiettivo:** sentire la differenza tra `some` e `any` in questo codebase, e aggiungere un primary associated type dove se lo guadagna.

### 5a — Misura l'existential

In un file di scarto (non nel progetto), scrivi due versioni di una piccola funzione: una che prende `some Session`, una che prende `any Session`. Leggi il SIL generato per entrambe e trova la differenza:

```bash
xcrun swiftc -emit-sil -O tuofile.swift | swift demangle | less
```

Cerca `open_existential_addr` / `witness_method` nella versione `any`, e la loro assenza nella versione `some`. **Scrivi cosa hai visto** — è il tipo di cosa che si fissa solo dopo averla vista nell'IR.

### 5b — Aggiungi un primary associated type

Dai a `HTTPCodableRequest` un primary associated type per la sua risposta:

```swift
protocol HTTPCodableRequest<ResponseType>: HTTPRequest { … }
```

**Criteri di accettazione.**

1. Tutto compila ancora e i 53 test SDK passano.
2. In `Pokespeare/Tests/`, scrivi un nuovo test che usa la forma existential vincolata — `any HTTPCodableRequest<PokemonDetailResponse>` — per contenere una request il cui tipo concreto non è noto staticamente. Se non trovi un uso naturale, **è un risultato valido**: scrivilo come "primary associated type non giustificato qui" e fai marcia indietro. Sapere quando *non* usare una feature è la metà più difficile.
3. `swiftlint lint --strict` pulito.

```bash
xcodebuild test -scheme Pokespeare -destination 'platform=iOS Simulator,name=iPhone 17 Pro'
```

### 5c — Applica gli opaque parameter

Trova almeno una funzione nell'SDK il cui parametro generico è dichiarato e poi mai più nominato, e convertila alla forma `some`. Verifica che i test passino ancora. Se non ce ne sono, dillo — il codebase è piccolo e potrebbe genuinamente non averne.

## 6. Trappole

- **`any` in un loop caldo.** `[any Shape]` dove i valori `Shape` superano 3 word significa un'allocazione heap per elemento. Profila prima di dare per scontato, ma conosci il meccanismo.
- **`some` in posizione di ritorno vuole un unico tipo concreto.** Ramificare su una condizione a runtime per restituire tipi diversi richiede `any`, o un enum, o `@ViewBuilder` se è SwiftUI (che non è né l'uno né l'altro — costruisce un `TupleView`/`_ConditionalContent` con il ramo codificato nel *tipo*).
- **Gli existential aperti non possono uscire.** Puoi passare un valore aperto a una funzione generica; non puoi restituirlo o memorizzarlo.
- **`some` in posizione di parametro non può esprimere relazioni.** Due parametri `some Collection` sono due tipi *indipendenti*. Se devono coincidere, usa generics espliciti.
- **Il `some View` di SwiftUI è la stessa feature.** `body: some View` è un tipo opaco, ed è il motivo per cui l'enorme tipo generico annidato di una gerarchia di view non va mai scritto. Capirlo spiega perché un `if`/`else` nel body di una view cambia il *tipo*, quindi l'identità, quindi azzera lo stato.

3. `func f(_ x: some P)` e `func f<T: P>(_ x: T)` — sono diversi a runtime? C'è qualcosa che il secondo può esprimere e il primo no?
