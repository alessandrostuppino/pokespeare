# WWDC22 · Module 3 — Concurrency Foundations: `Sendable`, Checking Levels, and `Clock`

**Swift 5.6 / 5.7** · [SE-0302](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0302-concurrent-value-and-concurrent-closures.md), [SE-0337](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0337-support-incremental-migration-to-concurrency-checking.md), [SE-0338](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0338-clarify-execution-non-actor-async.md), [SE-0329](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0329-clock-instant-duration.md)

> This module is the foundation Batch 3 (Swift 6 data-race safety) and Batch 4 (approachable concurrency) both build on. Read it properly even though the project already uses most of it — the *why* underneath is what makes those later batches make sense.

---

## 1. What shipped, and what problem it solves

Swift 5.5 (WWDC21) gave us `async`/`await`, `Task`, and actors. But it shipped with a hole: the compiler could not check that the values you passed *between* concurrency domains were safe to pass. You could hand a mutable class instance to a detached task and race against yourself, with no diagnostic.

WWDC22's contribution is the **checking machinery**:

- **`Sendable`** ([SE-0302](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0302-concurrent-value-and-concurrent-closures.md)) — a marker protocol meaning "safe to move across isolation boundaries."
- **Staged checking** ([SE-0337](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0337-support-incremental-migration-to-concurrency-checking.md)) — because turning full checking on at once would have broken every codebase in existence, so it arrived as a dial.
- **Defined execution semantics for nonisolated async functions** ([SE-0338](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0338-clarify-execution-non-actor-async.md)) — which thread does an `async` function that belongs to no actor actually run on?

Plus, separately but landing in the same release: **`Clock`, `Instant`, `Duration`** ([SE-0329](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0329-clock-instant-duration.md)) — a real time abstraction to replace `UInt64` nanoseconds.

## 2. How it actually works

### `Sendable` is a marker protocol

`Sendable` has **no requirements** — no methods, no properties. It is a *marker*: it exists only so the compiler can check it, and it is erased before code generation. There is no witness table, no runtime representation, no cost.

What the compiler checks:

| Type | `Sendable`? |
|---|---|
| `struct`/`enum` with all-`Sendable` stored properties | ✅ **inferred automatically** (if not public — see below) |
| `actor` | ✅ always — that is what an actor is for |
| `final class` with only immutable `Sendable` stored properties | ✅ if you declare the conformance |
| non-`final` class | ❌ — a subclass could add mutable state |
| class with `var` stored properties | ❌ unless protected by isolation |
| `@MainActor`-isolated class | ✅ — isolation *is* the protection |
| function types | ✅ only when marked `@Sendable` |

**The public-type gotcha.** Automatic inference for structs and enums stops at module boundaries: a `public` struct does *not* get an inferred `Sendable` conformance, because adding one later would be a source-compatible promise you had not made. You must declare it. This is why `Pokespeare.swift:3` writes it explicitly:

```swift
public struct Pokespeare: Sendable { … }
```

### `@Sendable` closures

A closure crossing an isolation boundary must be `@Sendable`, which imposes two rules: everything it captures must itself be `Sendable`, and it cannot capture anything mutably (no `inout`, no mutation of captured `var`s).

This project uses `@Sendable` closures as its *primary architectural device* — `Pokespeare.swift:4-5`:

```swift
private var _description: @Sendable (_ name: String) async throws -> String
private var _sprite: @Sendable (_ name: String) async throws -> URL
```

That is what makes `struct Pokespeare: Sendable` legal despite storing closures.

### The escape hatch, and its price

`@unchecked Sendable` tells the compiler "trust me." It is a promise, not a proof — you have taken responsibility for the synchronization by hand.

This project uses it exactly twice, both in test code: `MockedSession.swift:5` and the `RequestBox` at `:104`. That is the right density. Two `@unchecked` in test doubles is a considered decision; twenty across production code is a codebase that turned the compiler off.

When you write one, write a comment saying *what* provides the safety. "It's fine" is not a reason. "All mutation happens under `lock`, and `lock` is never held across a suspension" is.

### The checking dial — SE-0337

Three levels, historically reached via `-strict-concurrency=`:

| Level | Behaviour |
|---|---|
| `minimal` | Only checks what is explicitly marked. The Swift 5 default. |
| `targeted` | Checks code that has already adopted concurrency (async functions, actors), leaves the rest alone. |
| `complete` | Checks everything. This is what Swift 6 language mode enforces as **errors** rather than warnings. |

The intended migration path is `minimal` → `targeted` → `complete` as warnings → flip to Swift 6 mode, where they become errors.

**This project is already at the end of that path.** `Package.swift:1` declares `swift-tools-version: 6.0` and the app sets `SWIFT_VERSION = 6.0`, so both compile under complete checking with errors. There is nothing to migrate — which is exactly why Batch 3 can spend its time on the *interesting* parts (region-based isolation, `sending`) instead of on migration mechanics.

One thing to notice: `Package.swift` has **no `swiftSettings` at all**. Swift 6 mode is inherited purely from the tools version. In Batch 3 you will make that explicit and add upcoming-feature flags.

### SE-0338 — where does a nonisolated `async` function run?

This is the one people get wrong, and it is load-bearing for Batch 4.

```swift
@MainActor
func caller() async {
  await work()      // where does work() run?
}

nonisolated func work() async -> Int { 42 }
```

**Under SE-0338 (the WWDC22 rule):** `work()` does **not** inherit the caller's actor. It hops to the **global concurrent executor** — a cooperative thread pool. So calling it from `@MainActor` code means: leave the main actor, run on a pool thread, hop back.

The reasoning was sound — a nonisolated async function should not silently block a caller's actor. But the consequence was a great deal of unnecessary hopping, and a category of bug where developers assumed their code stayed on the main actor and it did not.

**Swift 6.2 reverses this default** via [SE-0461](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0461-async-function-isolation.md): nonisolated async functions now run *on the caller's actor*, and the new `@concurrent` attribute is the explicit opt-in to the old behaviour. Batch 4 covers it in full.

Hold both models in your head. Code written between 2022 and 2025 assumes the first; code written now assumes the second; and which one applies depends on a language-mode flag.

### `Clock`, `Instant`, `Duration` — SE-0329

Before this, you slept with `Task.sleep(nanoseconds: 300_000_000)` and counted zeros.

**`Duration`** is an amount of time, stored as 128 bits — seconds plus attoseconds — so it does not lose precision the way a `Double` of seconds does. All of these are verified to compile:

```swift
let base: Duration = .milliseconds(300)
base * 4                  // Duration × Int
base * 1.5                // Duration × Double
base + .seconds(1)
base / 2
base < .seconds(1)        // Comparable
base.components           // (seconds: Int64, attoseconds: Int64)
```

**`Clock`** is a protocol with two standard implementations, and the difference matters:

| Clock | Behaviour while the device is asleep |
|---|---|
| `ContinuousClock` | Keeps counting. "Wall time elapsed." |
| `SuspendingClock` | Pauses. "Time the process was actually running." |

For a network retry backoff you want `ContinuousClock` — if the user's phone slept for 30 seconds, that time really did pass as far as the server is concerned. `Task.sleep(for:)` uses `ContinuousClock` by default.

`Clock` also gives you `measure`, which is the honest way to time async work:

```swift
let elapsed = try await ContinuousClock().measure {
  try await someWork()
}
```

**Why `Clock` being a protocol matters:** it is a seam. A custom `Clock` conformance lets a test drive time forward instantly instead of actually sleeping. Keep that in mind for the exercise.

## 4. Where it lands in this codebase

This is the area the project already does well, so read it as a worked example rather than a list of defects.

**The `Sendable` surface.** `Pokespeare.swift:3` (`public struct Pokespeare: Sendable`), `APIClient.swift:9`, `RetryPolicy.swift:4`, `PokemonManager.swift:3`, `TranslationManager.swift:3`, and `Session.swift:3` — `protocol Session: Sendable`, which is what lets `any Session` be stored in a `Sendable` struct at `APIClient.swift:14`.

**`@MainActor` where it belongs.** `SearchViewModel.swift:5`. The audit's finding **C-02** is the story of what happens without it: the class was `@Observable` but not isolated, a detached `Task` mutated UI state and a non-`Sendable` `ModelContext` from a background thread, and it *compiled* — because the app target was still on `SWIFT_VERSION = 5.0`. The data race was real; the checking was off. That is the single most valuable thing this repository can teach you about Swift 6 mode, and it happened here.

**`Duration` used properly.** `RetryPolicy.swift:9,42`:

```swift
var baseDelay: Duration
func delay(forAttempt attempt: Int) -> Duration {
  baseDelay * (1 << attempt)          // 300ms, 600ms, 1200ms
}
```

and consumed at `APIClient.swift:40`:

```swift
try await Task.sleep(for: retryPolicy.delay(forAttempt: attempt))
```

Note the comment above that line — `Task.sleep` **throws on cancellation**, which is precisely the desired behaviour: a cancelled search must abandon its backoff rather than finish sleeping first. That is a subtle correctness property expressed for free by using the right API.

**The gap: the clock is not injectable.** `RetryPolicy` deals in `Duration` but `APIClient` calls `Task.sleep` directly. So the retry tests in `RetryTests.swift` either really sleep, or test the policy's arithmetic without testing the loop that uses it. `HANDOFF.md` lists "instrumenting the retry numbers" as unfinished work. This is the exercise.

## 5. Exercise

**Goal:** make time injectable, so the retry loop can be tested without real sleeping.

### 5a — Read before you write

Read `APIClient.swift:32-45` and `RetryPolicy.swift` in full, then `Pokespeare/Tests/PokespeareTests/RetryTests.swift`. Answer for yourself, in writing:

- Which of the 7 retry tests actually exercise the `while true` loop in `perform`, and which only test `RetryPolicy`'s arithmetic in isolation?
- How long does the SDK suite take today? Measure it. Some of that is real backoff sleeping.

### 5b — Inject the clock

Give `APIClient` a clock dependency, defaulting to `ContinuousClock()`, and route the backoff sleep through it instead of calling `Task.sleep(for:)` directly.

Design constraints to respect:

- `APIClient` is `Sendable` (`:9`) and must stay that way — so whatever you inject must be `Sendable` too.
- The SDK is not `@MainActor` anywhere. Keep it that way.
- Do not break the cancellation property. A cancelled task must still abandon the wait. Verify this, do not assume it.
- The public surface must not change. `Pokespeare`, `Pokespeare.Error`, `PokemonView`, `PokemonViewModel` are the whole public API (see `README.md`) and this is an internal refactor.

### 5c — Test with it

Write a test clock and use it to assert something the current tests cannot: that three attempts against a `500` response produce delays of exactly 300ms, then 600ms — without the test taking 900ms.

**Acceptance criteria.**

1. A new test asserts the actual backoff *sequence*, not just the policy's arithmetic.
2. The SDK suite gets measurably faster. Record both numbers.
3. Cancellation still works: a test proves a cancelled request stops during backoff rather than completing it.
4. All 53 SDK tests pass; the 18 app tests are untouched and pass.
5. `swiftlint lint --strict` clean.
6. The public API is byte-for-byte unchanged.

```bash
xcodebuild test -scheme Pokespeare -destination 'platform=iOS Simulator,name=iPhone 17 Pro'
```

**Hint, not a solution.** There are at least two designs: conform a test type to `Clock`, or inject a narrower `@Sendable (Duration) async throws -> Void` sleep closure. The second is smaller and matches the struct-of-closures idiom this SDK already uses everywhere. The first is more conventional and gives you `measure` for free. Pick one, then write down the argument against the one you rejected — that is the part that teaches.

## 6. Pitfalls

- **`public` structs do not infer `Sendable`.** Cross-module inference is deliberately off. Declare it.
- **`@unchecked Sendable` is a promise you must be able to state.** If you cannot name the mechanism providing safety, you do not have one.
- **A `@MainActor` class is `Sendable`;** the isolation is the proof. This is why `SearchViewModel` needs no `Sendable` annotation.
- **Nonisolated `async` did not inherit the caller's actor** before Swift 6.2. Every blog post, sample, and Stack Overflow answer from 2022–2025 assumes the old rule. Check the date on anything you read.
- **`SuspendingClock` for a network backoff is wrong.** Device sleep does not pause the server's rate limiter.
- **`Task.sleep` throwing on cancellation is a feature.** Swallowing that error with `try?` silently converts "abandon the retry" into "finish the wait, then continue."
- **`Duration` is not `Double` seconds.** Do not round-trip through `TimeInterval` to do arithmetic — you will lose precision the type exists to preserve.
