## 1. What shipped, and what problem it solves

Before Swift 5.7, generics and protocols had a usability cliff. Two symptoms everyone hit:

**"Protocol can only be used as a generic constraint."** The moment a protocol had an associated type, you could not write it as a type. `any Collection` was illegal. Your options were a type eraser you hand-wrote, or restructuring the whole call site around generics.

**`some` and `any` looked identical but weren't.** Both spelled as a bare protocol name — `func f(_ x: Shape)` — even though one is a compile-time-resolved concrete type and the other is a runtime box. Beginners could not tell them apart because the syntax gave them nothing to tell apart.

Swift 5.7 fixed both, plus the ergonomics around them. The through-line: **make the distinction between "one specific type, chosen by the caller" and "any type, decided at runtime" visible in the source, then remove the artificial restrictions on the second one.**

## 2. How it actually works

This is the section that matters. If you only remember one thing from this module, make it the layout diagram.

### `some` — opaque types, resolved at compile time

```swift
func makeShape() -> some Shape { Circle() }
```

`some Shape` means: *there is exactly one concrete type here, the compiler knows it, the caller does not.* The caller learns "this conforms to `Shape`" and nothing more.

Because the type is known at compile time, the compiler can **specialize**: it emits a version of the function with `Circle` baked in. Method calls are direct, the value is stored inline, no boxing, no indirection. The cost of `some` at runtime is *zero* — it is an information-hiding tool, not a performance tool.

The rule that trips people: a function returning `some Shape` must return **the same** concrete type on every path. This does not compile:

```swift
func makeShape(circular: Bool) -> some Shape {
  circular ? Circle() : Square()   // ❌ two different concrete types
}
```

### `any` — existentials, resolved at runtime

```swift
let shapes: [any Shape] = [Circle(), Square()]
```

`any Shape` means: *some type conforming to `Shape`, possibly different for each value, decided at runtime.* The heterogeneous array above is only possible with `any`.

This costs something, and the cost is precisely specified in Swift's ABI documentation. From [the official type layout document](https://github.com/swiftlang/swift/blob/main/docs/ABI/TypeLayout.rst):

> If there is no class constraint on a protocol or protocol composition type, the existential container has to accommodate a value of arbitrary size and alignment. It does this using a **fixed-size buffer**, which is three pointers in size and pointer-aligned.

The layout, quoted from that same document:

```c
struct OpaqueExistentialContainer {
  void *fixedSizeBuffer[3];              // 24 bytes on 64-bit
  Metadata *type;                         // what type is actually in there
  WitnessTable *witnessTables[NUM_WITNESS_TABLES];  // how to call its methods
};
```

Read that carefully, because three consequences fall straight out of it:

1. **Values ≤ 3 words fit inline.** A `struct Point { var x, y: Double }` is 2 words — it lives directly in the buffer. Free.
2. **Values > 3 words get heap-allocated.** A struct with four `Double`s does not fit, so the existential stores a pointer to a **side allocation**. Putting one in an array means one heap allocation *per element*. This is the hidden cost of `[any Shape]`.
3. **Method calls go through a witness table.** Not a direct call, not even a vtable — a table of function pointers looked up by protocol conformance. Not free, and not inlinable across the boundary.

There is a cheaper case, also from the ABI doc: if a protocol is class-constrained (`protocol P: AnyObject`), the compiler uses a `ClassExistentialContainer` — a single pointer, since class instances are already one pointer and already carry their own metadata. No fixed-size buffer, no side allocation.

**The rule of thumb:** reach for `some` by default. Reach for `any` when you genuinely need heterogeneity or runtime-varying types — and know that you are paying for it.

### Why `any` became mandatory

[SE-0335](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0335-existential-any.md) made the keyword required (in Swift 6 language mode; a warning before that). The motivation is exactly the confusion above: the expensive thing looked identical to the free thing. Now the expensive thing is spelled longer, which is a deliberate design signal.

This project already follows the rule — `APIClient.swift:14` writes `private let session: any Session`, and `:12` writes `@Sendable (Int) -> (any Swift.Error)?`.

### Primary associated types — SE-0346

The problem: `any Collection` tells you nothing about the element type. Before 5.7 you had no way to say "a collection of `Int`" without full generics.

A protocol now nominates some of its associated types as *primary*:

```swift
protocol Collection<Element>: Sequence {   // Element is primary
  associatedtype Element
}
```

and callers constrain them positionally:

```swift
func sum(_ xs: some Collection<Int>) -> Int { xs.reduce(0, +) }
func sumAny(_ xs: any Collection<Int>) -> Int { xs.reduce(0, +) }
```

[SE-0358](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0358-primary-associated-types-in-stdlib.md) retrofitted these across the standard library — `Sequence<Element>`, `Collection<Element>`, `AsyncSequence<Element, Failure>`, and so on. This is why you can write `some Collection<Int>` today without declaring anything.

### Opaque parameters — SE-0341

`some` in parameter position is pure sugar, but it is sugar you will use constantly:

```swift
func f(_ xs: some Collection<Int>) -> Int { xs.count }

// is exactly equivalent to:
func f<C: Collection<Int>>(_ xs: C) -> Int { xs.count }
```

Same code, same performance, no angle brackets. Use the generic form only when you need to *name* the type parameter — for example to constrain two parameters to the same type, which the `some` form cannot express.

### Implicitly opened existentials — SE-0352

This is the quiet one that makes the whole thing hang together. Given a value of existential type, the compiler can now "open" it to call a generic function:

```swift
protocol Shape { func area() -> Double }

func areaOf<S: Shape>(_ s: S) -> Double { s.area() }

func use(_ s: any Shape) -> Double {
  areaOf(s)   // ✅ Swift 5.7+: compiler opens the box and binds S to the dynamic type
}
```

Before 5.7 this was an error, and the workaround was a protocol extension method that existed purely to bounce the call. The compiler now inserts the open automatically at the call site.

The limit: the opened type only exists for the duration of that call. You cannot return it, because there is no way to name it in the return type.

### Unlocking existentials for all protocols — SE-0309

Finally: `any` now works for protocols with associated types and `Self` requirements. Where a member's type would depend on the erased type, that member is unavailable through the existential — the compiler tells you which. Everything else is usable.

## 4. Where it lands in this codebase

The SDK made an interesting architectural choice that is worth examining through this lens.

**`Pokespeare` is a struct of closures, not a protocol.** `Pokespeare.swift:3-5`:

```swift
public struct Pokespeare: Sendable {
  private var _description: @Sendable (_ name: String) async throws -> String
  private var _sprite: @Sendable (_ name: String) async throws -> URL
}
```

The README explains the motivation: substitution in tests with no protocol to declare and no mock class to maintain. Ask yourself what the alternative would have cost. `protocol PokespeareProtocol` + `any PokespeareProtocol` stored in the view model means an existential box and witness-table dispatch on every call — plus a protocol declaration, plus a mock class per test target. The closure struct has neither. This is a good decision, and now you can articulate *why* in ABI terms.

**Where existentials are used, they are used correctly.** `APIClient.swift:14` — `private let session: any Session` — is a legitimate `any`: the concrete type genuinely varies (real `URLSession` in production, `MockedSession` in tests), and it is stored, not just passed. `Session` is not class-constrained (`Session.swift:3` — `protocol Session: Sendable`), so this is an opaque existential container. `URLSession` is a class, so the buffer holds a single pointer and fits inline.

**Where the sugar is missing.** `APIClient.swift:32`:

```swift
func perform<R: HTTPCodableRequest>(_ request: R) async throws -> R.ResponseType
```

This one *must* stay generic — the return type `R.ResponseType` names the type parameter, which `some` cannot do. Good instinct to check, wrong candidate. Look instead for functions that take a generic parameter and never name it again.

**A gap worth noticing.** `HTTPCodableRequest` has an associated `ResponseType` but declares no primary associated type. If it did — `protocol HTTPCodableRequest<ResponseType>` — you could write `any HTTPCodableRequest<PokemonDetailResponse>`, which would make certain test helpers expressible.

## 6. Pitfalls

- **`any` in a hot loop.** `[any Shape]` where `Shape` values exceed 3 words means one heap allocation per element. Profile before assuming, but know the mechanism.
- **`some` in return position needs a single concrete type.** Branching on a runtime condition to return different types requires `any`, or an enum, or `@ViewBuilder` if it is SwiftUI (which is neither — it builds a `TupleView`/`_ConditionalContent` with the branch encoded in the *type*).
- **Opened existentials cannot escape.** You can pass an opened value into a generic function; you cannot return it or store it.
- **`some` in parameter position cannot express relationships.** Two `some Collection` parameters are two *independent* types. If you need them to match, use explicit generics.
- **SwiftUI's `some View` is the same feature.** `body: some View` is an opaque type, which is why the enormous nested generic type of a view hierarchy never has to be spelled. Understanding this explains why `if`/`else` in a view body changes the *type*, and therefore the identity, and therefore resets state.
