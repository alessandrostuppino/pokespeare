# WWDC22 · Modulo 2 — Regex ed elaborazione di stringhe

**Swift 5.7** · [SE-0350](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0350-regex-type-overview.md), [SE-0351](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0351-regex-builder.md), [SE-0354](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0354-regex-literals.md), [SE-0355](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0355-regex-syntax-run-time-construction.md), [SE-0357](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0357-algorithms-string-processing.md), [SE-0363](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0363-unicode-for-string-processing.md)

> Ogni frammento di questo documento è stato verificato col typechecker contro l'SDK iOS 26.4 in Swift 6 language mode prima di essere scritto.

## 1. Cosa è uscito, e quale problema risolve

Swift è uscito senza espressioni regolari native per otto anni. Quello che avevi era `NSRegularExpression`: una classe di Foundation, inizializzata da un pattern `String`, che lanciava a runtime se il pattern era malformato, e restituiva valori `NSRange` da riconvertire in `String.Index` — una conversione genuinamente facile da sbagliare, perché `NSRange` conta code unit UTF-16 e `String.Index` non conta nulla di semplice.

Swift 5.7 ha rilasciato un pacchetto di sei proposte che sostituisce tutto questo:

- Un **tipo `Regex`**, generico su ciò che cattura, così le catture sono *tipizzate* invece che indicizzate per stringa.
- **Literal** — `/pattern/` — parsati e validati **a compile-time**. Un pattern malformato è ora un errore di build.
- Un **DSL result-builder** (`RegexBuilder`) per pattern che hanno superato la leggibilità di una riga sola.
- **Algoritmi su stringhe** costruiti sopra: `split`, `replacing`, `trimmingPrefix`, `ranges(of:)`, `contains`.
- **Semantica di matching corretta per Unicode**, con un interruttore esplicito tra livello grapheme cluster e Unicode scalar.

Il cambiamento principale è la validazione a compile-time. Un refuso in un pattern `NSRegularExpression` arriva agli utenti. Un refuso in un literal `/…/` fa fallire la build.

## 2. Come funziona davvero

### Il tipo porta le catture

```swift
let r = /(\d+)-(\d+)/
// r: Regex<(Substring, Substring, Substring)>
```

`Regex` è generico sul suo `Output`. Senza catture, `Output` è `Substring` — l'intero match. Con *n* gruppi di cattura, `Output` è una tupla di *(n+1)* elementi: prima il match intero, poi ogni gruppo. Il compilatore ricava quella tupla **parsando il literal a compile-time**.

Ecco perché questo è sicuro:

```swift
guard let m = s.firstMatch(of: /(\d+)/) else { return nil }
return Int(m.1)          // m.1 è Substring — noto staticamente come esistente
```

Non esiste un fallimento a runtime del tipo "il gruppo 3 non esiste", perché il gruppo 3 non passa il typecheck.

Le catture nominate diventano etichette di tupla:

```swift
guard let m = s.wholeMatch(of: /(?<key>\w+)=(?<value>\w+)/) else { return nil }
return (String(m.key), String(m.value))     // ✅ nominate, non posizionali
```

### Tre modi per costruirne una, e quando usarli

**Literal** — validato a compile-time, costo zero a runtime per costruirlo, catture tipizzate. Scelta di default.

```swift
s.wholeMatch(of: /[a-z][a-z\-']{1,29}/)
```

**DSL builder** — per pattern che altrimenti un lettore dovrebbe decifrare:

```swift
import RegexBuilder

let pattern = Regex {
  Anchor.startOfSubject
  CharacterClass("a"..."z")
  Repeat(1...29) {
    CharacterClass.anyOf("-'").union(CharacterClass("a"..."z"))
  }
  Anchor.endOfSubject
}
```

Più verboso, ma diffabile, commentabile e componibile — puoi estrarre un sotto-pattern in un `let` e riusarlo. Il DSL è un result builder, esattamente come il `body` di SwiftUI.

**Stringa a runtime** — quando il pattern davvero non è noto fino a runtime (ricerca fornita dall'utente, file di configurazione):

```swift
func runtime(_ pattern: String) throws -> Regex<AnyRegexOutput> {
  try Regex(pattern)     // throws — è l'unica forma che può fallire a runtime
}
```

Nota il tipo `Output`: `AnyRegexOutput`. Il compilatore non può conoscere la forma delle catture, quindi torni all'accesso dinamico. Questa è la via di fuga, e deve sembrarlo.

### Semantica di matching: la parte Unicode che tutti saltano

Di default Swift fa matching a livello di **grapheme cluster** — lo stesso livello su cui itera `String`. `.` corrisponde a un carattere percepito dall'utente, quindi corrisponde a `🇮🇹` come una cosa sola, e a `e` + accento combinante come una cosa sola.

`NSRegularExpression` fa matching su code unit UTF-16. È una differenza di comportamento reale, non un dettaglio. Se stai portando un pattern e i risultati differiscono su input non ASCII, il motivo è questo.

Puoi passare al matching a livello di scalar con `.matchingSemantics(.unicodeScalar)` ([SE-0363](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0363-unicode-for-string-processing.md)).

Le opzioni si applicano come metodi sulla regex, non come flag nel pattern:

```swift
let ci = /pikachu/.ignoresCase()
```

### Gli algoritmi su stringhe

[SE-0357](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0357-algorithms-string-processing.md) ha generalizzato l'API di `String` così che tutto ciò che prende un separatore o un pattern prende un `RegexComponent`:

```swift
s.replacing(/\s+/, with: " ")     // comprime sequenze di spazi
s.split(separator: /,\s*/)        // divide su virgola con spazi opzionali
s.trimmingPrefix(/\s+/)           // toglie gli spazi iniziali
s.contains(/pikachu/.ignoresCase())
s.ranges(of: /a/)
```

Sono quelli a cui ricorrerai più spesso. La maggior parte dei momenti "mi serve una regex" è in realtà uno di questi cinque.

## 3. La trappola: `Regex` non è `Sendable`

Questo è verificato, non ricordato. Compilando questo in Swift 6 language mode:

```swift
let g = /[a-z]+/
nonisolated func fromNonisolated(_ s: String) -> Bool {
  s.wholeMatch(of: g) != nil
}
```

si ottiene:

```
error: main actor-isolated let 'g' can not be referenced from a nonisolated context
```

E esplicitamente:

```
error: type 'Regex<Substring>' does not conform to the 'Sendable' protocol
```

**Cosa sta succedendo.** `Regex` non è `Sendable`. In Swift 6, un `let` globale di tipo non `Sendable` non può essere accessibile globalmente senza isolamento, quindi il compilatore gli inferisce `@MainActor`. La dichiarazione compila benissimo — l'errore scatta solo nel punto in cui codice **nonisolated** lo tocca.

Quest'ultima parte conta, ed è il motivo per cui il bug si nasconde: la tua costante regex globale compila, e il tuo view model `@MainActor` la usa contento. Esplode solo il giorno in cui la referenzi da un helper `nonisolated` o da un task distaccato.

**Due fix, entrambi verificati che compilano:**

```swift
// A — costruiscila nel punto d'uso. Costruire da un literal è economico.
nonisolated func a(_ s: String) -> Bool {
  s.wholeMatch(of: /[a-z]+/) != nil
}

// B — una proprietà statica *calcolata*: una Regex nuova a ogni accesso, nessuno stato condiviso.
enum Patterns {
  static var name: Regex<Substring> { /[a-z]+/ }
}
nonisolated func b(_ s: String) -> Bool {
  s.wholeMatch(of: Patterns.name) != nil
}
```

Nota che B è `static var` con un getter, **non** `static let`. Un `static let` reintrodurrebbe esattamente il globale condiviso non `Sendable` a cui il compilatore si opponeva.

Questo conta direttamente per l'esercizio qui sotto, perché l'SDK non è `@MainActor` da nessuna parte.

## 5. Dove atterra in questo codebase

La validazione dell'input è fatta attualmente due volte, in due modi improvvisati diversi, e nessuno dei due dice cosa intende.

**`SearchViewModel.swift:87-89`** — un numero magico che fa due lavori:

```swift
var isSearchButtonVisible: Bool {
  searchText.count > 2
}
```

Questa singola espressione è *sia* "il bottone Search deve comparire" *sia* "questo input è valido" — viene riconsultata come guardia a `:140`. L'audit l'ha registrata come finding **C-20**. Due domande diverse che condividono una risposta sola è esattamente il modo in cui una regola di UI e una di validazione divergono più avanti.

**`SearchViewModel.swift:233-236`** — filtro dei caratteri via closure:

```swift
func searchTextDidChange() {
  let filtered = searchText.filter { $0.isLetter || $0.isWhitespace }
  searchText = filtered != searchText ? filtered : searchText
}
```

Questo permette `"   "` (solo spazi) e `"a"` (troppo corto) e rifiuta `"farfetch'd"`, `"ho-oh"` e `"mr. mime"` — tutti nomi di Pokémon reali. Il filtro è simultaneamente troppo permissivo e troppo restrittivo.

Una regex enuncia la regola vera in un posto solo, e la enuncia in una forma che un lettore può confrontare con la realtà.

## 7. Trappole

- **`Regex` non è `Sendable`.** Trattato sopra. Il fallimento compare nel punto d'*uso*, non nella dichiarazione, quindi si nasconde finché codice nonisolated non la tocca.
- **`static let` vs `static var` per i pattern.** In codice non `@MainActor`, solo la forma `var` calcolata è sicura.
- **Semantica grapheme vs scalar.** Swift usa i grapheme cluster di default; `NSRegularExpression` usa code unit UTF-16. I pattern portati possono cambiare comportamento silenziosamente su emoji, segni combinanti e bandiere.
- **Il literal `/…/` e l'operatore di divisione.** Il parser di Swift gestisce l'ambiguità, ma una `/` nuda dentro un literal va escapata. Per pattern con molte barre, usa la forma estesa `#/ … /#`.
- **`AnyRegexOutput` butta via la type safety** che è tutto il punto. Se ti ritrovi a usare `try Regex(String)` per un pattern che in realtà è una costante, usa un literal.
- **Non validare con una regex ciò che il server validerà comunque.** La validazione del nome lato client qui è un affordance di UX (fallisci subito, nessuna richiesta sprecata), non un confine di sicurezza. `Pokespeare.Error.pokemonNotFound` resta l'autorità.
