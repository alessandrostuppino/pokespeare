## 1. App Intents

### Cos'è, e perché ha sostituito ciò che c'era prima

**App Intents** è il modo in cui la tua app espone azioni al resto del sistema: Comandi rapidi, Siri, Spotlight, il tasto Azione, i widget e (da iOS 18) Apple Intelligence.

Ha sostituito SiriKit Intents, e la differenza non è cosmetica. SiriKit richiedeva un file `.intentdefinition`, un generatore di codice e un target di app extension separato. App Intents è **puro Swift nel target dell'app** — una conformance a un protocol, e l'integrazione è tutta lì.

```swift
import AppIntents

struct ShowPokemonIntent: AppIntent {
  static let title: LocalizedStringResource = "Show Pokémon"
  static let openAppWhenRun = true

  @Parameter(title: "Name")
  var name: String

  func perform() async throws -> some IntentResult & ProvidesDialog {
    .result(dialog: "Showing \(name)")
  }
}
```

Tre cose da notare:

- **`title` è un `LocalizedStringResource`,** non una `String`. È il tipo che il Batch 2 tratta come si deve — rimanda la localizzazione al momento della *visualizzazione* invece di risolverla alla costruzione. Il sistema ne ha bisogno, perché potrebbe mostrare il nome del tuo intent in Comandi rapidi sotto un locale in cui la tua app non sta girando. L'abitudine di questo progetto di pre-risolvere `String(localized:)` all'init (`SearchViewModel.swift:40-56`) sarebbe qui attivamente sbagliata.
- **`perform()` è `async throws`** e restituisce un tipo di risultato composto da protocol — `ProvidesDialog`, `ReturnsValue`, `ShowsSnippetView` e così via, mescolati secondo necessità.
- **`@Parameter`** fa comparire la proprietà come campo modificabile nell'editor di Comandi rapidi, con un controllo adatto al tipo, gratis.

`AppShortcutsProvider` pubblica gli intent che devono essere disponibili senza alcuna configurazione da parte dell'utente:

```swift
struct Shortcuts: AppShortcutsProvider {
  static var appShortcuts: [AppShortcut] {
    AppShortcut(
      intent: ShowPokemonIntent(),
      phrases: ["Show \(.applicationName)"],
      shortTitle: "Show",
      systemImageName: "sparkles"
    )
  }
}
```

Le frasi devono interpolare `\(.applicationName)` — il sistema richiede il nome della tua app nella frase così gli utenti non possono collidere con i comandi di altre app.

### Perché a questo progetto dovrebbe interessare

App Intents è il consumatore naturale del lavoro di navigazione del Modulo 4. "Hey Siri, mostra Pikachu in PokéSpeare" ha bisogno di un posto *dove* navigare — cioè di un path da assegnare, che la presentazione basata su sheet non ha. Fai prima il Modulo 4.

**Batch successivi:** widget interattivi guidati da intent (WWDC23), Control Widget e integrazione con Apple Intelligence (WWDC24), integrazione Spotlight (WWDC25).

## 2. Swift Charts

Un framework di grafici dichiarativo costruito sulla stessa macchina di layout e result builder di SwiftUI.

```swift
Chart(data) { p in
  BarMark(x: .value("Day", p.day), y: .value("Count", p.count))
    .foregroundStyle(by: .value("Day", p.day))
}
.chartXAxis { AxisMarks() }
```

Il modello mentale è la **grammatica dei grafici**: non configuri un oggetto grafico, descrivi mark e le dimensioni dei dati che codificano. `BarMark`, `LineMark`, `PointMark`, `AreaMark`, `RuleMark`, `RectangleMark`, `SectorMark` (iOS 17). `.value("Label", keyPath)` è un *valore plottabile* — la stringa è l'etichetta dell'asse e la voce di legenda, quindi è visibile all'utente e va localizzata.

`.foregroundStyle(by:)`, `.symbol(by:)` e `.lineStyle(by:)` creano una divisione in serie *e* una legenda automaticamente.

**L'accessibilità non è gratis.** I grafici generano una rappresentazione audio-graph, ma solo se i tuoi dati sono `Identifiable` e fornisci `.accessibilityLabel`/`.accessibilityValue` sui mark. Dato il lavoro di accessibilità già fatto in questo progetto (commit `9f787fc`), non far regredire lo standard aggiungendo un grafico senza etichette.

**Batch successivi:** `SectorMark` e grafici scrollabili (WWDC23), plotting di funzioni (WWDC24), grafici 3D (WWDC25).

## 3. Widget da lock screen

WidgetKit è uscito a WWDC20; WWDC22 ha aggiunto le **famiglie accessory** per la schermata di blocco e, più tardi, le complicazioni di Watch e le superfici della Dynamic Island:

```swift
StaticConfiguration(kind: "w", provider: P()) { _ in Text("x") }
  .supportedFamilies([.accessoryCircular, .accessoryRectangular, .accessoryInline, .systemSmall])
```

Le famiglie accessory rendono in una modalità di rendering vincolata e **desaturata** — ottieni forma e gerarchia, non colore. Progetta per quello: `.widgetAccentable()` marca le parti che devono prendere la tinta d'accento.

Il modello `TimelineProvider` è la parte che vale la pena capire, perché non assomiglia al normale codice di app. Non aggiorni un widget; consegni al sistema una **timeline** di entry future pre-renderizzate più una `TimelinePolicy` per quando richiederti (`.atEnd`, `.after(date)`, `.never`). Il sistema decide quando ricaricare davvero, soggetto a un budget. Non puoi forzare un refresh su una cadenza che scegli tu — `WidgetCenter.shared.reloadTimelines(ofKind:)` è una richiesta, non un comando.

**Batch successivi:** widget interattivi via App Intents (WWDC23), Control Widget e i cambiamenti di rendering di iOS 18 (WWDC24).

## 4. Transferable e `ShareLink`

`Transferable` è un protocol che descrive come un tipo si converte da e verso dati per condivisione, drag-and-drop e pasteboard — sostituendo il balletto `NSItemProvider`/UTI.

```swift
struct Card: Transferable {
  let name: String
  static var transferRepresentation: some TransferRepresentation {
    ProxyRepresentation(exporting: \.name)
  }
}

ShareLink(item: Card(name: "Pikachu"), preview: SharePreview("Pikachu"))
```

Rappresentazioni, in ordine indicativo di preferenza: `CodableRepresentation` (JSON, per i tipi della tua app), `DataRepresentation` (byte grezzi con un UTType), `FileRepresentation` (un URL di file), `ProxyRepresentation` (delega a un altro tipo `Transferable` — il caso più semplice, sopra).

Puoi dichiararne diverse; il destinatario sceglie la migliore che capisce. `ShareLink` poi ti dà il share sheet di sistema con una sola view.

## 6. Dove atterra in questo codebase

Nessuno di questi quattro esiste nel progetto. Ma i dati per alimentarli ci sono già.

`Demo/PokeApp/Models/Pokemon.swift` memorizza `name`, `shakespeareanDescription`, `spriteUrl` e `searchDate`. Basta per:

- **App Intent** — "mostra il Pokémon X", che ha bisogno della navigazione del Modulo 4.
- **Widget da lock screen** — il Pokémon cercato più di recente. La cronologia è già ordinata per `searchDate` (`SearchViewModel.swift:256`).
- **`ShareLink`** — condividere nome e descrizione di un Pokémon dalla view di dettaglio. Genuinamente una riga, una volta che `Pokemon` è `Transferable`.
- **Grafico** — ricerche per giorno da `searchDate`. Onestamente è debole: la cronologia di ricerca di un'app hobbistica non è un dato interessante. Fai il grafico per imparare l'API, non perché l'app ne abbia bisogno.

**L'unico ostacolo reale.** Un'estensione widget è un **processo separato** con un bundle separato. Non può leggere lo store SwiftData dell'app com'è configurato oggi, perché `PokeApp.swift:28` mette lo store in `URL.applicationSupportDirectory` — dentro il container dell'app stessa. Condividerlo richiede un **App Group** e lo spostamento dello store nel container del gruppo.

È un cambiamento architetturale vero, ed è la parte interessante dell'esercizio. Tocca anche il percorso di recupero dello store a `PokeApp.swift:27-47`, che oggi cancella e ricostruisce in caso di fallimento — con due processi che aprono lo stesso store, "cancella e ricostruisci" è una mossa considerevolmente più pericolosa di quanto fosse con uno solo.

## 7. Esercizio

Scegli **una** tra A e B. Sono entrambe feature reali; nessuna delle due è lavoro fine a sé stesso. Non fare tutti e quattro i framework — qui la larghezza serve all'orientamento, la profondità arriva dopo.

### Opzione A — `ShareLink` (piccola, ~30 minuti)

Fai conformare `Pokemon` a `Transferable` e aggiungi uno `ShareLink` alla view di dettaglio.

**Criteri di accettazione.**
1. Condividere su Messaggi produce testo leggibile con nome e descrizione.
2. `Pokemon` è una **classe** `@Model` di SwiftData — ragiona esplicitamente se rendere `Transferable` il modello stesso o introdurre un piccolo value type `Sendable` per la condivisione. Scrivi il tuo ragionamento. (Considera: le classi `@Model` non sono `Sendable`, e i valori `Transferable` attraversano confini di processo.)
3. Tutti i 71 test passano ancora; `swiftlint lint --strict` pulito.

### Opzione B — App Intent + widget da lock screen (sostanziale, diverse ore)

Esponi "mostra il Pokémon X" come App Intent, e aggiungi un widget che mostra la ricerca più recente.

**Fai prima il Modulo 4.** Senza un path di navigazione l'intent non ha dove mandare l'app.

**Passi.**
1. Aggiungi una capability App Group condivisa tra l'app e un nuovo target di estensione widget.
2. Sposta lo store SwiftData nel container del gruppo. Rivedi la logica di recupero a `PokeApp.swift:27-47` — con due processi, ragiona su cosa succede se il widget sta leggendo mentre l'app cancella.
3. Scrivi `ShowPokemonIntent`, usando `LocalizedStringResource` per `title` (non `String(localized:)`).
4. Aggiungi un `AppShortcutsProvider` così funziona in Siri senza configurazione da parte dell'utente.
5. Aggiungi un widget che supporta `.accessoryRectangular` e `.systemSmall`.

**Criteri di accettazione.**
1. L'intent compare nell'app Comandi rapidi e naviga l'app in esecuzione sul Pokémon giusto.
2. Il widget mostra la ricerca più recente e si aggiorna dopo una nuova.
3. Il widget è leggibile nella modalità di rendering accessory desaturata — controlla sulla schermata di blocco, non solo nella galleria widget.
4. VoiceOver legge il widget in modo sensato.
5. Tutti i 71 test esistenti passano ancora. La logica dell'intent è coperta da almeno un nuovo test.
6. `swiftlint lint --strict` pulito, e CI verde — nota che aggiungere un target cambia la build, quindi tieni d'occhio la prima CI.

```bash
xcodebuild test -project Demo/PokeApp.xcodeproj -scheme PokeApp -destination 'platform=iOS Simulator,name=iPhone 17 Pro'
xcodebuild test -scheme Pokespeare -destination 'platform=iOS Simulator,name=iPhone 17 Pro'
```

## 8. Trappole

- **`LocalizedStringResource`, non `String`,** per tutto ciò che il sistema mostra fuori dalla tua app. Le stringhe pre-risolte congelano il locale alla costruzione; Comandi rapidi potrebbe mostrare il tuo intent sotto un altro.
- **I widget sono un processo separato.** Nessuna memoria condivisa, nessun container condiviso senza un App Group, e un limite di memoria stretto — non decodificare un'immagine grande in una entry di timeline.
- **Non controlli il refresh del widget.** La timeline policy è un suggerimento contro un budget di sistema.
- **Le famiglie accessory sono desaturate.** Il significato veicolato dal colore sparisce. Usa `.widgetAccentable()` e affidati a forma e gerarchia.
- **I parametri di App Intents devono essere risolvibili senza la tua UI.** `perform()` può girare con l'app non in primo piano, o non in esecuzione affatto.
- **Le stringhe `.value("Label", …)` in Swift Charts sono visibili all'utente.** Sono etichette d'asse e voci di legenda — localizzale.
- **Un grafico senza etichette di accessibilità è peggio di nessun grafico** in un'app che ha già fatto bene VoiceOver.
- **Aggiungere un App Group cambia il provisioning.** Aspettati una deviazione sulla firma, e aspettati che la CI abbia bisogno di attenzione.
